# First adopter: the drain's post-merge follow-up becomes a durable queued job, done once per pass under the numbering lock

Slice of decision 4120 (daemon job model); audit we:reports/2026-09-24-daemon-blocking-antipatterns.md. Filed uncleared until 4120 is ratified; the shape below follows its bold defaults and changes with the ruling. Findings D2, D8. Today we:scripts/merge-ai-prs.mjs lines 4683-4880 run the post-merge work inline after the merges: pull, primary sync, JIT numbering, resolve-on-land, push, derived regen. The next pass cannot merge anything until it ends (observed 7-17 min today; most of it is D1, fixed by 4127, after which the follow-up is about 30 s), and a kill mid-way (45-min pass timeout, or a daemon restart whose clone refresh does reset --hard) loses the local numbering commit. Adversarial round constraints: this kind changes a git tree, so under 4120 Fork 2 it does NOT run from a code snapshot; it runs in its own dedicated working tree of main (never the daemon clone the next pass refreshes with reset --hard), with the hash ledger pinned to the state root, and holds the numbering lock with a heartbeat and no unlocked fallback (4134). Resolve-on-land cannot re-derive its input from main, so the job record must carry the pass's landed ids and carriers. The daemon's releaseAndExit must stop killing this job (#drain-daemon-self-hosting-boundary clause 2 amendment in 4120). Adopt after 4127, 4134 and 4121 land, and after the health daemon has proved the core. Shape: the merge loop records one follow-up job per pass (the merged set) and returns; a single serial follow-up job, holding the numbering lock with a heartbeat, drains the queue in a batch; each step is idempotent (numbering re-derives pending hashes from main; resolve checks status first; regen is deterministic). The merge loop keeps merging while follow-up runs; the ordering invariant (resolve only after the whole couple landed) is kept by reading the merged set from the record. Done when: tests for crash between steps; LIVE proof: a pass that merges 3 WE PRs ends within 90 s of its last merge, and the follow-up job's record shows numbering and push done once (timestamps in the PR).

## Design

Delivered flow, for orientation: the pass records one job at we:scripts/merge-ai-prs.mjs:6082-6085, keeps its own checkout sync (:6089-6098) and the stranded sweep and tripwire; the job runs the three steps of `followupSteps` (we:scripts/lib/drain-followup-job.mjs:150-215) in its worktree. This card closes the gaps.

1. **Heartbeat the job record from inside a step (gap 1, 5643 item 2).** `runJob` hands a step only `{ jobId, input, data, step }` (we:scripts/lib/daemon-jobs-runtime.mjs:412) and its interval heartbeat (:400-402) cannot fire while `execFileSync` or the lock's `sleepSyncMs` blocks the event loop. So the entry (we:scripts/drain-followup-job.mjs) opens `createJobStore(process.env.OPERATION_RUNS_DIR)` and builds `recordHeartbeat(jobId)`, which calls `markHeartbeat` (we:scripts/lib/daemon-jobs.mjs:257) through `store.update` only while the record's `job.handle` equals `selfHandle().handle` (we:scripts/lib/daemon-jobs-runtime.mjs:87, which returns an object); it returns false (never throws) when superseded, when `store.update` returns null, or when the file lock throws. `followupSteps` takes `recordHeartbeat` as a new dep (default a no-op returning true), and each step's `run({ jobId, input })` passes a `beat()` into the lock callback: `beat()` calls the lock's `heartbeat()` and `recordHeartbeat(jobId)`, and throws `drain-followup: heartbeat lost` only when either returns exactly `false` (gap 3; the real lock returns a strict boolean, while the lock callback default `(heartbeat = () => {})` and the test fakes return `undefined`, which must stay a pass or every existing step test breaks). `regenDerivedOnLand` (we:scripts/merge-ai-prs.mjs) is not changed; `beat()` is the FIRST statement in each lock callback, before `resetToRemoteTip`'s fetch (the 30 s lock wait plus the fetch can otherwise pass the 60 s stale limit before the first beat); step 2 also calls it before and after the regen, and a code comment states that one generator longer than 60 s is not covered (Follow-ups).
2. **Short lock wait (gap 2, 5643 item 2).** `underNumberingLock` (we:scripts/lib/drain-followup-job.mjs:137) passes `waitMs: 30_000` (a `lockWaitMs` dep so tests use 0). `withNumberingLock` already returns `ran:false` on contention (we:scripts/readiness/drain-lock.mjs:222), which the helper throws, so the runtime retries with backoff instead of the job blocking 5 minutes. `withLandWriteLock` shares the numbering lock key, so a merge waits for the job's hold; the PR body says that "the merge loop keeps merging while follow-up runs" is only partly true.
3. **Pin the hash ledger to the state root (gap 4).** The ledger (`LEDGER_REL`, we:scripts/lane-drain.mjs:597; read :841-843, written :1171 with a plain `writeFileSync`) is local and untracked and ignored, so it survives `reset --hard` and `clean -- backlog` in the reused worktree, but the worktree starts without the clone's history and a recreated worktree loses it; a later card citing an already-numbered hash would then stay a hash. Moving it to the state root makes it survive worktree recreation and carries the clone's history over once. `numberPendingHashes` (we:scripts/lane-drain.mjs:682) takes an optional `ledgerPath`; the entry sets it to a file in a `drain-followup-state` folder that is a SIBLING of the jobs folder, never inside it (the store reads every `*.json` there as a job record; since PR #4796 `list()` skips a well-formed JSON object with no `job` block via `isForeignJson`, we:scripts/lib/daemon-jobs-runtime.mjs:97, so a ledger there would be silently ignored rather than reported, but a torn ledger write would still be listed as a corrupt record, and the state must not depend on that sidecar rule). On EVERY run, inside the numbering lock, the launching clone's ledger is unioned into the pinned file (append-only, so safe to repeat; the inline fallback path and other callers keep writing the clone's ledger, so a one-time seed would let hashes numbered there drift out of the pinned copy) (the entry finds the clone with `git rev-parse --git-common-dir` from its worktree). The `ledgerPath` branch writes with `writeJsonAtomic` (we:scripts/lib/atomic-json-file.mjs); the inline path keeps `LEDGER_REL` and its plain write, unchanged.
4. **Incomplete open-PR context defers resolve (gap 5).** The inline code never consults `openPrContext.contextComplete` for resolve-on-land. `buildFollowupInput` (we:scripts/lib/drain-followup-job.mjs:69) gains `openContextComplete` (normalised to a boolean, default `false` = fail closed), and the call site (we:scripts/merge-ai-prs.mjs:6084) passes `!!openPrContext.contextComplete`. In step 1, when it is false every item `planResolveOnLand` (we:scripts/merge-ai-prs.mjs:1325) would resolve is reported `deferred` with reason `open-pr-context-incomplete` and `resolveLandedItem` is not called; numbering and push still run. This is deliberately MORE conservative than the inline path (which resolves regardless); the deferred ids are recorded in the step's checkpoint data so they are visible, and the backstop is the stranded sweep (we:scripts/backlog-stranded-sweep.mjs, auto-resolves a card whose id ends a real commit on `main`). The PR body states the behaviour change.
5. **A terminally failed job is replaced once (gap 6).** `reattachTick` fails a record on one tick only, so a later pass never sees it. A record that failed AT LAUNCH is already handled (the pass ran inline, we:scripts/lib/__tests__/drain-followup-wiring.test.mjs:120), so replacing it would redo done work. `handOffDrainFollowup` (we:scripts/lib/drain-followup-job.mjs:286) gains, before its enqueue and OUTSIDE the `if (landed)` guard (we:scripts/lib/drain-followup-job.mjs:309; a pass that landed nothing must still replace a failed job, like the reattach), a scan of `jobStore.list()` for `failed` records that ran (their `job.timeline` holds a `step-error` or `checkpoint` row, written by `markStepError`/`markCheckpoint` in we:scripts/lib/daemon-jobs.mjs), failed within the last 7 days, carry no `input.retryOf`, and have no record whose `input.retryOf` equals their id; for each it calls `enqueueJob` ONCE with the same input plus `retryOf: <id>` (a field inside `input`, so no runtime change) and logs it. `defineDrainFollowupKind` is given `maxAttempts: 5` (lock contention now throws and spends attempts from the same budget as real errors, so the default 3 would fail more often). A replacement that also fails stays failed and is returned as `failed: [{ id, error }]` and surfaced in the `--json` line (we:scripts/merge-ai-prs.mjs:6338) so it is loud; it is never re-enqueued again. The scan is skipped under `dryRun` and with the switch off. The pass-start resume is already covered: `handOffDrainFollowup` runs `reattach` on every pass, landed or not.
6. **Parameterised regression and bare-worktree smoke test (gap 7, 5643 items 1 and 4).** Tests below; no production code beyond items 1-5. The entry is NOT guarded or restructured (an `import.meta.url` vs `argv[1]` guard can silently no-op under a symlinked path such as macOS `/var`, leaving a dead record); the smoke test imports the entry's dependency modules (the lane-drain, merge-ai-prs, drain-lock and job-runtime modules) from the bare worktree in a child process instead.
7. **Daemon shutdown must not kill the job.** `releaseAndExit` lives in the plateau-app drain daemon, outside this scope. The job is spawned detached (`spawnDetached`, we:scripts/lib/daemon-jobs-runtime.mjs:188), so it is not the pass's child. The live restart test proves it; if the daemon's shutdown does kill it, the daemon-side fix is filed as a follow-up, not edited here.

8. **Queue-merged PRs are retired only when the job owns them durably (gap 8).** Retiring at hand-off is correct ONLY because the record already carries them (they are in `merged`/`landedItems` of the input) and item 5 replaces a failed job once. So: (a) the pass keeps retiring them at hand-off when `followup.handedOff` is true, and stays pending (existing inline rule at :6304) when it is false; the `queueFollowUpsClean` expression gets an explicit `followup.handedOff ||` arm and a comment, so this is a stated rule, not an accident of `landedLocal` being false; (b) `buildFollowupInput` keeps `mergedBy` on each `merged` entry (we:scripts/lib/drain-followup-job.mjs:76-77 drops it today; one extra string field, same normalisation as `repo`), and a job that stays `failed` after its one replacement is reported in `failed` (item 5) with the queue-merged PRs from its input named, because their state entry is already retired and nothing retries them. The message is its own wording (the strategy's message at we:scripts/lib/drain-merge-strategy.mjs:259 says "then remove it" from the state file, which does not apply once the entry is in `followedUp`): "run numbering, resolve-on-land and derived regen for these PRs by hand; their queue state entry is already retired". Moving the confirmation into the job itself is a Follow-up.

## Edge cases this change must handle

1. **Untrusted text** — the job input is the pass's own verdicts normalised to plain strings (`buildFollowupInput`, we:scripts/lib/drain-followup-job.mjs:69). Head refs and slugs are PR-author-controlled and reach git only as values compared in `planResolveOnLand`, never argv, a path, a shell or a regex. Test: a `--x` plus newline head ref round-trips the record store byte-for-byte and never appears in an injected `exec` argv. The replacement record copies the input verbatim, so the same holds for it.
2. **Truncated reads** — `store.list()` reports corrupt records separately and the tick leaves them alone; the failed-record scan reads the good records only and logs each corrupt entry, never reading it as "no failures". `openPrContext.contextComplete === false` is carried as `openContextComplete: false`, never as an empty open-ref list meaning "none open". Test for both.
3. **Shared state files** — job records update by compare-and-set in the 4125 store; `recordHeartbeat` goes through `store.update` with the handle check. The pinned ledger is written only inside the numbering lock with `writeJsonAtomic`, and seeded under the same lock only when absent. Stale-lock steal is the existing lock's (we:scripts/readiness/drain-lock.mjs), unchanged.
4. **Fail closed** — a failed enqueue, prepare or setup still returns `handedOff:false` and the pass runs inline (delivered, covered in the wiring test). New: a refused lock, a `false` heartbeat, an unwritable ledger path or a failed seed each throw so the runtime retries; none is read as "nothing to do". A failed push throws (existing). A terminal failure is reported, not silent, and names any queue-merged PR whose state entry was already retired (Design 8).
5. **Identity scoping** — records are keyed `newRunId('job-drain-followup')`; `retryOf` names the failed record id; the worktree and deps link are keyed by the launching clone's real path (delivered); the pinned ledger is one per jobs root; hash and NNN spellings both resolve through `planResolveOnLand`'s assigned map. `recordHeartbeat` writes only while the record names this process's handle.
6. **State over time** — a restart mid-job resumes from the checkpoint and each step resets the worktree to fresh `origin/main` first, so "numbering done once" means pushed once. A failed record gets one replacement ever (the `retryOf` check survives passes and restarts). A seeded ledger is append-only and never re-seeded. A 60-s stale heartbeat is covered by item 1; clock skew uses the store's injected `now`.
7. **Who wrote it** — records are trusted only from the drain follow-up jobs folder under the user's home (`drainFollowupJobsDir()`); `runJob` refuses without the job id, attempt and `OPERATION_RUNS_DIR` env; the ledger path derives from `OPERATION_RUNS_DIR` set by the launcher, never from PR text; `retryOf` is honoured only on a record the scan itself read from the same store.

## Proof plan

1. **Before:** from the last few passes' `--json` result lines and stderr step timings (the `createStepTimer` summary, we:scripts/lib/pass-timings.mjs) in the drain daemon's pass log, the last passes that merged WE PRs, with the pass-end minus last-merge gap and the inline numbering/regen/sync timings.
2. **Dry run on the live drain:** `merge-ai-prs --dry-run --json`; it ticks and enqueues nothing and writes nothing.
3. **Live, switch on (default):** one real pass merges 3 WE PRs, at least one carrying a hash-named card (otherwise there is nothing to number, `shouldPush` is false and there is no numbering commit to show). Record: pass end minus last merge under 90 s; the job record in the drain-followup jobs folder shows `number-resolve-push` and `derived-regen` each done once with `numbering.pushed: true`, with timestamps; `git log origin/main` shows exactly one numbering commit for the pass. Paste the record and timestamps in the PR body. Pre-warm the job worktree first so the first `git worktree add` does not eat the 90 s.
4. **Stall check:** covered by the real-process test above (a lock held late cannot block a step past 60 s now that the wait is capped at 30 s, so it cannot serve as the live blocker); the live proof instead polls the 3-PR job record's `heartbeatAt` every few seconds while the job runs (`markHeartbeat` keeps no timeline row, we:scripts/lib/daemon-jobs.mjs:257, so a finished record cannot show it) and pastes the samples, showing it advances during the lock wait and the push.
