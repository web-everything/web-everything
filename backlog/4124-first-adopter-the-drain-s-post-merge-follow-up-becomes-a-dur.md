# First adopter: the drain's post-merge follow-up becomes a durable queued job, done once per pass under the numbering lock

Slice of decision 4120 (daemon job model); audit we:reports/2026-09-24-daemon-blocking-antipatterns.md. Filed uncleared until 4120 is ratified; the shape below follows its bold defaults and changes with the ruling. Findings D2, D8. Today we:scripts/merge-ai-prs.mjs lines 4683-4880 run the post-merge work inline after the merges: pull, primary sync, JIT numbering, resolve-on-land, push, derived regen. The next pass cannot merge anything until it ends (observed 7-17 min today; most of it is D1, fixed by 4127, after which the follow-up is about 30 s), and a kill mid-way (45-min pass timeout, or a daemon restart whose clone refresh does reset --hard) loses the local numbering commit. Adversarial round constraints: this kind changes a git tree, so under 4120 Fork 2 it does NOT run from a code snapshot; it runs in its own dedicated working tree of main (never the daemon clone the next pass refreshes with reset --hard), with the hash ledger pinned to the state root, and holds the numbering lock with a heartbeat and no unlocked fallback (4134). Resolve-on-land cannot re-derive its input from main, so the job record must carry the pass's landed ids and carriers. The daemon's releaseAndExit must stop killing this job (#drain-daemon-self-hosting-boundary clause 2 amendment in 4120). Adopt after 4127, 4134 and 4121 land, and after the health daemon has proved the core. Shape: the merge loop records one follow-up job per pass (the merged set) and returns; a single serial follow-up job, holding the numbering lock with a heartbeat, drains the queue in a batch; each step is idempotent (numbering re-derives pending hashes from main; resolve checks status first; regen is deterministic). The merge loop keeps merging while follow-up runs; the ordering invariant (resolve only after the whole couple landed) is kept by reading the merged set from the record. Done when: tests for crash between steps; LIVE proof: a pass that merges 3 WE PRs ends within 90 s of its last merge, and the follow-up job's record shows numbering and push done once (timestamps in the PR).

## Design

Today the pass cannot end until the follow-up ends: after the merge loop, `sweepOnce` runs the local pull and primary sync (we:scripts/merge-ai-prs.mjs:5983-6036), then `numberPendingHashes` + resolve-on-land + push inside `withNumberingLock` (we:scripts/merge-ai-prs.mjs:6048-6141), then `regenDerivedOnLand` (we:scripts/merge-ai-prs.mjs:6185), all in the daemon's own clone, whose next refresh does `reset --hard`. A kill in that window loses the unpushed numbering commit. Slice 1 built the replacement; this card connects it.

1. **A per-kind switch, default inline (4120 adoption rule).** Add we:scripts/settings/drain-followup.json (namespaced, `{ "drainFollowup": { "enabled": false } }`, to pass the settings-files layout test) and a loader in a new we:scripts/lib/drain-followup-hook.mjs, mirroring `loadMergeQueueSettings` (we:scripts/lib/merge-queue-hook.mjs, called at we:scripts/merge-ai-prs.mjs:5497; errors fall back to defaults with a stderr warning). The loader also honours an env override `WE_DRAIN_FOLLOWUP=on|off` (env wins; the merge-queue hook has only the kill switch `WE_DRAIN_MERGE_QUEUE=off`, so `on` is new here) and a `WE_DRAIN_FOLLOWUP_SETTINGS_FILE` file override like `WE_MERGE_QUEUE_SETTINGS_FILE`, with the hermetic `{}` under test, so a CLI-level test can set it. This lets the live proof arm the job path without a settings commit. Sequence: merge with default off; the operator sets BOTH `WE_DRAIN_FOLLOWUP=on` and `WE_DRAIN_FOLLOWUP_REPO=<the drain's WE clone>` in the launchd environment (the plateau-app daemon spawns the pass with the inherited environment and sets neither; this card does not change the daemon) and restarts it; run the proof; then a one-line settings PR flips the default. Off = today's inline code, unchanged. On = the job path. Rollback is the env flag or one settings flip.
   - **Test seam.** The pass body is a closure inside `runCli`, so the hook exports two functions. `followupPassStart({ settings, dryRun, store, kindDef, tick, log })` does the pass-start resume (`tick` is the injected `reattachTick`) and the terminal-failure re-enqueue scan (see item 3), and does nothing under `dryRun`, with the switch off, or with the repo pin unset. `runFollowupPhase({ settings, landedLocal, dryRun, buildInput, enqueue, tick, runInline })`: switch off, `dryRun`, unpinned repo, or `landedLocal` false calls the `runInline` thunk (its no-op in the last case) and nothing else, with no enqueue and no tick; switch on with `landedLocal` calls `buildInput`, `enqueue` once, then `tick` once, and never `runInline`. Under `dryRun` with the switch on, `runFollowupPhase` also returns a `dryRunNote` string that the caller prints: `followup: armed` or `followup: inline (repo pin unset)` (a dry run enqueues nothing). Wiring tests drive these two functions, plus a source-shape pin that merge-ai-prs calls each once.
2. **Record, then return.** `runFollowupPhase` is called ONCE, at the numbering site (we:scripts/merge-ai-prs.mjs:6041-6141); the `runInline` thunk it receives is exactly that block, unchanged, and the call returns `{ jobPath: boolean, followupJob }`. The derived-regen block (we:scripts/merge-ai-prs.mjs:6182-6190) stays where it is, between which the stranded sweep and duplicate-id tripwire (6144-6180) keep their order, and is guarded by `&& !phase.jobPath` (the job runs regen as its step 2). So merge-ai-prs has five small touch points, not one: the settings load, the pass-start call, the numbering-site call, the regen guard, and `followupJob` in the `--json` result (plus the hoist below); the hook module holds all logic. With the switch off the file's behaviour is byte-for-byte today's. With the switch on and `landedLocal` true the job path runs: `buildFollowupInput({ passId, landedLocal, merged, landedItems: landedThisPass, carriers: landedCarriers, openHeadRefs })` then `enqueueJob({ store: createJobStore(daemonJobsDir('drain')), kindDef, input })` (we:scripts/lib/drain-followup-job.mjs:65, we:scripts/lib/daemon-jobs-runtime.mjs:98 and :141, we:scripts/operations/run-store.mjs:143). `landedCarriers` is built at we:scripts/merge-ai-prs.mjs:6082-6083 and `openHeadRefs` comes from `liveOpenHeadRefs` at :6093; hoist both (with the `unmatchedMerges` stderr warning) out of the inline block so both paths share one construction. The record carries the landed ids and carriers because resolve-on-land cannot re-derive them from main. `numbered` stays `{ assigned: [], committed: false }` and `derived` stays at its "not run" value; the `--json` result gains `followupJob: { id, enqueued }` so a caller can find the record.
3. **Launch and resume.** The pass that enqueues also runs one `reattachTick({ store, kinds: new Map([[DRAIN_FOLLOWUP_KIND, kindDef]]), maxConcurrent: 1, log: <stderr writer> })` (we:scripts/lib/daemon-jobs-runtime.mjs:273) so the job starts at once, and so does the START of every pass (before the merge loop), which resumes a job a restart killed. Neither tick runs under `--dry-run` (a dry run must not launch, requeue or fail real jobs). Every action the tick returns is logged on stderr, and a terminal `fail` action is also surfaced as `followupJob.failed` in the `--json` result.
   - **Heartbeat during synchronous steps.** The steps block in `execFileSync` and the lock's spin-wait, so the runtime's interval heartbeat cannot fire (stale threshold `DEFAULT_HEARTBEAT_STALE_MS` = 60 s); a pass-start tick would then classify a live job as stalled and SIGTERM it mid-push. `runJob` hands a step only `{ jobId, input, data, step }` (we:scripts/lib/daemon-jobs-runtime.mjs:397), so this API is BUILT here: the entry (we:scripts/drain-followup-job.mjs) opens `createJobStore(OPERATION_RUNS_DIR)` and builds a `recordHeartbeat` that calls `markHeartbeat` only while the record's handle still equals `selfHandle()` (a superseded child must not keep a replacement's record looking live); `followupSteps` takes it as a new dep and the lock `heartbeat` callback calls it, and a `heartbeat()` that returns false throws. `regenDerivedOnLand` also calls it between generators, since it otherwise runs all of them with no heartbeat against the 60 s limit. A runtime test blocks a step past `staleMs` and shows the tick leaves it alone.
   - **Terminal failure.** The kind keeps the runtime default of 3 attempts with backoff; the hook passes a larger `maxAttempts` (5). `retryOf` does not exist in the runtime today; it is introduced here as a field inside the replacement's `input` (`input.retryOf = <failedId>`), so no runtime change is needed. `followupPassStart` scans `store.list()` itself (a `fail` action from `reattachTick` fires only on the tick that fails the record, so a later pass would see none): for each `failed` record of this kind with no record whose `input.retryOf` equals its id, and that does not itself carry `retryOf`, it enqueues ONE replacement with the same landed/carrier/open-ref fields and logs it. `followupJob.failed` in `--json` is built from that scan. A replacement that also fails stays failed and is reported loudly, and a second pass does not re-enqueue (the stranded sweep, we:scripts/merge-ai-prs.mjs `runStrandedSweepStep`, plus the next pass's re-derived numbering are the backstop). The resolve-on-land input is therefore never silently lost. `kindDef` comes from `defineDrainFollowupKind({ prepareWorktree: makeFollowupWorktreePreparer({ repoDir, worktreeDir }) })` (we:scripts/lib/drain-followup-job.mjs:46 and :114): a linked worktree of main, never the clone the next pass refreshes. `repoDir` is pinned to the resident drain's own clone (path from the drain's config/env, `WE_DRAIN_FOLLOWUP_REPO`), NOT `process.cwd()`: a lane clone's `/pr` fast drain also runs this code, and a worktree added from a recycled lane clone would leave a dangling gitdir. The job path is armed only when that pin is set (the operator sets it with the switch, see item 1); a fast drain from a lane clone has it unset and keeps the inline path, so `pr-land`'s own numbering path never depends on this one. `worktreeDir` is `<state root>/followup-worktree`. Test: unset pin keeps inline even with the switch on.
4. **Keep inline what the job does not own.** The local `pull --ff-only`, the detached-cwd resync and the primary ff-sync (we:scripts/merge-ai-prs.mjs:5983-6036) stay in the pass: they only fast-forward clones and are cheap once the numbering work is gone. The stranded sweep (`runStrandedSweepStep`) and the duplicate-id tripwire (we:scripts/merge-ai-prs.mjs:6144-6180) read the pass's own clone; they stay, and the card notes that numbering now lags by one job.
5. **Pin the hash ledger to the state root.** The hash-to-number ledger is local and untracked (`LEDGER_REL` at we:scripts/lane-drain.mjs:597, read at :841-843, written at :1171) and its folder is a symlink, so the job's worktree starts with no ledger, and a later card that still cites an already-numbered hash would not be rewritten to its number (the observable difference: that citation stays a hash). Let `numberPendingHashes` (we:scripts/lane-drain.mjs:682) take an optional `ledgerPath`, set by the job entry (we:scripts/drain-followup-job.mjs, from `OPERATION_RUNS_DIR`) to a file in a SUBFOLDER of the state root (`followup-state/`), never directly among the job records (the store lists every `*.json` there and would report the ledger as a corrupt record every tick). It is seeded once from the clone's ledger if the pinned file is absent; the entry finds the clone through `git rev-parse --git-common-dir` from its worktree, and `followupSteps` takes `ledgerPath` as a new dep passed to `numberPendingHashes`. The `ledgerPath` branch writes with `writeJsonAtomic` (today's write at :1171 is a plain `writeFileSync`). The inline path keeps `LEDGER_REL` and its plain write.
6. **Daemon shutdown must not kill the job.** The self-hosting-boundary clause 2 amendment (we:docs/agent/platform-decisions.md, anchor `drain-daemon-self-hosting-boundary`) already says `releaseAndExit` no longer kills a detached follow-up job. `releaseAndExit` itself lives in the plateau-app drain daemon (outside this card's scope). The job is spawned detached by `spawnDetached` (we:scripts/lib/daemon-jobs-runtime.mjs:173), so it is not a child of the pass. This card proves that by the live restart test and, if the daemon's shutdown path does kill it, files the daemon-side fix as a follow-up rather than editing plateau-app here.
7. **Review debt from PR #4679 (card 5643), folded in because it is the same code:** the preparer must make `node_modules` reachable so the real entry runs unmodified in the worktree (symlink from the drain clone, plus a smoke test that imports the entry's dependency graph from a bare worktree); the step helper must throw when `heartbeat()` returns false; `withNumberingLock` is called with a short `waitMs` so contention throws and the runtime retries instead of blocking up to 5 minutes; and a parameterised test asserts reset-before-effects and primary-clone refusal for both steps. These tighten we:scripts/lib/drain-followup-job.mjs:103-190; they add no new behaviour.

8. **Incomplete open-PR context is new behaviour, not just wiring.** The inline code never consults `openPrContext.contextComplete`. `buildFollowupInput` gains `openContextComplete` (normalised to a boolean). When false, the resolve part of the step skips every landed item and reports it as `deferred` with reason `open-pr-context-incomplete`; numbering and push still run.
9. **Merges are not fully concurrent with the job.** `withLandWriteLock` shares the numbering lock key (we:scripts/readiness/drain-lock.mjs:247), so a merge waits for the job's lock hold (about 10-15 s per step). The pass still ends within 90 s of its last merge because the job runs after the loop; the claim "the merge loop keeps merging while the follow-up runs" is only partly true and the PR body says so.

## MVP

Musts only:

- The job's step heartbeat also writes the job-record heartbeat; terminal-failure re-enqueue once; dry run never ticks or enqueues; the pin on `repoDir`; `openContextComplete`.
- The switch file and loader; default off; the off path is byte-for-byte today's behaviour.
- With the switch on: one `drain-followup` record per pass that landed a local PR, carrying the landed items, carriers and open head refs; no inline `numberPendingHashes`, `resolveLandedItem`, `pushNumberingOnLand` or `regenDerivedOnLand` call; `followupJob` in the `--json` result.
- `reattachTick` at pass start and after enqueue.
- Ledger pinned to the state root.
- The 5643 tightenings (node_modules in the worktree, heartbeat-false throws, short `waitMs`, parameterised reset/primary-refusal test).
- Live proof (see Proof plan). The default flips to on only after the proof passes, as a one-line change the proof PR names.

Out of scope (Follow-ups): any plateau-app daemon change, other job kinds, a job dashboard, and moving the stranded sweep or tripwire into the job.

## Edge cases this change must handle

1. **Untrusted text** — the job input is built from the pass's own verdicts; `buildFollowupInput` already normalises every field to plain strings (we:scripts/lib/drain-followup-job.mjs:65-82). Head refs and repo slugs are PR-author-controlled: they reach git only as values compared in `planResolveOnLand`, never argv, a path or a shell. Test: a carrier `headRef` starting with `--` and containing a newline round-trips through the record and never reaches an argv.
2. **Truncated reads** — `store.list()` reports corrupt records separately and the runtime leaves them untouched (we:scripts/lib/daemon-jobs-runtime.mjs:281-284); the pass must log a corrupt record, never read it as "no job". The `gh` listings feeding the open head refs already fail the pass on a listing error. When `openPrContext.contextComplete` is false the wiring must not record an empty open-ref list as "none open": it records that the context was incomplete so the job defers resolve for that pass's items. Test for the incomplete-context case.
3. **Shared state files** — two writers: the job record (the 4125 store updates by compare-and-set on the generation) and the pinned ledger (written only inside the numbering lock, with `writeJsonAtomic`, we:scripts/lib/atomic-json-file.mjs). Seeding the ledger from the clone happens inside the same lock, only when the pinned file is absent.
4. **Fail closed** — a failed enqueue, a failed worktree prepare or an unwritable jobs folder must not silently drop the follow-up: the pass reports `followupJob: { enqueued: false, error }`, writes a loud stderr line and sets `ok: false` in the `--json` result (the exit code stays as today; exit 3 is reserved for the duplicate-id tripwire). It must NOT fall back to inline (that would run in the clone, unlocked). The numbering lock is taken with `runUnlockedOnContention: false` (we:scripts/lib/drain-followup-job.mjs:131-133). A push failure throws so the runtime retries on the new tip.
5. **Identity scoping** — the record id is `newRunId('job-drain-followup')`; `merged` entries carry repo + number; landed items are keyed as the pass keys them (hash and NNN spellings both resolve through `planResolveOnLand`'s assigned map). The kind is `serial`, so two records never run at once; a second pass's record queues behind the first.
6. **State over time** — a restart mid-job: the reattach classifies the dead handle and resumes from the checkpoint; each step resets the worktree to fresh `origin/main` first, so an unpushed numbering commit is discarded and redone ("numbering done once" means pushed once). A pass that lands nothing local enqueues nothing (`followupNeeded`); a pass that starts while a job runs neither duplicates it nor waits on it (the input is only this pass's landed set). Finished records stay terminal and are never relaunched. Host sleep is handled by the runtime's tick clock.
7. **Who wrote it** — a job record is trusted only from the daemon's own jobs folder (`daemonJobsDir('drain')`, under the user's home); the runtime's `isJobRecord` rejects anything else. The job claims its record from the `DAEMON_JOB_ID` / attempt env set by the launcher and refuses to run without them (we:scripts/drain-followup-job.mjs). The pinned ledger path is derived from the jobs root, never from a PR-supplied value.

## Proof plan

1. **Before** (captured first from the drain daemon's `daemon.log` under plateau-app's `.drain-daemon`): the last passes that merged WE PRs, with the `jitNumbering`, `derivedRegen` and `postMergeSync` timings (~11 s, ~14 s, ~7 s per card 5671) and pass-end minus last-merge time.
2. **Dry run on the live drain first:** run the merge sweep with `--dry-run --json` and `WE_DRAIN_FOLLOWUP=on`; the pass prints the `dryRunNote` from `runFollowupPhase` (`followup: armed`, or `followup: inline (repo pin unset)` if `WE_DRAIN_FOLLOWUP_REPO` is missing), ticks no job and writes nothing, which proves both env variables reach the pass. Before the live pass, pre-warm the job worktree (the first `prepareWorktree` runs `git worktree add` and a fetch inside the pass) so it does not eat the 90 s. (A dry run never plans a follow-up, because `landedLocal` is false under `--dry-run`.)
3. **Live, switch on:** let one real pass merge 3 WE PRs. Record that pass end minus last merge is under 90 s; that the job record in the drain's jobs folder shows `number-resolve-push` and `derived-regen` each completed once, with timestamps and `numbering.pushed: true`; and that `git log origin/main` shows exactly one numbering commit for the pass. Paste the timestamps and the record into the PR body.
4. **Restart mid-job:** land one WE PR, restart the drain daemon while the record is `running`, and show it reattached and finished without a second numbering commit, and that the daemon's shutdown did not kill it (the `releaseAndExit` check; if it does, record that and file the plateau-app fix).
5. **Rollback:** flip the switch off and show the next pass uses the inline path.
