# First adopter: the drain's post-merge follow-up becomes a durable queued job, done once per pass under the numbering lock

Finish the already-wired `drain-followup` adopter: one durable record carries each pass's landed set, a serial detached job does numbering, resolve-on-land, push, derived regeneration and primary sync, and the pass returns without waiting for that work. The governing rules are [we:docs/agent/platform-decisions.md#daemon-jobs](../docs/agent/platform-decisions.md#daemon-jobs) and [we:docs/agent/platform-decisions.md#drain-daemon-self-hosting-boundary](../docs/agent/platform-decisions.md#drain-daemon-self-hosting-boundary). A tree-changing job runs in its own linked worktree, uses the numbering mutex without an unlocked fallback, retains the pass input, and survives daemon shutdown. The switch is already default on. This is hardening and proof of that flow, not a new queue or switch.

Done when the remaining safeguards below pass their tests and a real pass merging three WE PRs ends within 90 seconds of its last merge, with job records and remote history demonstrating one numbering publication for that pass. The pass can continue independently, but merges sharing the numbering mutex can still wait for a job's critical section.

## Design

1. **Preserve the delivered topology.** Keep the serial, resumable, tree-mutating kind (`we:scripts/lib/drain-followup-job.mjs:51`), its dedicated worktree and parent dependency link (`we:scripts/lib/drain-followup-job.mjs:277`), and its three steps (`we:scripts/lib/drain-followup-job.mjs:173`). Keep own-checkout sync in the pass and separate-primary sync in the job. Keep inline fallback for switch-off, setup/enqueue failure, and unreadable or failed-at-launch records. One normal record represents one landed pass; do not coalesce different passes or infer their landed inputs from main.

2. **Fence job and mutex heartbeats at step boundaries.** The entry binds a `recordHeartbeat(jobId)` dependency using `createJobStore`, `selfHandle().handle` and `markHeartbeat` (`we:scripts/lib/daemon-jobs-runtime.mjs:124`, `we:scripts/lib/daemon-jobs-runtime.mjs:146`, `we:scripts/lib/daemon-jobs.mjs:257`). Only update a running record still owned by this handle and launch attempt; return false for a missing/superseded record or write failure. Construct this lazily so missing job environment still reaches the entry's existing refusal path. In the two writing steps, combine this with the lock callback's heartbeat; exactly `false` from either throws `drain-followup: heartbeat lost` before further effects. Test fakes returning `undefined` remain compatible. Refresh the record before entering the lock wait, then make the combined heartbeat the first statement after lock acquisition, before fetch/reset. Beat between numbering, resolution and push, before/after regeneration, and around primary sync using only the record heartbeat there. A checkpoint already refreshes the record, but is too late for a long synchronous step (`we:scripts/lib/daemon-jobs-runtime.mjs:438`).

3. **Bound contention honestly.** Pass `waitMs: 30_000` with `runUnlockedOnContention: false` from the job helper, with injectable `lockWaitMs` for tests. A refused lock throws and consumes a runtime retry, rather than waiting for the five-minute default (`we:scripts/readiness/drain-lock.mjs:200`). Set `maxAttempts: 5` when the hand-off constructs this kind, so both original and replacement enqueues persist the prior plan's five-attempt budget. The current shared default is three (`we:scripts/operations/job-record.mjs:36`); leave that default and existing records unchanged. Assert the budget on actual queued records, not only on a separately constructed test kind. Boundary heartbeats cover a long sequence of individually bounded operations; they do not run *inside* synchronous fetch, numbering, push, regeneration, primary sync, or lock polling. A single blocking operation beyond the 60-second stale threshold remains a limitation, not a claimed fix. The short lock wait prevents that wait alone from consuming the threshold; verify it with a fresh pre-wait record heartbeat. Do not claim continuous heartbeat advancement while a subprocess is blocking.

4. **Persist numbering bookkeeping outside disposable trees.** Add optional `ledgerPath` beside `dryRun` and `minNext` to `numberPendingHashes` (`we:scripts/lane-drain.mjs:682`). Omitted means the existing checkout-local behavior. The entry derives the pinned file beneath a `drain-followup-state` directory sibling to the jobs directory identified by `OPERATION_RUNS_DIR`; use a single shared ledger for this WE follow-up queue, outside worktrees and job records. A wrapper forwards all numbering options, including `minNext`, and supplies this path. Implement explicit-path ledger validation/import inside `numberPendingHashes`, before any no-work return: under the caller-held numbering mutex, read the launching clone's legacy ledger (locate the clone via the linked worktree's common git directory), import missing mappings, then run numbering. Keep the entry responsible only for deriving and forwarding the pinned path. Validate both ledgers as hash-to-positive-number objects, accepting the existing zero-padded decimal strings; reject arrays, null, malformed values and conflicting mappings. A no-pending invocation still preserves newly imported mappings in the pinned file. Create its parent directory only on a non-dry write. Missing legacy files are normal; malformed/unreadable ledgers and conflicting mappings must be reported and refused rather than silently replaced with empty data. Preserve the current held-card deletions, duplicate-birth checks and remote-birth fallback. Persist the resulting ledger with `writeJsonAtomic` from `we:scripts/lib/atomic-json-file.mjs`; do not re-union deleted mappings after numbering. Explicit-path reads must distinguish ENOENT from corruption, unlike the current catch-all read at `we:scripts/lane-drain.mjs:843`. A dry run never writes either ledger. Test recreation and repeated imports, including mappings added by the inline path between jobs. Do not claim ledger persistence alone fixes hash-to-number resolution after an already-completed numbering push.

5. **Carry complete resolve input and defer unsafe flips.** Extend `buildFollowupInput` with `openContextComplete`, default false, and pass `!!openPrContext.contextComplete` at `we:scripts/merge-ai-prs.mjs:6877`. Preserve optional `mergedBy` as a string on merged entries; retain `numberingOnBranch`, landed IDs, carrier refs, open refs and primary metadata. When context is incomplete, numbering/push still run, but every otherwise-resolvable ID from `planResolveOnLand` (`we:scripts/merge-ai-prs.mjs:1591`) goes to the checkpoint's deferred bucket with `open-pr-context-incomplete`; call no resolve mutator. Preserve existing couple deferrals. This is deliberately stricter than today's inline behavior, not parity. Existing positive fixtures must explicitly pass complete context; absent fields in old records fail closed. The stranded sweep remains a separate recovery path, not proof that every deferred item will later resolve automatically.

6. **Recover a terminal failure once, without losing provenance.** Keep the prior plan's bounded recovery: scan valid records of this kind on every enabled, non-dry hand-off, even if nothing landed. An original terminal failure whose `finishedAt` is valid, not in the future and at most seven days old, and whose timeline proves execution started (`started`, `step-error` or `step-applied`) gets one replacement carrying the complete original input plus `retryOf`. Exclude failed-before-start records because the pass already used inline fallback. A kill before the first checkpoint still qualifies through `started`. Never replace a replacement. Use a deterministic replacement ID derived from the original ID with `enqueueJob`'s explicit `id` and atomic `store.create` (`we:scripts/lib/daemon-jobs-runtime.mjs:193`, `we:scripts/lib/daemon-jobs-runtime.mjs:152`); two concurrent drain callers must converge on the same record. Re-read an already-created replacement; a corrupt collision is an error, not proof of successful enqueue. Scan before enqueue/reattach and collect failure visibility after reattach so a newly failed record is reported immediately and can be recovered next pass. Preserve these summaries on the existing enqueue/launch-fallback return paths too; a new pass's enqueue failure must not hide an older failed job. A matching existing replacement must have this kind, the expected `retryOf` and the same retained input before it counts as the one recovery; an unrelated valid record at the deterministic ID is also a collision error. Log corrupt IDs separately. Return persistent `failed` summaries for unrecovered originals and failed replacements, including IDs, errors and affected PRs, and include them in `followupJob` at `we:scripts/merge-ai-prs.mjs:7136`. An expired original remains visible even though automatic recovery is exhausted. A successful replacement suppresses its original's active failure report. Switch-off/dry-run do not perform this recovery scan.

7. **Make queue ownership explicit and avoid competing repair.** Queue-merged PRs already enter the landed input (`we:scripts/lib/drain-merge-strategy.mjs:484`). Retain the prior plan's hand-off retirement rule: confirmation means durable responsibility was accepted, not that asynchronous steps finished. Make `followup.handedOff` explicit in the confirmation expression at `we:scripts/merge-ai-prs.mjs:7101`, retaining numbering warnings and resolve/derived failure checks. Failed inline work stays pending. For a terminal job failure involving `mergedBy: 'github-merge-queue'`, report which PRs need manual numbering, resolve-on-land and regeneration, and that their queue entries were already retired; do not instruct removal from pending state. At `we:scripts/merge-ai-prs.mjs:6951`, skip `repairHashOnMain` when this pass handed off. The job checks fresh remote backlog filenames even without `numberingOnBranch` and requests `minNext` whenever the flag is true **or** hash cards are found, matching the inline condition at `we:scripts/merge-ai-prs.mjs:6957`. A pass without a hand-off keeps existing repair. This prevents this pass pre-empting its job; it does not claim to serialize every future recovery pass with every queued job beyond the existing mutex.

8. **Exercise the real entry and keep dependencies unchanged.** Add planned `we:scripts/__tests__/drain-followup-job-entry.test.mjs` as the matching entry suite. The existing wiring harness at `we:scripts/lib/__tests__/drain-followup-wiring.test.mjs:64` writes an immediate-exit stub, and the restart harness at `we:scripts/lib/__tests__/drain-followup-job.test.mjs:359` writes a custom test entry; neither covers production dependency binding. Import the real entry's dependency graph from a real disposable linked worktree with the actual dependency-link layout; separately launch the unmodified entry through the runtime against a temporary remote and controlled local command shims. Assert heartbeat ownership and ledger option binding through observable records/files, including no-job-env refusal. Do not add an import-only main guard that can silently skip execution through an aliased filesystem path. Existing helper tests keep covering crash/checkpoint behavior, reset-before-effects and primary-clone refusal. No shared runtime or daemon implementation changes are required by this plan.

4. **Heartbeat and contention evidence.** Sample the record's `heartbeatAt` from a separate observer while the job runs, alongside step/command boundaries. ## Follow-ups

- Heartbeats or bounded asynchronous execution inside a single long synchronous command, including numbering/fetch/push/regeneration/primary sync; boundary callbacks do not solve that case.
- Move queue confirmation to job success if the lifecycle is later changed from retirement on durable hand-off. This preparation retains the prior plan's semantics and makes failed ownership visible.
- Any plateau-app daemon shutdown change discovered by the restart proof. Record the actual daemon source path after inspecting that repository; detached process creation alone is insufficient evidence.
- Move stranded sweep and duplicate-ID tripwire only if separately scoped; they still run in the pass and can see a different point in numbering progress. Retain explicit deferred-ID diagnostics.
- Coordinate no-land queue repair with outstanding job ownership if cross-pass recovery races are observed; this card's hand-off guard prevents the demonstrated same-pass race only.
- Hash resolution after a push succeeded but its checkpoint did not persist: verify remote-birth behavior and file any remaining resolve gap separately; a pinned ledger is not by itself an `assigned` map for an already-numbered item.
- Changes to the shared runtime retry default or retroactive migration of existing job budgets require their own scope; this card binds the existing five-attempt proposal only to new follow-up records.
- Retire inline fallback/switch only after an evidenced soak and a plan for outstanding records; then reuse the proven pattern for other daemon jobs. Do not expand this card to those adopters.
