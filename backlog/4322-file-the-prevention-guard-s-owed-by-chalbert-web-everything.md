## Design

Implement the owed **cycle-detection** guard, without inventing a new aggregate size or priority policy for couples.

1. Extend the overlap-row projection in `we:scripts/merge-ai-prs.mjs` with stable, repository-qualified couple identity. Derive membership from manifest repo/ref membership in the full open-PR context (manifests and lane refs), including non-ready carriers, by reusing or extracting the couple indexing `joinImplToCouples` does (`we:scripts/merge-ai-prs.mjs:1225-1268`); never infer a couple from equal PR numbers. The INITIAL plan builds its rows (`overlapRows0`, `:5525`) BEFORE `planDrainPass` runs `joinImplToCouples` (`:2107`, the only writer of `coupleCarrier`/`coupleDefer`), so the verdicts it sees carry no join stamps: membership must NOT depend on them, or the initial plan and every replan (`:5554`, which sees stamped verdicts) would differ. The stamps may only ADD to the unknown set when present. Normalize the local repository slug consistently. Singleton PRs retain their own identity. Already merged members must not introduce fresh waits.
2. In `we:scripts/conveyor/land-overlap-yield.mjs`, compute the existing eligible overlap waits, then check their graph with couple members contracted into one node. Include known hard dependency/stack edges in the cycle check; those edges are never removed. Suppress overlap edges internal to a couple or inside a cyclic strongly connected component. Keep acyclic overlap edges and all existing eligibility, exemption, red-CI, and deadline behavior. This extends the existing exclusion of yields to a dependent target to the composed graph; it does not select a new winner between couples. Unknown membership must not be asserted complete: suppress the affected optional yield rather than risk a cycle. "Unknown" is defined narrowly, covering only rows that could be in a couple: a verdict carrying `coupleCarrier`/`coupleDefer`, or a body that contains the manifest markers but fails to parse or names an unresolvable repo/ref. `extractManifestFromBody` returns `null` for both an absent and a malformed manifest, so the projection must check for the markers itself to tell them apart; a body with no markers is a singleton and keeps its own identity (existing fixtures stay green). The row carries the membership as a `coupleKey` field (repository-qualified carrier identity, absent for a singleton) and an `membershipUnknown` flag; `overlapYieldWaits` reads only those two fields. The suppressed yield is reported through `overlapSkips` with a distinct token (e.g. `couple-cycle`, `couple-unknown`) and no yield-to PR (`pr: null`), and `logOverlapYields` (`we:scripts/merge-ai-prs.mjs:5509`) must print that token instead of its hardcoded `(red-ci) — required check failed` and dedupe on `${key}#${entry.token}` when `entry.pr` is null. Hard gates and couple atomicity continue to decide whether anything can land.

## Edge cases this change must handle

1. **Untrusted text** — PR bodies and manifests feed couple membership: read them only through the existing manifest parser (`extractManifestFromBody`, `we:scripts/readiness/lane-manifest.mjs`); a body that has the manifest markers but fails to parse yields "unknown membership" (optional yield suppressed, per Design step 2's narrow definition), a body with no markers is a plain singleton, and neither throws or uses the text in a regex/argv/path. Test: a marker-bearing body with newlines, backticks and a `--`-prefixed ref (unknown, suppressed), and a marker-free body (singleton, still yields).
2. **Truncated reads** — a PR whose file list is at the listing cap already reads `filesComplete:false` (never yields); the membership projection applies the same narrow rule to a truncated open-PR context (`contextComplete:false`): only a row that could be in a couple (a verdict with `coupleCarrier`/`coupleDefer`, or a marker-bearing body whose carrier is absent from the truncated listing) is unknown and suppressed; a plain singleton still yields, and fixtures that pass no `contextComplete` (the existing `buildOverlapRows` tests) behave as today. Test: truncated-context fixture with a carrier missing from the listing. No new `gh` reads are added.
3. **Shared state files** — n/a: the guard is a pure function over the in-memory rows of one planning pass; it writes no state file and takes no lock. The settings writer's fail-soft lock (`we:scripts/conveyor/land-overlap-yield.mjs:364`) is untouched.
4. **Fail closed** — a failed or unknown couple-membership read, or a cycle that cannot be ruled out, suppresses the optional overlap yield (the PR is held by hard gates only); it is never read as "no couple" and never as "assert a wait". Name the reason with a distinct token in `overlapSkips` (`pr: null`), printed truthfully by `logOverlapYields` (today it hardcodes `(red-ci)`). Test: unknown-membership case in Test plan 1 and the printed-line assertion in Test plan 2.
5. **Identity scoping** — membership and the contracted graph are keyed by `overlapRowKey` (repo + number, `we:scripts/conveyor/land-overlap-yield.mjs:175`) with the local repo normalized to `localSlug`; equal PR numbers in different repos never merge into one couple. Hash (`xNNNNNN`) and NNN item spellings resolve through `asItemId`. Test: equal-number-different-repo and local-null repository cases.
6. **State over time** — the guard is recomputed on every plan and replan from fresh rows (initial `overlapCtx0` and the replan closure), so a member merging mid-pass drops its influence and an already-merged member adds no wait; no cross-tick state is kept, so restart mid-operation is a plain re-plan. Budget expiry (rule 6) is unchanged. Test: replan after a simulated merge; expired budget.
7. **Who wrote it** — n/a: the guard grants no trust and reads no comment/label/ref as authorization; `ready-to-merge` label eligibility and review gates are unchanged and still decide whether anything lands.
