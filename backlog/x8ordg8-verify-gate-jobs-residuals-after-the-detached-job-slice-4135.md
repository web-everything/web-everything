# Verify gate jobs: residuals after the detached-job slice (#4135)

Follow-ups from 4135, seen live 2026-10-10. (1) The first launch for a new clone HEAD builds the readonly-tree snapshot synchronously inside the verify daemon tick (git archive + node_modules clone; 28 s live at 13:34:38Z-13:35:06Z), so that tick blocks; build snapshots off-tick or reuse the previous snapshot until the new one is ready. (2) When a gate supervisor dies and is relaunched while its gate still runs, the relaunch kills the surviving gate and re-runs it; it could instead re-attach to the surviving gate and settle it. (3) verify-lane notice lines now land in the job log under ~/.claude/daemon-jobs/verify-daemon/ instead of the daemon log; relay them. (4) "Is a gate alive" still fails open on a few edges (found by PR 4764 round-1 self-review): [fixed in PR 4764 round 4: the gate sidecar is now written `pending` BEFORE the spawn, carrying the run id the gate is spawned with (`--run-id=`); a supervisor killed between spawn and pid write leaves a pending sidecar, and the relaunch and the tick find the gate by that run id in `ps` (held, never killed, while any process carries it); a superseded job entry is killed only after a fresh handle probe (`killJobGate`), never by the registry pid alone; a gate is `dead` only once its whole process group is gone, so a leader that died while its test runners run on holds the lane (never killed on the group id alone)] [fixed in PR 4764 round 3: a sidecar with `handle: null` (process start time unreadable), a `foreign` host handle or a throwing probe now reads `unknown` — the lane is held and nothing is killed or started; a foreign handle is held with NO time bound — a held survivor stays in the live set, so the 6-hour prune never reaches its record — so a hostname change can hold a lane until someone clears the sidecar (see item 6); a handle-less sidecar that names its run id is released once its pid no longer carries that run id (a reused pid)] [fixed in PR 4764 round 5: before spawning, `runGateStep` refuses while ANY other gate job of the lane has a sidecar not proven gone (or an unreadable job record has one), and while `ps` shows a dispatched gate (`--repo=<dir>` with a `--run-id=`) on the lane that no sidecar names — never killing either; the pid is written before the start-time read, and a gate whose pid cannot be written is killed at once and its run failed, so a pending sidecar now only outlives a supervisor SIGKILLed in the synchronous instant between spawn and that write; gate start rewrites the in-memory record whole instead of re-reading it from disk (a torn read used to shrink it to a bare timestamp that named no gate)] [the check runs AFTER the job's own `pending` record (which names its lane) is written, so two jobs starting together each see the other's, and only the earlier record spawns; an unreadable job record blocks only the lane its sidecar names] Still open: a refusal on a gate found only by `ps` leaves no sidecar that holds the lane, so the tick queues a fresh job that refuses again each tick until that gate exits (hold the lane on the refusal instead); a lane compared as two spellings (symlink, relative path) escapes both the sidecar and the `ps` check; [fixed in PR 4764 round 6: `sync` collects every live job and held survivor of each lane; when the job owning a lane's entry ends, another holder takes the entry over in the same sync, so a rollback dispatch never sees the lane unheld for a tick; a job whose record will not parse keeps its registry entry instead of being read as removed] an in-process (rollback) gate's entry, deleted by its own settlement between a sync and the next dispatch, is not replaced by a survivor of that lane until the next sync (two gates had already overlapped to reach that state); a pending sidecar costs one synchronous `ps` per tick until its job ends (cap or cache it). [fixed in PR 4764 round 7 (operator ruling: a gate is gone only when CONFIRMED gone by pid + start time): a pending record, a handle-less pid that still exists, a malformed handle, an unreadable sidecar and any unrecognised record now read `unknown` (the run-id `ps` inference is gone), so such a lane is held until an operator runs the gate job's `release-lane` command; the clock ordering of pending records is replaced by an exclusive per-lane claim taken before anything is recorded or spawned, passed on only once the holder's supervisor and gate are proven gone; the dispatch sweep checks the claims before every start; a gate proven gone is written down as gone, so a later reuse of its pid cannot hold the lane again; two spellings of one lane (symlink, trailing slash) now compare as one (real path); an in-process gate's lane stays held until its whole process group is gone, not just its leader] Still open (round 7): a held lane is a registry entry, so held lanes count against the max-in-flight cap — enough quarantined lanes stop dispatch everywhere (exclude held-only entries from the cap, with the alert). (5) [fixed in PR 4764 round 3: rolling back with `WE_VERIFY_GATE_AS_JOB=0` still syncs the job store each tick, so a job-supervised gate holds its lane; only new gates run in-process.] [round 7: rollback also starts no gate supervisor, and the sweep checks the lane claims and the lane's processes before each in-process start.] (6) A held lane (unkillable or unprovable gate) logs one `⚠ HEALTH lane … is held` line per claim and is surfaced by the `fixer-verify-never-settles` smell through its stranded request; add a dedicated health smell that reads held lanes from the job store, with age escalation. Done when: unit tests per item and a live tick log showing no snapshot stall.

## Acceptance

- [A1] **Executable** — `npm run test:unit -- we:scripts/conveyor/__tests__/verify-gate-job.test.mjs` with one new test per open item: (1) a launch for a new clone HEAD returns before its snapshot is built; (6) a survivor held past a declared age is escalated (one alert, distinct from the first log line). Each fails before its fix lands.
- [A2] **Live** — a verify-daemon tick log across a clone HEAD change shows no tick blocked on a snapshot build.

## Non-goals

- [N1] Re-attaching to a surviving gate instead of killing it (item 2) is optional: refusing beside it, as today, is safe; this card only makes it cheaper.
- [N2] No automatic kill of a gate whose identity is `unknown` — escalation (item 6) alerts a person, it never signals a pid it cannot prove.

## Edge cases this change must handle

One line per class: either the handling, or `n/a: <why>`.

1. **Untrusted text** — the run id matched against `ps` output stays a validated token (`[\w.-]{1,128}`) compared as a whole argv token, never a regex or substring.
2. **Truncated reads** — `ps` is read with `-ww` and the shared reader's buffer; a timeout or an oversized read throws and reads as `unknown`, never as "no gate".
3. **Shared state files** — sidecars and the consumed list are written write-then-rename; a per-lane sidecar scan (item 4) must tolerate a sidecar being renamed under it.
4. **Fail closed** — every "is it gone" answer that did not run (probe, `ps`, group check) reads `unknown`: the lane is held and nothing is killed.
5. **Identity scoping** — a gate is identified by its handle (`host:pid:procStart`), its run id and its process group; a bare pid alone never proves identity.
6. **State over time** — a held lane has no time bound today; item 6 adds the age escalation, and item 4's foreign-host hold depends on it.
7. **Who wrote it** — n/a: the job store is written only by the verify daemon and its own job supervisors under this user's home.
