# Assistant session registry and escalation delivery

Make the operator session bootstrap write a durable registration (session id, account, host, capabilities, quiet policy, heartbeat), refreshed whenever sessions or accounts switch. Daemon escalations go to the needs-you feed plus a direct message to the live registered session, with evidence and a suggested pick. When no live session is registered (stale heartbeat), they fall back to a desktop or phone notification, or to the 07:00 digest during quiet hours. The session acknowledges each item in three steps: received, presented, decided. Operator 2026-10-17: "the assistant will move from handling to being on the receiver end".

## Design

### Registration and receiver lifecycle

Add a pure registration/state module at we:scripts/operations/operator-session-registry.mjs and its local filesystem/CLI adapter at we:scripts/operations/operator-session-registry-io.mjs. Store versioned state outside all lane checkouts, beneath the operations home adjacent to the handoff location resolved by we:scripts/operations/handoff-home.mjs. Use a private directory (0700), private records (0600), and the lock/atomic-write helpers in we:scripts/lib/atomic-json-file.mjs:64 (pass `mode: 0o600` explicitly); reject symlinks, non-regular records, malformed schemas and paths escaping that directory before invoking those helpers.

A registration contains schema version, session id, opaque account alias (never credentials), host id, feed identity, receiver capability (`monitor-inbox-v1`), quiet-policy snapshot with source, registration generation, registered time, and heartbeat time. Routing identity is the whole tuple, not a display name or session id alone. This is same-OS-user local coordination; account aliases label routing and do not prove provider authentication.

Keep the existing declared bootstrap operation and its GET surface read-only. Extend its plan/formatter to supply a concrete registration command, targeted Monitor command and stage-ack instructions. The standalone bootstrap CLI gets an explicit registration mode requiring session/account identity, which writes the durable record and returns that plan. The returned plan explicitly instructs the operator assistant to run this mode on every fresh session or account switch before starting its Monitor; no automatic provider lifecycle hook currently exists. Emit commands with resolved script paths and safely quoted arguments so they work from a different working directory. Keep we:scripts/operations/run.mjs:402 wired to the read-only collector; only the standalone CLI's explicit registration branch writes. The Monitor runs the new adapter's `listen` verb, proves ownership of the registration generation, emits queued envelopes, and refreshes heartbeat every 30 seconds. Freshness expires at 120 seconds; absent capability, malformed/future heartbeat, wrong host or expired generation makes direct delivery unavailable. These defaults and bounds live in planned we:scripts/settings/operator-session.json, resolved with provenance and exercised by the registry tests. Include `deliveryEnabled: false` while the prototype is ungraduated; an isolated proof explicitly enables it. Registration and read-only planning remain available when delivery is disabled, but no inbox emission, fallback or digest flush occurs through this new drain. Reject invalid explicit settings rather than silently accepting a fallback. Heartbeat interval, freshness, and receipt timeout must be finite positive millisecond integers, with freshness greater than heartbeat interval. Keep the existing feed enable/disable and interval settings authoritative for the supervised job; enabling delivery cannot resurrect a disabled or superseded job.

Only explicit bootstrap registration selects the operator receiver for this host/feed. Repeating the same registration is idempotent; switching identity replaces the active generation atomically. Require the previously observed generation when replacing an existing registration, so racing bootstraps cannot silently steal one another's selection. Heartbeat, listener and acknowledgement calls must match that generation; an old listener cannot resurrect itself. Stop on broken stdout or generation loss. A live listener is transport availability, not proof that the assistant read its output.

### Escalation publication and routing

Keep the needs-you feed as the durable source. Extend we:scripts/operations/needs-you-feed.mjs with versioned escalation envelopes carrying event id, subject identity, producer, timestamp, bounded reason/evidence references, options and suggested pick. Preserve legacy PR events and cursor commands. Support an explicit incident subject key as well as repo/PR/head/kind, including the current legacy `pr: 0` incident convention; #6187 can publish incident evidence without inventing a PR number. Event id includes the publication occurrence, so closing and reopening the same subject is a new ask. Validate complete identity fields before display truncation; long identities must refuse rather than collide. This is pinned by the named planned test `A3 rejects identity collisions before truncation` (we:scripts/operations/__tests__/needs-you-feed.test.mjs; see Test plan), which asserts over-limit identities are rejected before truncation can alias another subject. Normalize legacy items centrally: retain supplied pick/command as display-only suggestions; if neither exists, suggest inspecting the identified subject, without fabricating a ruling or evidence. Label missing producer provenance as legacy/unknown; explicit new envelopes must supply it. Retain bounded episode/link references and validated emergency metadata. Evidence bodies remain owned by their producer; send bounded, redacted references, not an arbitrary file read or the entire evidence bundle.

Planned we:scripts/operations/escalation-delivery.mjs computes routing and monotonic receipt transitions; we:scripts/operations/escalation-delivery-io.mjs owns durable attempts, targeted inbox writes and the checked desktop adapter. Extend the existing supervised loop in we:scripts/conveyor/needs-you-feed-job.mjs to drain published escalations on every tick, including when the current operator-queue read failed. Both `runOnce` and `publishAttention` therefore reach the same delivery path through committed feed replay without changing individual daemon publishers. They remain publication APIs; notification latency is bounded by the next successful supervised tick, not by publication return. Inject a separate drain callback into `runFeedLoop`, recheck job ownership after the producer settles (including throws), and call the drain even when collection failed. Recheck ownership before external sends; a superseded job must not send. Do not run an asynchronous drain inside the synchronous feed lock. Existing ordinary feed items remain compatible.

After feed publication, enqueue a direct envelope only for the current fresh capable registration. Record the attempt before advancing the delivery cursor. On missing/stale receiver, failed delivery, or no `received` acknowledgement within 120 seconds, use `notifyDesktopChecked` from we:scripts/conveyor/branch-sync.mjs. Its existing quiet gate holds routine notifications for the digest and preserves emergency breakthroughs. Each delivery drain also calls the existing `flushDigest` with the checked sender, even when there are no new feed events; notification success is required before removing held entries. Direct inbox delivery follows the original brief even during quiet hours; fallback follows the existing quiet policy. Quiet policy is re-read at delivery, not frozen at registration. Inspect `suppressed` before `ok`: `{ok:true, suppressed:true}` means `queued-for-digest`, never delivered, `received`, `presented` or `decided`. Persist that transfer and stop re-enqueuing the same fallback on subsequent ticks. The existing digest owner retries and confirms its own sends; it provides no per-event completion callback, so the per-item record stays `queued-for-digest` unless explicitly acknowledged. Call `flushDigest` with a checked sender whose quiet gate is disabled to avoid recursive gating. Unsupported desktop platforms and `{ok:false}` remain retryable failures. Existing quiet-policy read/queue errors retain the shared gate's deliver-now behavior; registry corruption still refuses mutations.

Drain all committed feed occurrences not yet attempted, using publication order and a durable outbox/cursor transaction. Add a strict reader for delivery: byte offsets advance only over complete validated records; stop visibly at malformed/oversized records or a truncated tail without skipping bytes or overwriting the feed. This cursor behavior is pinned by the named planned test `A3 strict replay cursor stops at invalid records` (we:scripts/operations/__tests__/escalation-delivery-io.test.mjs; see Test plan). Keep legacy display replay compatible. Assign stable occurrence ids at publication; map legacy occurrences from feed identity plus byte offset, not a timestamp or subject alone. If append succeeded but the open-key sidecar write failed, recover the open-key state from the committed log under the publication lock before publishing again. Derive the delivery cursor from the same atomic record as its pending attempts, never from the legacy user acknowledgement. Recover pending attempts after restart even when feed deduplication produces no new line. Recheck generation under lock before enqueue and receipt updates. Do not hold a state lock across an OS notification. Use a 30-second attempt lease (longer than the checked notifier’s 10-second timeout), revalidated before completion; an interrupted send is retryable. Completion-time revalidation is pinned by the named planned test `A4 expired lease cannot complete a replacement attempt` (we:scripts/operations/__tests__/escalation-delivery-io.test.mjs; see Test plan), which asserts a stale worker's completion is rejected. Delivery is at least once: a crash after emission and before recording success can repeat a notification, but cannot erase the escalation. Deduplicate by event id plus destination generation; account/session switches re-offer undecided items without resetting their event history. A cleared subject stops further prompts but is recorded as cleared, never silently converted to a human decision.

### Three acknowledgements and input boundary

The receiving assistant explicitly acknowledges an event as `received` after reading the Monitor envelope, `presented` after actually showing the evidence/options/pick to the operator, and `decided` only with the operator's recorded choice or a reference to the existing ruling. Stage changes require the preceding stage, are monotonic, idempotent and generation-scoped; repeated identical stages are successful no-ops, but skipping a stage or changing an already-recorded decision refuses. Store actor, account, host, event, stage and time; a new receiver records its own receipt/presentation. Existing decided history survives handoff. A decision receipt records the conversation outcome; it does not authorize a merge, clear a gate or apply the suggested command. The legacy global feed `ack` remains read-position compatibility only and never manufactures stage receipts.

No new HTTP endpoint, port or browser-triggered writer: registration/listening/acks are explicit local CLI verbs. CSRF/origin checks therefore do not apply; keep the read-only operation's HTTP regression. Bound registration/ack JSON input at 8 KiB and envelopes at 16 KiB, reject overflow before parsing, and bound strings/arrays. Rate-limit mutations per host/feed to 60 per minute, stored independently of registration generation; listener heartbeats are coalesced to one per 30 seconds. At most one logical direct attempt per event/generation and one terminal fallback outcome per event; retry interrupted emissions under the same attempt id, accepting possible crash-window duplicates rather than promising exactly-once physical delivery; failed fallback retries no more than once per existing feed tick. Reject replayed backward stages, foreign generations and reset/delete commands. No register or account-switch action may erase acknowledgements, clear pending deliveries or reset rate counters. Return explicit failure on unreadable/corrupt state, preserving bytes; never treat it as an empty registry with successful delivery.

## MVP

**Must**

- Explicit bootstrap registration plus a targeted, heartbeating Monitor receiver survives restart and account/session replacement. The read-only bootstrap operation remains read-only.
- Every committed escalation remains in the needs-you feed and is offered to the selected live receiver with evidence and a suggested pick. Lack of confirmed receipt invokes checked desktop fallback or the existing quiet-hours digest; no silent loss on transport errors.
- All three acknowledgement stages are durable per item and attributable; legacy cursor acknowledgement cannot masquerade as a decision.
- Invalid identity, corrupt/truncated state, failed writes and oversized input refuse the affected mutation. Source text, docs, configuration, data, titles and evidence are all untrusted display data; none becomes executable shell text or authority to bypass gates.
- Bounded input, persistent throttling, generation checks and no reset verb apply at the actual CLI boundary. Production wiring remains ungraduated until the real Monitor receipt proof below passes.

**Could / already-designed follow-ups:** phone transport and additional assistant receiver adapters. Desktop satisfies the brief's “desktop or phone”; new transports must implement the same identity, receipt and fallback contract. No change to escalation classification, human decision policy or incident evidence generation.

## Non-goals

No autonomous decision-making, automatic execution of suggested picks, changes to human review/merge authority, new incident triage, provider credential storage, phone service provisioning, or fleet-wide receiver election.

## Edge cases this change must handle

1. **Untrusted text:** sanitize and bound all display fields; explicit evidence references only, no shell evaluation or authority from message content.
2. **Truncated reads:** reject incomplete JSON and oversized records; preserve pending events and prior state, report the failed read.
3. **Shared state files:** lock read/modify/write transactions, atomic private files, attempt leases and generation checks; exercise concurrent child processes.
4. **Fail closed:** refuse invalid registration/receipts; failed direct delivery retains the feed event and attempts the established fallback, never claiming acknowledgement.
5. **Identity scoping:** session/account/host/feed/generation must match; no wildcard recipients or cross-account receipt reuse.
6. **State over time:** stale/future heartbeat, restart, DST, cleared/reopened asks and account replacement retain durable history; legacy cursor state is not a decision.
7. **Who wrote it:** preserve producer provenance and receipt actor separately; local account aliases are routing labels, not authenticated human approvals.
