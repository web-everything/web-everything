# Binding prior round: late findings on unchanged code become cards

Fixer/review proposal, operator 2026-10-08, P3. On code unchanged since round N, a finding that was tolerated or not raised in round N is filed as a card, not a blocker. The one exception is `broken` + `CONFIRMED`: a reviewer may still block a real defect (the #5399 floor rule). A re-raise of a finding marked "fixed" must say why the fix fails; without that it is advisory. Ruled: 3 days in shadow with a "would have blocked" journal first, then on. Needs the finding identity from 5469. The rule is a pure function in the protocol card 5468's shape.

## Acceptance

- [A1] **Executable** — replay fixtures: (a) a tolerated finding re-raised on unchanged code becomes a card; (b) a `broken`+`CONFIRMED` one on unchanged code still blocks; (c) a finding on changed code blocks as today; (d) a re-raise of a "fixed" finding with no reason is advisory.
- [A2] The mode is a declared setting: off (today) / shadow / on. Shadow journals "would have blocked" per finding and changes no verdict.
- [A3] Shadow runs at least 3 days; the switch to on is a settings change citing the journal's counts.
- [A4] Each auto-carded finding is covered by a backlog card with its identity and the round that tolerated it (findings sharing one `findingId` share one card that lists every member), and counted per finding ("auto-carded findings").
- [A5] **Proof** — on a live round-2+ PR, before/after: the shadow journal entry, then (after the flip) the card filed instead of the block.

## Non-goals

- [N1] No change to round 1, CI, or the drain's live gate.
- [N2] No round budget: that is 5471 (P5).

## Edge cases this change must handle

One line per class: either the handling, or `n/a: <why>`.

1. **Untrusted text** — the MVP reads no "why the fix fails" text (Design 6). Every model-supplied field that reaches a card title or body (summary, path, symbol, impact) is folded by `foldUntrusted` and label-prefixed; `line` is coerced to an integer (Design 5).
2. **Truncated reads** — unknown "changed since round N" status counts as changed: the finding blocks as today (the existing `bindingRoundDecision` branches; Test plan "Fail-closed cases").
3. **Shared state files** — the shadow journal and the filed-cards record are append-only. One filing per `findingId` group is decided by the append order of the record's `pending` line, with a per-group lock in front as an optimization (Design 5). A lock that is wrongly reclaimed can at worst let an expired holder file a duplicate card; it can never lose a blocker, and the first `pending` line still arbitrates.
4. **Fail closed** — missing identity, an unreadable ledger, a failed lookup, lock, record append or `file-item` call leaves today's blocking behaviour.
5. **Identity scoping** — `findingId` is NOT unique per finding, so "unchanged" and carding are decided per `findingId` group (Design 3), and prior statuses are folded per PR (a row of another PR is ignored). Card dedupe matches only an exact `findingId: fi-…` line (Design 5).
6. **State over time** — the 3-day shadow window starts at the journal's first line; there is no new setting and no clock check in this build (Follow-ups). A restarted or resumed `bind-round` writes rows and the journal entry once (Design 7); a repeat of the same group reuses its card (Design 5); a lock is reclaimed after the 10-minute TTL or when its same-host pid is gone, and a `pending` line with no `filed` line is abandoned after the TTL (Design 5).
7. **Who wrote it** — `CONFIRMED` is read from the finding itself (`requiresMandatoryReferral`), never from a ledger row. In `on`, prior statuses come from ledger rows whose `source` is `review-pr`; a foreign row can only add a `raised` status (a block), never supply `tolerated`, `fixed` or `carded` (Design 2). A prior head with no `review-pr` finding rows is a full review.

## Design

Today the shadow runs as the LAST effect of the `advise` step (we:scripts/operations/review-pr.mjs:2775), after the verdict is final. `recordScopedRereviewShadow` (we:scripts/operations/review-pr-io.mjs:341) reads the ledger and git, calls `shadowRound`, appends `finding` rows and the journal; it never changes a verdict. To make `on` real, the decisions must be known BEFORE the verdict is fixed:

1. **Setting.** Add `'on'` to `SCOPED_REREVIEW_MODES` (we:scripts/lib/review-settings.mjs:18). Env override keeps working through `resolveReviewSettings`. Every place that carries the mode to the compute must learn `'on'`: the read carry at we:scripts/operations/review-pr-io.mjs:311, `read.scopedRereview` (we:scripts/operations/review-pr.mjs:1130) and `basisLenses` (we:scripts/operations/review-pr.mjs:2708). The shadow effect gate (we:scripts/operations/review-pr.mjs:2775) is the one exception: it stays `=== 'shadow'` and must NOT learn `'on'`, so the `advise` shadow effect never runs in `on` (Design 7); `bind-round` writes the rows and journal in `on`. `resolveScopedRereviewMode` (we:scripts/operations/review-pr-io.mjs:408) already follows `SCOPED_REREVIEW_MODES` and needs no change. The shadow-mode start date is the journal's first line; there is no new setting for it (see Follow-ups).
2. **Extract the compute.** Split `recordScopedRereviewShadow` (starts at we:scripts/operations/review-pr-io.mjs:341) into `computeScopedRound({payload, exec, readLedgerRows})` (reads only: prior head, scope, prior statuses, per-finding symbol via `git show`, then `shadowRound`) and the existing recorder that appends rows and journal. `shadowRound` entries gain `priorRound` (from `foldFindingStatuses`' `round`). Shadow behaviour stays byte-identical. **Prior-status provenance:** `foldFindingStatuses` does not look at who wrote a row, so in `on` `computeScopedRound` passes it the ledger rows whose `source` is `review-pr` (the value `recordScopedRereviewShadow` and `bind-round` write), plus any `finding` row from another writer ONLY when its status is `raised` (a foreign row can add a block, never remove one). A foreign `tolerated`, `fixed` or `carded` row is dropped before the fold, so it cannot supply the prior status that `bindingRoundDecision` reads; the finding is then judged as if it had no prior row. The filter is applied in `on` only; shadow keeps reading every row, which keeps it byte-identical. **Prior-head completeness (fail closed):** with no prior row a finding on unchanged code is carded as `late-unchanged`, so a MISSING prior row must not be read as "tolerated earlier". In `on`, if a prior head exists (`lastReviewedHead` also counts `review-run` rows) but no `review-pr` `finding` row exists at that head, or any row write of the prior round was reported missed, `computeScopedRound` returns scope `all` (a full review) and `applyBindingRound` moves nothing.
3. **Where `on` applies: a new step after `reduce`, before the referral verdict (decided; option b).** Findings do not exist at read time: they are juror answers consumed inside the pure `reduce` compute (we:scripts/operations/review-pr.mjs:2453-2680), which has no git or ledger access, and `computeScopedRound` needs reduce's output (`scopedRereviewFacts`, `basisLenses`) plus `git show` for symbols. So `on` adds one step `bind-round` (an effect step with io, like `advise`) that runs AFTER the `mandatoryReferrals` effect (whose `blockedReferrals` / `pendingReferrals` it needs for the referral exclusion in item 4) and BEFORE `referralVerdict` (we:scripts/operations/review-pr.mjs:2721-2750). `referralVerdict` then reads `bind-round`'s output (the shortened lists and recomputed verdict) in place of reduce's. It runs `computeScopedRound` on reduce's output, then a new pure `applyBindingRound` (we:scripts/lib/review-round-rules.mjs) moves each finding whose entry is `decision: 'card'` out of the blocking set into `deferredAdvisory`. It never moves a finding with no entry, nor one with reason `confirmed-broken` (we:scripts/lib/review-round-rules.mjs:269). Any throw or unreadable ledger returns the unchanged lists.
   - **Entry-to-original mapping.** `scopedRereviewFacts` (we:scripts/operations/review-pr.mjs:3063) rebuilds findings as copies, so entries refer to copies. `findingId` is NOT unique per finding: `findingIdentity` (we:scripts/lib/review-round-rules.mjs:128) hashes only repo, pr, path, symbol and defect class, never line, verdict or impact, so two findings in one function (or two with an empty symbol) share an id while carrying different decisions (one `confirmed-broken`, one `card`). Matching by id alone would move both and drop the mandatory-referral blocker. So `applyBindingRound` groups entries by `findingId` and moves an ORIGINAL only when its whole group is carded: every entry sharing that id decides `card`, AND the number of entries equals the number of BLOCKING-SET originals with that id (an original with no entry of its own keeps the group blocking; originals already in `deferredAdvisory` are not counted, they never have entries). Originals carry no id of their own, so `computeScopedRound` returns, for each input item, its `findingId` aligned by index, and every `shadowRound` entry carries its `itemIndex`; `applyBindingRound` joins on that index, never by position guesswork. Any `block` entry in the group, or a count mismatch, keeps every original in the group blocking. The moved originals keep their lens-prefixed category. Tests: two findings, one carded, the right original moves; two originals sharing one `findingId` with mixed decisions (`confirmed-broken` + `card`) both stay blocking and the verdict does not flip; a shared-id group with an entry-less blocking sibling stays blocking; a shared-id group where one sibling is already in `deferredAdvisory` and the other is carded still cards (the deferred one is not counted).
   - **Verdict recompute.** The panel verdict is built inside `reduce` from `verdictAdmitted` (per-lens `deriveVerdict` at we:scripts/operations/review-pr.mjs:2616-2620, then `derivePanelVerdict` at :2655 and `deriveLoopOutcome` at :2677), and `verdictAdmitted` (which excludes the advisory seat) is not in reduce's output. So `reduce` must also expose `verdictAdmitted`; `applyBindingRound` drops the carded originals from it and the `bind-round` step recomputes `lensVerdicts`, `admittedFindings`, `verdict` and the loop outcome with those same functions. `deriveAdvisoryOutcome` (we:scripts/operations/review-pr.mjs:1899) re-derives from `lensVerdicts` + `admittedFindings`, so both must be the recomputed ones. The builder confirms `referrals`, `deferredAdvisory`, `humanRequired` and `pendingReferrals` also see the shorter list.
4. **Composition with the live rules.** `bind-round` runs AFTER `classifyReferralsByRound` / `classifyLaterRoundAdvisory` (we:scripts/operations/review-pr.mjs:2564-2580), so it only sees what they kept; it never re-promotes anything. A finding that is a kept or block-ruled referral (`blockedReferrals`, `pendingReferrals`) is excluded from carding, and the exclusion is decided per `findingId` group like Design 3: if ANY original in a group is a kept or block-ruled referral, no original in the group is carded (a referral may be keyed by an id that other findings share). So no carded copy ever binds to a block-ruled referral, and `referralVerdict`'s existing promotion of a block-ruled referral's deferred copy (we:scripts/operations/review-pr.mjs:2731-2736) is untouched: it only skips copies tagged `binding-round`, which by construction have no referral. The existing `referralVerdict` promotion of deferred findings back to blocking (we:scripts/operations/review-pr.mjs:2736-2745) must not promote a `bind-round` card: carded findings are tagged `deferred: 'binding-round'` and the promotion skips that tag. Test both.
5. **File cards.** For each carded entry, `bind-round` calls the `file-item` operation in-process (we:scripts/operations/file-item.mjs) for the WE backlog: kind task, size 1, no parent, `queue=false` (so the conveyor does not dispatch an auto-card to a builder), title from the folded summary, body carrying `findingId: fi-…`, the PR, path/symbol/class, and the round that tolerated it (`priorRound`, `priorStatus`). **One card per id group.** The unit that is filed and deduped is the `findingId` group, not the single finding: findings that share an id (Design 3) go on ONE card whose body lists every group member's folded summary, line and impact, so a second finding with a shared id is never silently "linked" to a card that records only the first. **Order of operations, per group:** take the lock (below); read the record (the dedupe below): a live `filed` hit means LINK and stop; only a missing or retired hit goes on to claim. **Exclusivity: the claim.** One filing per group is decided by the APPEND ORDER of the filed-cards record, not by the lock. Before `file-item`, the step appends `{findingId, memberSet, state: 'pending', owner: <unique token>, checkout, at}` as one `O_APPEND` line (capped at 4 KiB, written with a leading `\n` so a torn tail never glues onto it), then RE-READS the record: the first CLAIMABLE `pending` line for that (`findingId`, member set) in file order wins. A `pending` line is not claimable (it is retired) when a `filed` or `discarded` line for the same group and member set follows it, or when it is abandoned: older than the 10-minute TTL (an unparseable `at` counts as abandoned) with no `filed` line and no written card found by the recovery below; the next claimant appends its own line and the first claimable line wins again. If the winner's owner is not this token, this round lost: it writes nothing more and its finding stays blocking. **Reader rule:** an unparseable line, or a tail without a newline, is UNKNOWN; the claim cannot then be proven first, so the round loses and the finding stays blocking. The record must live on a local filesystem (`O_APPEND` is not atomic on NFS). Immediately before `file-item` the holder re-reads the record and aborts, filing nothing, if its `pending` line is no longer the winner. Once `file-item` has run, it appends its `filed` line (with the `cardId`) regardless of who is now the winner, so an orphan card is never invisible to later dedupe; any duplicate that results is the stated leftover risk. In front of the claim sits a per-`findingId` lock, an optimization that keeps rounds from racing each other: an atomic `mkdir` directory beside the journal holding hostname, pid, timestamp and a unique token (the review daemon is assumed single-host per journal directory; a lock from another hostname is only reclaimed by age). **The check-then-act window:** reclaiming a stale lock is "inspect it, then remove it", and a rename by path after a separate inspection can remove a lock that was replaced in between. Waiter A inspects the stale lock; waiter B renames it away and `mkdir`s a fresh lock; A's rename now moves B's FRESH lock, and the emptied path lets a third waiter `mkdir` too. Renaming back does not close it (the path may already be re-created, so the rename-back fails). So reclaim takes a second exclusive guard first: `mkdir <lock>.reclaim` (a waiter that cannot create it loses and stays blocking), re-reads the lock's token and timestamp WHILE HOLDING it, and proceeds only if they still equal the stale snapshot it inspected; then it renames the lock to a unique name, `mkdir`s anew and removes `<lock>.reclaim`. A `<lock>.reclaim` older than the TTL is removed by the next waiter with a plain `rmdir`; two waiters racing that removal can at worst both reach the claim, which arbitrates. A lock is reclaimed when older than 10 minutes or when its same-host pid is gone, so a crashed holder cannot freeze a finding as blocking forever. A lock directory with no readable token yet (the window between `mkdir` and the token write) is judged by its directory mtime against the TTL. If the fresh `mkdir` fails after the rename, the reclaimer loses and stays blocking. A holder releases its lock only after re-reading that the token at the path is still its own. **Leftover risk, stated plainly:** a holder that stalls past the TTL between its last re-read and `file-item`, or inside `file-item` itself (its `at` is not refreshed, so another claimant sees an abandoned line and no card yet), can still file once more after another claimant took over. The worst outcome is a duplicate auto-card; no blocker is ever lost or accepted by this. Failing to take a live lock leaves the finding blocking. A resumed `bind-round` is a new owner and loses to its own crashed `pending` line until the TTL passes; that is fail-closed, and its cost (a round blocked for up to 10 minutes) is accepted. **Dedupe, in this order:** (1) the **filed-cards record**, an append-only `bound-cards.jsonl` beside the journal. The record is written in two lines: the claim line above (`pending`, with `pr`, `round`, member set, owner token) BEFORE `file-item`, then `{findingId, state: 'filed', cardId, owner}` right after it. A crash between the card write and the second line leaves a `pending` line with no `filed` line; recovery looks in the `backlog/` of the checkout root recorded on that `pending` line for a card with the exact `findingId:` line AND the exact `members:` line of the same member set, and, if found, writes the missing `filed` line instead of filing again. Both lines record the **member set** (a hash of the group members' `path:line` keys); the `pending` line records the checkout root, and the `filed` line the card's file path and its `bornAs` hash (a card is born under a hash-based file name and renamed to its backlog number when it lands, so the path alone does not survive landing; the card's `bornAs:` frontmatter does). The card body carries `findingId: fi-…` and `members: <member-set hash>` as two exact lines of its own. A `filed` hit is reused only when its member set equals the current group's; a group that has GROWN or changed since (round 3 adds a member round 2 did not have) gets a new card for the new member set, never a link to a card that does not list it. A `filed` hit is never re-filed merely because its card file is absent from the checkout and `origin/main` (it may sit in an open PR or a cleaned-up lane): absence alone LINKS the recorded `cardId`. The ONLY positive discard signal is that a card carrying the recorded `bornAs: <hash>` line was DELETED on `origin/main` and no file on `origin/main` carries that line any more: `git log origin/main --diff-filter=D --format=%H -S'bornAs: <hash>' -- backlog/` prints a commit AND `git grep -l 'bornAs: <hash>' origin/main -- backlog/` prints nothing. The test goes by content, not by the recorded path, because landing renames the card (a rename is not a deletion, and the renamed card still carries its `bornAs:` line, so it is linked). A card with any `status:` value still exists and never counts as a discard. On a positive discard the step appends `{findingId, memberSet, state: 'discarded', cardId}`, which retires the earlier `pending` and `filed` lines for that group and member set, then claims again and re-files with a new `cardId`. A `filed` hit whose card file still exists (in the daemon checkout's `backlog/` or on `origin/main`) is linked, not refiled. **Known gap:** a card that never landed and whose PR was closed unmerged is never deleted from `origin/main`, so it stays linked forever (Follow-ups). This is what catches a card that is written but not yet landed: the `origin/main` tree cannot see it, the record can. (2) A grep of the `origin/main` `backlog/` tree for a card with BOTH a line that is exactly `findingId: fi-<id>` (anchored, multiline `^findingId: fi-[0-9a-f]{12}$`, never the bare id) AND the exact `members: <hash>` line of the current member set (a card with the right id and another member set is a miss, so a grown group never links to a card that does not list its new member): card bodies hold folded untrusted finding summaries, so an unanchored match would link a finding to a card that merely quotes its id. The step writes that line itself and runs EVERY model-supplied field it puts in the body or title (summary, path, symbol, impact; `line` is coerced to an integer) through `foldUntrusted`, which removes newlines, and prefixes each member's folded text with a fixed label (`member: `), so no field can begin a line with `findingId:` or `members:`. A failed lookup, a failed lock, a failed record append or a failed `file-item` call leaves the finding blocking. **Durability:** `file-item` writes the card file into a checkout and does not land it; landing goes through the normal verify and `open-pr` path, which this step does not run. So the durable record of a carded finding is the ledger `finding` row with status `carded`, the journal entry (`autoCarded`, `cardIds`) and the filed-cards record; the card is landed later, and an unlanded card is reused by the next round rather than duplicated. **Landing owner:** no step in this build lands a card. The journal entry therefore records `unlandedCards` (recorded `cardId`s whose `bornAs` hash is on neither `origin/main` nor the recorded checkout), so a card lost with a reset daemon checkout or a closed PR is visible in the A3 counts rather than silently linked; the sweep that re-files or lands such cards is a Follow-up.
6. **Re-raise of a "fixed" finding.** In the MVP `reraise-of-fixed` always cards (already the rule's behaviour, we:scripts/lib/review-round-rules.mjs:282), which satisfies A1(d) "no reason → advisory". Accepting a stated "why the fix fails" is a Follow-up: the field does not exist and the finding normalizer would strip it.
7. **Journal, no double count.** In `on`, `bind-round` recomputes the ledger rows AFTER `applyBindingRound` and the filing outcome: a group that was actually filed or linked gets status `carded`; a group kept blocking by the group rule, a referral, a lock/filing/lookup failure keeps `raised` (otherwise the next round would see `carded` for a finding that never left the blocking set, or `raised` for one that did and block it as `sent-back-carry`). It writes the finding rows and the journal entry itself on EVERY round, including round 1, a full-scope round and a round where `computeScopedRound` throws (the rows are the next round's prior statuses, so a skipped write would let a real blocker be carded as `late-unchanged`); a failed row write is journaled as `findingRowsMissed`, which the next round's prior-head completeness check (Design 2) reads. Entry: `mode: 'on'`, `unlandedCards` (Design 5), `autoCarded` (a count of FINDINGS) and `cardIds` (the deduped card list); each `on` entry also records the effective outcome (`applied: true|false` plus a `heldReason` such as `group-mixed`, `referral`, `lock`, `filing`), so the A3 counts cite what actually left the blocking set, not the raw rule decision. Shadow stays byte-identical and so ignores the group, referral and lock rules: its "would have accepted" count is an upper bound, which the flip must say when it cites it. The rows and entry are keyed by (pr, head, round, `findingId`) and skipped when already present, so a replayed or resumed `bind-round` writes once. The check and the append are not atomic, so two same-head rounds can both append; readers de-duplicate by that key (the fold is last-wins per `findingId`, and the A3 counts count each key once), so a duplicate line cannot double-count; the `advise` shadow effect (we:scripts/operations/review-pr.mjs:2775) is skipped when the mode is `on`, so rows and counts are written once. Shadow entries keep their would-block / would-card rows. Reuse `appendScopedRereviewJournal` (we:scripts/operations/review-pr-io.mjs:322).

## MVP

Musts:
- `'on'` accepted by the setting; `off` and `shadow` unchanged.
- `computeScopedRound` extracted; `applyBindingRound` pure, with a replay path for `on` (extend `replayPrRounds`, we:scripts/lib/review-round-rules.mjs:395, to apply the decisions).
- The `bind-round` step, composed after the existing round rules (Design 3-4), with `reduce` exposing `verdictAdmitted`.
- The replay CLI (we:scripts/operations/review-round-replay.mjs) gains an `on` mode and a `--dry-run` that prints the blocking set before/after and the `file-item` payload (the Proof plan needs it).
- In `on`: carded findings leave the blocking set; each `findingId` group is filed through `file-item` (`queue=false`) once, deduped by `fi-` id and member set, with exclusivity from the first non-abandoned `pending` line of the filed-cards record behind a lock (reclaimed through a `.reclaim` guard, Design 5), and counted per finding in the journal (`autoCarded`). The claim, lock, filed-cards record and anchored lookup helpers live in we:scripts/operations/review-pr-io.mjs (in scope).
