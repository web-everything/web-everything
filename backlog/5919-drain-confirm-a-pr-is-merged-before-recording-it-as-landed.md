# Drain: confirm a PR is MERGED before recording it as landed

After gh pr merge returns, the drain (we:scripts/merge-ai-prs.mjs, the mergePr write site before merged.push) adds the PR to merged/landedThisPass, posts its landed trace and starts post-land work without checking GitHub actually merged it. Once main has a merge-queue ruleset, a drain-direct pass (a stale drain clone, a lane's /pr or /finish run that reads its own branch's we:scripts/settings/merge-queue.json, a pr-watch fast drain, a manual /drain) gets gh pr merge turned into an enqueue, and the PR is recorded as landed early even if merge-group CI then fails. Fix: require a fresh, explicitly repo-scoped MERGED response after mergePr; otherwise report an unconfirmed write, never landed, and retain durable follow-up tracking. Found in the PR #4950 fix round (merge-queue switch runbook); that runbook lists this card as a precondition for the switch. Add a soak break for the live case.

## Edge cases this change must handle

One line per class: either the handling, or `n/a: <why>`.

1. **Untrusted text** — n/a: the check reads GitHub's PR `state`/`mergedAt` fields, not free text.
2. **Truncated reads** — a failed or empty re-probe counts as NOT merged (never as landed).
3. **Shared state files** — the drain's queue follow-up state (`queueStatePath` in `we:scripts/lib/drain-merge-strategy.mjs`) must not get a landed entry for an unconfirmed merge (asserted by A1's case “unconfirmed write leaves no landed entry in queue state”).
4. **Fail closed** — any re-probe error records the PR as unconfirmed, not landed; durable pending state allows a later pass to re-check it.
5. **Identity scoping** — the re-probe names the PR's own repo (`--repo`), never the cwd default.
6. **State over time** — GitHub may report MERGED a moment late; use one immediate confirmation read; an unconfirmed PR stays pending for the existing follow-up collector, without sleeping inside the writer lock (asserted by A2's case “no sleep or poll while holding the writer lock”).
7. **Who wrote it** — applies to every caller of the drain (resident daemon, lane `/pr` and `/finish`, `pr-watch` fast drain, manual `/drain`), since the check sits at the shared write site (asserted by A5's case “every drain caller confirms direct writes” and A6's real-daemon soak).

## Design

1. In `we:scripts/merge-ai-prs.mjs`, add a fresh post-write read of state using the candidate's explicit repository (`c.repo || localSlug`), refusing to write if that identity cannot be resolved. Accept only parsed state MERGED; OPEN, CLOSED, empty/malformed output, contradictory mergedAt-only evidence and read errors are unconfirmed. Do not reuse a cached pre-write read. Use one read, no sleep or polling loop. Put this in an exported helper that takes the state reader and sleep function as injectable dependencies, so A2's case can assert it directly.
2. In `we:scripts/lib/drain-merge-strategy.mjs`, add pending-intent registration using the existing entry metadata (repo, number, head SHA, item, manifest flag, head ref, title). Mark new entries with `origin: direct-write`; missing origin retains the legacy queue meaning. Register after successful head revalidation and before the direct merge write, outside the already-held land callback, through the existing locked read-modify-write machinery. Use the injected lock that refuses unlocked fallback; never acquire it recursively inside the land callback (asserted by A3's case “registration never takes the state lock recursively inside the land callback”). Store the revalidated head and canonical repository identity, normalizing legacy local null-repo entries against localSlug when comparing keys. Deduplicate by repo plus number, preserve peer entries, enqueueFailures, redTeamPending and followedUp completion keys (including a concurrent completion between registration and writing; the enqueueFailures/redTeamPending preservation is asserted by A3's named case), and refuse the merge when the state file is unreadable, the lock is refused or the write fails. Return a structured refusal and skip the candidate before entering the land callback or its permissive merge-error recovery; persistence errors must not fall into that recovery. An absent file may be created. A pending intent is not evidence of enqueue or land. Retain it on command failure or unknown outcome: subsequent confirmed MERGED/CLOSED determines recovery or retirement.
3. At the direct write site in `we:scripts/merge-ai-prs.mjs:6854`, replace unconditional success with the confirmation result. Before the existing landing bookkeeping, an unconfirmed result sets the remaining candidate to skip, leaves dependents blocked and appends `{num, repo, headSha, reason}` to an additive JSON `unconfirmed` list. Emit a concise diagnostic without claiming enqueue. Return an unconfirmed result rather than throwing into the permissive existing exception-recovery check. Never call the landed trace, write direct-land ledger clearing facts, or credit this candidate on that branch. Pre-write audit comments and stacked-PR retargeting remain pre-write actions; the regression must distinguish those from claims of successful land (asserted by A1: those pre-write actions still occur for the OPEN candidate while no landed effect does). Existing independent candidates may continue.
4. Reuse `collectQueueMerged` and `confirmQueueFollowUps` for durable recovery. The collector already runs before post-land work at `we:scripts/merge-ai-prs.mjs:6993`. Pass a repository-keyed map of direct confirmation observations into collection: reuse a confirmed observation for completion tracking and skip this pass's unconfirmed candidates until the next pass (including CLOSED, which retires on a later observation). Do not issue a second immediate read for those candidates. Only legacy/queue-origin entries may run queue-specific dequeue handling; direct OPEN intents remain pending regardless of send-back labels. Split pending diagnostics by origin. For a pending candidate already in this pass's merged list, return it for completion tracking without appending/crediting it again. Carry repository identity through planning (or plan each repository separately), and join facts by repo plus number, not number alone; preserve the existing queue path's behavior. Report recovered direct intents as direct-write recovery rather than asserting GitHub queue provenance (asserted by A4: `mergedBy` equals `direct-write-recovery`). Keep pending entries until inline post-land completion succeeds or the existing durable job handoff accepts responsibility; a handoff is not proof of completed execution. Failed inline work remains subject to the existing retry cap, and detached work retains its existing job-owned recovery. Confirmed delayed land may run follow-up in the same pass or a later one. Do not promise globally exactly-once execution: post-land work is idempotent and can retry.
5. Add an opt-in per-repository fake merge-queue flag in `we:scripts/conveyor/__tests__/helpers/fake-gh-shim.mjs:349`: successful command, observable enqueue event, OPEN PR, unchanged base ref. Thread the opt-in flag through repository construction in `we:scripts/conveyor/__tests__/helpers/fake-gh.mjs:879`; expose fixture configuration for the soak setup. Normal fake merges remain unchanged. The soak judge must prove the command was attempted so a pass that never reaches the write cannot pass vacuously.

## MVP

Deliver as one implementation change with its executable regression and soak fixture; keep the confirmation and durable recovery together so refusing early credit cannot strand a later merge.

- Must: strictly confirm direct writes before landing credit, trace, dependency release or candidate-specific post-land effects, for every PR content kind.
- Must: persist the explicit repository and revalidated head in recovery intent before writing; errors refuse that write and preserve existing state (A3: no merge command, state file byte-identical). Never turn unknown state into landed or positively queued output.
- Must: recover delayed merges even after they vanish from open listings; prevent duplicate same-pass credit and cross-repository number collisions. Retire after successful inline follow-up or accepted durable handoff, retaining existing retry behavior and job-owned recovery.
- Must: distinguish direct intents from legacy queue intents in recovery and diagnostics; reuse same-pass observations without a second confirmation read (A7).
- Must: executable CLI regression, fake-gh regression and daemon soak break with normal-merge control.
- Could, deferred: bounded fast retries and watcher-triggered follow-up. No queue-policy, ruleset or runbook change; no change to the explicit queue strategy's enqueue decision or clearance behavior.
