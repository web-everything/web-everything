# Lazy restacking for stacked PRs (stack.restack: eager | lazy)

Held finding 228 (2026-10-10, operator OK) reports that three of four commits on #4814 were base updates as #4799 changed, each restarting roughly twenty minutes of CI. Preserve the goal: a cascaded `stack.restack` setting, default `lazy`, avoids updating children on every parent-head change while review-on-stack-base continues. `eager` retains existing behavior. The drain's pre-land retarget remains the existing “next in line” boundary; it changes PR metadata, not the child's commit history. That boundary precedes either a direct merge attempt or enqueueing, depending on the active merge strategy; it is not proof the parent has landed.

## Design

1. Add we:scripts/lib/stack-restack-policy.mjs with an injectable resolver using `cascadePolicy('stack', …)` from we:scripts/lib/policy-cascade.mjs. Resolve the `restack` leaf through standard `lazy`, platform preference, tool override read by `readSettings` from we:scripts/settings/stack.json, then proposed env `WE_STACK_RESTACK`. Accept only the exact strings `eager` and `lazy`; invalid values fall through to the next valid layer, with cascade diagnostics. Expose the effective mode and source for tests/logging, and allow injected settings, platform and env inputs. Catch settings-read failures and retain the cascade's valid lower layer/default. Read only the resolved restack result; do not change `reviewWhileBaseOpen` or migrate its separate resolver in we:scripts/lib/stack-review-while-open.mjs. Document the contract in the new module and a top-level `$comment` in we:scripts/settings/stack.json; leave the committed tool block without a redundant `restack` override so platform preferences remain effective.
2. In we:scripts/conveyor/pr-stack.mjs, add proposed `restackMode` to the object returned by `resolvePrStackSettings`; its default is lazy even when callers supply an older settings object without this field. Resolve it once per pass through the shared resolver. Both `applyStackOrder` and `planIdleRestacks` already receive that object. Keep `prStack.restack=false` and `WE_PR_STACK_RESTACK` as the existing enable switch, distinct from timing. With timing `lazy`, an open bottom does not authorize a restack merely because its head moved. Apply the timing predicate to both the restack branch and the cap-exhausted release at we:scripts/conveyor/pr-stack.mjs:293: old eager attempt counts must not release an overlapping child past bottom-first rules in lazy mode. Continue existing bottom-first/parallel-fix/hold-age logic without discarding an owed fix or takeover. Update the hold explanation at we:scripts/conveyor/pr-stack.mjs:343 so lazy mode does not promise restacks on parent movement. A positively detected landed bottom remains eligible for the ordinary bounded restack onto main. With `eager`, retain current scheduling. Do not infer landing from disappearance alone: retain the ancestry proof at we:scripts/conveyor/pr-stack.mjs:143.
3. In we:scripts/conveyor/ci-red-recovery-watch.mjs, resolve the same policy once per sweep and inject/pass it to `restackStackedPr`, which must also enforce it for direct callers. Under `lazy`, a candidate still targeting a non-default base is deferred without fetch, refresh, push, retry comment, or label clearing. After the existing missing-run plan is built, partition its dispatch: retain eligible candidates in `dispatch` and put lazy deferrals in `refusals` with proposed kind `stack-restack-lazy` and a reason naming the base and effective mode. This makes the existing report renderer truthful in dry-run. On apply, surface those same skipped candidates as structured `deferred: true` outcomes without invoking either writer. The direct helper returns the same deferral before chain IO; existing apply accounting already skips deferred outcomes at we:scripts/conveyor/ci-red-recovery-watch.mjs:1062. Do not classify a missing/empty base as default: defer it with an explicit unknown-base reason. Under `eager`, retain current chain identity/claim checks and recovery behavior; unknown evidence must never authorize a write. A candidate positively targeting the default branch continues through ordinary guarded recovery after retargeting, without a new requirement to prove its former parent landed.
4. “Next in line” uses the existing drain pre-land point after candidate revalidation at we:scripts/merge-ai-prs.mjs:6488. It precedes merge-strategy enqueueing as well as direct merge attempts; it does not prove queue position or completed landing. Do not add a guessed queue rank, elapsed-time threshold, green-CI shortcut, or persisted scheduling signal. Retargeting must still be attempted before deletion in both modes, preserving its current best-effort behavior. If the parent merge/enqueue fails after retargeting, existing merge/review/CI guards remain authoritative; neither the timing result nor retargeting grants merge permission.
5. Keep mode selection separate from review acceptance and merge safety. All existing claims, identity checks, retry caps, required checks, and current-head review validation still apply when an action becomes eligible. No new persistent state, endpoint, timer, or daemon is required.

## Done when

- Default lazy mode schedules no child restack on an open parent's head changes through either planner path or stacked missing-run recovery. Eager mode retains those actions.
- A deferred recovery does not push, clear labels, post an attempt marker, increment retry rounds, or spend a dedupe key. Changing to eager or observing a landed parent can make it eligible on a later pass.
- Parent landing enables ordinary bounded recovery; pre-delete retargeting still runs. Review and legitimate fix work continue under the existing stack policy.
- Must refuse writes on unknown identity, ambiguous ancestry, unreadable required state, or a live claim whenever the existing action guards require refusal; lazy mode is not an authorization bypass.
- Must apply identical timing and safety rules to source, documentation, configuration, and data changes. No extension-based exemption.
- Executable acceptance: through we:scripts/readiness/heavy-admission.mjs, run the focused Vitest files listed in Test plan. New default-lazy sequence assertions must fail against pre-change consumer behavior and pass after implementation; existing eager and safety assertions must remain green.

## Non-goals

- No review-acceptance relaxation, CI bypass, new queue ranking, stack detector redesign, history rewriting, or changes to branch-deletion policy.
- No guarantee that all CI reruns disappear: explicit fixes, real conflicts, eventual restacks, and GitHub base-retarget events may legitimately trigger checks.

## Edge cases this change must handle

1. **Untrusted text** — retain validated refs, repository checks, and argument-array command execution; setting text is an enum, never shell input.
2. **Truncated reads** — unknown ancestry/identity remains unknown; no incomplete read authorizes restacking or claims parent landing.
3. **Shared state files** — no new state; deferred actions leave attempt counters and dedupe state untouched. Preserve existing atomic stack-memory writes.
4. **Fail closed** — malformed mode layers fall back through the validated cascade to lazy; existing mutation guards still refuse when evidence is missing.
5. **Identity scoping** — preserve same-repository, verified branch-tip and actor checks. A branch-name collision cannot authorize a push.
6. **State over time** — repeated open-parent moves defer without spending retries; mode changes and observed landing are reevaluated, not latched. Retarget-before-merge failure grants no merge permission.
7. **Who wrote it** — preserve writer claims and ownership checks; this setting changes timing, not the authorized actor.
8. **Receive/write endpoints** — no new endpoint, request body, or externally callable reset surface; body-size caps, rate limits, and CSRF/origin handling are not introduced by this change.
