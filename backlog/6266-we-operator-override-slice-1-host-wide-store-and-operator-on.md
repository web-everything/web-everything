# we: operator override slice 1 - host-wide store and operator-only write CLI with audit log and expiry

Build the store of decision 6268 (we:docs/agent/platform-decisions.md#operator-override-settings-layer): a host-wide path outside any lane clone, one readOperatorOverrides read interface, and an operator-only write that appends a change log and supports expiry. Operator authority comes only from a channel an agent on this host cannot forge (below).

The store module, the attestation module, the operation module, the approval workflow and both tests are new files. The two operations, `operator-override-request` and `operator-override-apply`, are registered in `OPERATIONS` in we:scripts/operations/run.mjs, the way existing operations are, and get their module-map entries in we:scripts/operations/__tests__/http-adapter.test.mjs. Every input is a `--flag` (the CLI adapter rejects positional arguments): `node we:scripts/operations/run.mjs operator-override-request --key=<key> --value=<value> --instruction=… --reason=… [--expires=…] [--confirm-loosen]`, then `node we:scripts/operations/run.mjs operator-override-apply --pr=<n>`.

**Authority: a non-forgeable channel, never a local check.** No local signal is evidence of the operator: not an interactive terminal (`operatorTerminalPresent`), not the local `gh` login (`resolveOperatorCredential`), not `attemptedBy`, an environment variable, a flag, the request body or a commit author. An agent on this host can open a pseudo-terminal, clear agent environment markers and run `gh` with the credentials the host already holds, so every one of those checks can be passed by an agent. The authority instead reuses the protected-CI trust root of slice 2 A10, now carried by `#6246` (`forged-settings-operator`, with its A15 gate self-protection): the identity is the authenticated GitHub review actor, fetched by protected CI with credentials unavailable to PR jobs and agent sessions, checked against the protected operator allowlist.

1. **Request (anyone may run it; writes nothing to the store).** `operator-override-request` opens a request PR against the default branch whose only change is one request file, `operator-overrides/requests/<requestId>.json`, holding exactly `key`, `value`, `expiresAt`, `confirmLoosen`, `instruction`, `reason`, a fresh `requestId` nonce, the target host id and the repository. The file must be byte-exact canonical JSON (UTF-8, NFC, sorted keys, no insignificant whitespace, at most 16 KiB, instruction at most 4 KiB). The verifier parses it strictly: a duplicate or unknown field, a non-canonical byte or an oversize file is refused, so the bytes the operator reviews are the bytes applied. `requestHash` is the SHA-256 of those exact bytes. A loosening request (slice 3's `isLooseningOverride`) must carry `expiresAt` at most 24 hours after approval. The key is checked against `SETTABLE_OVERRIDE_KEYS` and classified by slice 3 at request and again at apply.
2. **Approval (only the operator).** The operator approves the request PR with a GitHub review. The protected workflow we:.github/workflows/operator-override-approve.yml is triggered only by `schedule` and `workflow_dispatch` on the default branch, never by `pull_request`, `pull_request_review`, `pull_request_target` or `issue_comment`, so it always runs the default branch's definition and code. It never checks out the PR ref; it reads the request file and reviews through the API as data, and no PR-controlled text (title, branch, file field) is expanded with `${{ }}` inside a `run:` step. Its signing key is a secret of a GitHub environment limited to the default branch. For each open request PR it accepts the review only when: the PR base is the default branch; the review state is `APPROVED`, it is the author's latest review on the PR, and it is not dismissed; the author's numeric user id is on the operator allowlist we:.github/operator-allowlist.json (read from the default branch; App and bot accounts never count); the review's `commit_id` equals the PR head; and the PR diff against its base is exactly that one request file. It then signs an attestation `{ repository, pr, head, requestHash, requestId, actorId, actor, reviewId, reviewState, approvedAt }`. PR jobs and agent sessions never receive that key or any privileged token.
3. **Apply.** `operator-override-apply` fetches the attestation and verifies it with the public key pinned at host setup. It checks the signature, request hash, repository, host id, PR head, freshness (`approvedAt` at most 15 minutes old and before `expiresAt`) and that the `requestId` never appears in the log. Only then does it append the log record, which carries the attestation and the exact request bytes. Any caller may run apply, over the CLI or a `POST …/runs` HTTP route alike, because it can only apply exactly what the operator approved, once. Missing, unsigned, wrongly-signed, stale, replayed, wrong-repository, wrong-host, wrong-head, non-`APPROVED`, dismissed, superseded-review or non-allowlisted approvals refuse the write, and nothing is written. The HTTP adapter itself is not changed.
4. **Read.** Readers re-verify every log record's attestation and request bytes against the pinned key. A record without a valid one (for example an agent that wrote the log file directly) is never applied. A `requestId` counts only at its first appearance in the log, and a record whose `approvedAt` is older than the previous valid record for the same key is ignored, so a copied, validly signed record appended later cannot win again. A log truncated to before a safe re-set can revive only an approved loosening that is still inside its own 24-hour expiry. The actor is the review author from the attestation, and the channel is `github-review`.

**What protects the trust root.** The approval only proves the operator if no agent can produce an approving review as the operator or swap the key that checks it:

- **No operator credential on an agent host.** Today the host holds the operator's personal `gh` token (`personalGhToken` in we:scripts/lib/gh-throttle.mjs), and any agent process can read it and submit an `APPROVED` review as the operator's own account. So the layer is inert on a host where any credential authenticates as an allowlisted account: `operator-override-apply` refuses and `readOperatorOverrides` returns `readable: false` while `gh auth token` (with `GH_TOKEN` cleared) or the host's `gh` config holds a token whose user id is on the allowlist. The operator approves from a device or browser session that agents on this host cannot reach. Moving that token off the host is an operator setup step, not part of this build. Binding agent credentials to the role-App identity is tracked by we:backlog/6161-operator-controls-tie-actor-to-the-authenticated-identity.md.
- **The pinned key is not agent-writable.** The public key is installed at host setup in a root-owned file and directory that the agents' OS user cannot write. The reader and apply refuse (layer unreadable) when the key file or any parent directory is writable by the current user, or the key is missing.
- **The trust root lands only through a human.** The allowlist, the approval workflow, the verifier module (we:scripts/lib/operator-override-attestation.mjs) and their CODEOWNERS entries (we:.github/CODEOWNERS) are added to `GATE_PATH_PREFIXES` in we:scripts/lib/merge-queue-enqueue.mjs, the path predicate behind `workflowEditHold` that the drain's human-only workflow boundary (we:scripts/lib/drain-workflow-edit-hold.mjs) shares, so a separate agent PR that edits them is held for the operator, not landed by the drain.
- **The code that enforces the authority lands only through a human too.** Protecting the verifier is not enough: a caller that skips it bypasses it. So these files are also added to `GATE_PATH_PREFIXES`: the store module (we:scripts/lib/operator-override-store.mjs, which runs the read-time re-verification), the floor module (we:scripts/lib/operator-override-floor.mjs, built by slice 3), the operation module (we:scripts/operations/operator-override.mjs, which runs apply), and their tests (we:scripts/lib/__tests__/operator-override-store.test.mjs, we:scripts/lib/__tests__/operator-override-floor.test.mjs and we:scripts/lib/__tests__/operator-override-attestation.test.mjs). A separate agent PR that makes `readOperatorOverrides` return unsigned entries, drops a floor check or skips verification in apply, and edits the tests to match, is held for the operator. The predicate matches by prefix, so each entry names the full file path: it holds that path and any path that begins with it (such as a `.orig` copy), never its directory siblings. The floor entry already holds before slice 3 creates the file. The list and its predicate do not yet protect their own files, so an agent PR could remove these entries; that gap is tracked by we:backlog/6309-human-only-gate-predicate-own-code-is-agent-landable.md. Backdating a signed approval by writing it straight into the log is tracked by we:backlog/6310-operator-override-signed-approval-backdating-by-direct-log-ins.md (expedite, due before public preview).
- **Operator setup.** The build names, in its PR, the one-time operator steps it cannot do itself: create the default-branch-limited environment and its signing secret, install the root-owned public key, add the operator's numeric user id to the allowlist, and move the operator token off agent hosts. `#6246` is deferred until public preview, so this slice builds this one writer's copy of the A10/A15 pattern instead of waiting for it.

**Read interface.** `readOperatorOverrides()` returns `{ readable, entries }`. `readable` is false when the store or snapshot cannot be read or parsed, so a caller can tell "unreadable" from "no overrides". Each entry carries `key`, `value`, `entryId` (the log line it came from), `actor`, `channel`, `at`, `instruction`, `reason`, `expiresAt`, the verified attestation and the recorded confirmation, if any. Slices 2, 3 and 4 build on exactly this shape.

**History read.** `readOperatorOverrideLog({ after, now, limit })` reads the log once and returns `{ readable, entries, records, cursor, rewritten }`. `entries` is the same current view as `readOperatorOverrides()` evaluated at `now`, and `records` holds the committed, attestation-verified log records after cursor `after`, in append order (at most `limit`, default 1000; the rest come on the next call; an absent `after` reads from the start of the log), each with the entry fields above plus `endedAt` and `endedBy` (`expired`, `superseded` or `null` while still effective at `now`). Both come from the same read at the same `now`, so a record cannot fall between them. A cursor is `{ position, entryId, hash }` of the last record read. When `after` is past the end of the log, or the record at `after.position` no longer has that `entryId` and hash (the log was truncated or rewritten), the call returns `rewritten: true` with every record from the start of the log, so the caller can rescan. Slice 4 uses it to show overrides that started and ended between two feed polls.

**Current view and identity.** `entries` contains at most one effective entry per key. Append order, not a caller-supplied timestamp, decides the latest write. Select the latest write before checking expiry or the slice 3 floor: an expired, invalid or unconfirmed latest write never revives an older entry. Re-setting to a safe value supersedes a loosening value; expiry removes the override from the current view and lower code/env layers resume. The historical log keeps every write. Generate a fresh, unique `entryId` matching `^[A-Za-z0-9-]{1,128}$` for every write, including a re-set with the same value; the snapshot cannot rebind an id to a different key, value or expiry.

**Write consistency.** Hold one lock across re-reading current state, appending the complete JSON log record and atomically replacing the snapshot. Readers verify the snapshot against the authoritative log; a crash between append and rename must recover the newest committed log view or return `{ readable: false, entries: [] }`, never a stale snapshot. An unreadable or partial log/snapshot invalidates the whole read, with no partial entries applied.

## Non-goals

- [N1] Does not wire the layer into the cascade (slice 2), the guard floor (slice 3), the needs-you flag (slice 4) or any plateau DB work.
- [N2] The store module exports `SETTABLE_OVERRIDE_KEYS`: the referral safety keys, the merge-queue switches `refreshOnUnsatisfiedWorkflows` and `refreshOnStaleMergeGate`, and the cascade keys whose reader uses `cascadePolicy(...).value` (never a `.layered` reader that applies env itself). Any other key is refused by the write (named test: `a key outside SETTABLE_OVERRIDE_KEYS is refused and nothing is written`), so an override that no resolver reads is never stored. Slice 2 proves every listed key is read.

## Edge cases this change must handle

One line per class: either the handling, or `n/a: <why>`.

1. **Untrusted text** — the verbatim instruction is stored as a quoted JSON string, never executed or interpolated.
2. **Truncated reads** — a snapshot or log line that fails to parse invalidates the whole layer and is logged, never half-applied, and the read reports `{ readable: false, entries: [] }`.
3. **Shared state files** — the log is append-only under a lock; the snapshot is replaced atomically.
4. **Fail closed** — an unreadable store, a missing or unverifiable attestation, a missing or user-writable pinned key, or an allowlisted operator credential on the host means no write and no applied override.
5. **Identity scoping** — actor and channel come only from the protected-CI attestation of an allowlisted human GitHub review; no local signal (terminal, `gh` login, environment, flag, `attemptedBy`) is evidence. Test: `forged-override-operator`.
6. **State over time** — latest write per key wins before filtering; supersession and expiry remove earlier values from the derived view without deleting history or reviving an older override.
7. **Who wrote it** — every entry carries actor, channel, time, instruction and reason.
8. **Trust boundary** — authority is checked by protected CI with a signing key that PR jobs and agent sessions never receive, and verified on the host with a root-owned public key the agents' user cannot write; the layer is inert while an allowlisted operator credential is on the host; the trust root lands only through a human. Tests `forged-override-operator`, `an allowlisted operator credential on the host disables the layer`, `the pinned key is refused when the current user can write it or its directory, or it is missing`, `override-approval-self-protection`, `a separate agent PR that edits the override trust root is held for human landing` and `the human-only predicate holds each authority-enforcing override module and its test` (the store, floor and operation modules and their tests land only through a human, not only the verifier). The store sits outside any lane clone, so a lane's Edit/Write grant does not cover it. we:scripts/guard-bash.mjs denies agent shell writes to the store path, tested in we:scripts/__tests__/guard-bash.test.mjs as `an agent shell write to the operator-override store is denied`. A record that still gets past this has no valid attestation and is never applied (`a log record without a valid attestation is never applied, even when written directly to the store`).
9. **Normalization** — the request is byte-exact canonical JSON hashed over its exact bytes; the allowlist matches numeric user ids, not logins; the key must match a `SETTABLE_OVERRIDE_KEYS` entry exactly (no case folding). Test: `the request file is strict canonical JSON`.
10. **Resource bounds** — request file at most 16 KiB, instruction at most 4 KiB, and `readOperatorOverrideLog` returns at most `limit` records per call. Tests: `the request file is strict canonical JSON` (oversize case) and `readOperatorOverrideLog with no cursor reads from the start, returns at most limit records, and its cursor resumes exactly after the last one`.
