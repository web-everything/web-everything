# we: stacked PR policy slice 4 - closed or rejected base handling

When a stacked child's base PR is closed or rejected, rebase a low-risk child onto main only on a clean rebase with an unchanged delta fingerprint (a setting); every other child goes to the operator as needs-you. Ruled in 6903.

A Git rebase moves only the child's commits. The drain holds a child on its base through two other things, and the recovery must clear both, or the rebased child never lands:
- **The PR's base branch.** The child PR still targets the closed base's `lane/*` branch. `classifyPr` skips any PR whose `baseRefName` is not the repo's default branch (`base is not main (lane/…)`). GitHub retargets a child only when its base merges (through `retargetStackedPrs`, which runs before the base lands); a base closed without merging never reaches that call. So the recovery retargets the child PR to its own repo's resolved default branch, with the existing `buildRetargetArgs` argv. It never uses a literal `main`, and a default branch that cannot be resolved sends the child to the operator (existing callers fall back to `'main'`; this handler does not).
- **The durable stack edge.** The edge is the `stackParents` entry in the child's lane manifest, and the drain (`planLabelDrain`) keeps waiting on a parent that never lands. So the recovery removes the closed base from every manifest source the drain reads. That means the PR-body lane manifest (rewritten with the existing `embedManifestInBody`) and, when the body carries none, the legacy head-ref `we:.lane-manifest.json`. Writing the cleaned manifest into the body is enough for a legacy child too, because the drain reads the body first.

How the child is moved off the closed base:
- **Pass wiring.** Wire the close/reject handler and recovery sweep into the real drain pass in `we:scripts/merge-ai-prs.mjs` (`runCli`), before its verdict building and merge planning. Each pass handles newly observed closed/rejected bases and runs the sweep, including passes with no new close event. Re-read child state after recovery writes before classifying it. Besides the pass orchestration, the only change to `classifyPr` and `planLabelDrain` is the closed-base ancestry hold below; their existing base gate and proof-of-land gate are unchanged.
- **Closed-base ancestry hold (drain side).** The recovery's other holds (the edge, the fix claim, the markers) each depend on a write or a read that can fail or expire. Once the claim has expired and a replacement PR carrying the closed item has landed, the edge is logically satisfied, so a child that still carries the closed base's commits could land if the sweep's marker read failed that pass. So the drain itself refuses that child, using neither the fix claim nor any marker. In the real drain pass (`runCli`, before verdict building), every open PR that targets its repo's default branch gets a `closedBaseCommits` fact, built only from that PR's own GitHub history:
  1. Its earlier bases: every `previousRefName` in the PR's `BaseRefChangedEvent` timeline items (GraphQL), read to the last page. A PR with no such event was never retargeted and is `clear`.
  2. For each earlier base that is a lane branch, the PRs in the child's own repo whose head was that branch (`GET /repos/{owner}/{repo}/pulls?state=closed&head=<owner>:<branch>`, read to the last page). A closed PR with no `merged_at` is a closed (unmerged) base.
  3. For each closed base, its head commit (`headRefOid`, fetched as `refs/pull/<n>/head`) and every commit on its commit list (`GET .../pulls/<n>/commits`; a list at the 250-commit cap counts as truncated). The PR `carries` that base when any of those commits is an ancestor of the child's head (`git merge-base --is-ancestor <commit> <childHead>`) and is not an ancestor of the default branch's head. A commit that already reached the default branch by another route is not a risk, so it never holds a child forever.

  `classifyPr` skips a PR whose fact is `carries` (`head carries commits of closed base #<n>`) or `unknown` (`closed-base ancestry unreadable: <why>`). The arm sits ahead of the required-check arm, so a stale green `test` from the old head never matters. Unlike the existing base arm, which is inert when a value is unknown, this arm fails closed: a missing fact on a default-branch PR in the real drain pass, any failed, partial or truncated read in steps 1 to 3, a fetch of `refs/pull/<n>/head` that fails, or a git ancestry check that errors makes the fact `unknown`, and the PR waits for a pass that can read it. `planLabelDrain` also refuses a `ready` candidate whose fact is `carries` or `unknown`, as a second check that does not depend on the classifier's verdict. A correctly rebased child no longer contains the closed base's commits, so it passes. The hold never removes an edge, never retargets and never writes a label.
- **Which id.** The trigger is a base PR number, but `stackParents` holds item ids. Map the closed base PR to its item id by reading that PR's own manifest (it is closed, so the drain's open-PR read does not have it). If that read fails or gives no item, the child goes to the operator.
- **The recovery hold.** Between the retarget and the edge removal the child targets the default branch while its old head (closed base commits included) still carries a green `test` from the run against the closed base's branch; `classifyPr` cannot tell which base a run was against. Two holds keep it from landing in that window. The first is the edge itself, which step 2 below guarantees lives in the PR body, where no head rewrite can drop it; `planLabelDrain` defers the child on it. The second is the child's existing fix claim (`we:scripts/conveyor/fix-procedure.mjs`), which the handler takes before its first write and holds, with heartbeats, until the edge removal or the operator route is confirmed; the drain's merge-site re-read (`attachLiveFixClaim`) refuses a claimed PR. The drain's main pass does not read the claim, but its closed-base ancestry hold (above) refuses the old head in the window, because that head still carries the closed base's commits. A main pass that ran before that refusal, or with the fact somehow computed `clear`, could still classify the child `merge` in the window, and its manifest strip or rebase-drop can rewrite the head. That is safe but not free: the handler's own push names the head it expects to replace (`--force-with-lease=<ref>:<old head>`), so a head that moved under it is a lost race: nothing is pushed, and the child takes the operator route. A head another writer moved after the push no longer matches the marker, so the sweep sends that child to the operator too. A child whose fix claim is already held by someone else when the handler starts is left alone that pass (it keeps both holds) and retried next pass.
- **Write order.** The full eligibility check runs before any write, and includes a rebased sha different from the current head. Each write is confirmed by a fresh read before the next one starts, and the base state and the setting are re-read before each write; a base that reopened or a setting turned off mid-recovery takes the operator route.
  1. The fix claim (above).
  2. For a legacy child (no manifest block in the body), the head-ref manifest copied into the body, edge intact, so the edge no longer depends on a file a head rewrite can drop.
  3. The auto-rebase marker (below).
  4. The retarget, confirmed by a fresh read of the child's `baseRefName` equal to the default branch.
  5. The push of the rebased head, confirmed by the child's remote head equal to the rebased sha.
  6. The edge removal, then the claim release.

  Claim renewal runs throughout slow reads and writes, including the operator route and every half of a couple; it is not deferred until the next recovery step. Before every write the handler also confirms that it still owns a live claim. Failed renewal stops forward recovery before expiry and takes the operator route under a live claim. If ownership has already expired or been lost, abort pending work and make no further recovery writes or claim release as that holder; re-acquire a valid claim before establishing the operator hold. An expired holder cannot resume writes after another session takes over.

  The retarget comes before the push on purpose: CI runs on `pull_request` opened, synchronize and reopened, not on a base edit. Pushed after the retarget, the new head's synchronize run is against the default branch; pushed before it, the run would be against the closed base's branch, and a later retarget would not re-run it. A rebase that leaves the head sha unchanged triggers no new run, so the old run against the closed base's branch would still count: that child goes to the operator before any write. The edge is always the last write.
- **Failure.** A retarget that errors or whose fresh read does not show the default branch, a push that is not confirmed or loses the lease, or a body manifest write that fails, sends the child to the operator and keeps the edge. A child GitHub already closed because the closed base's branch was deleted goes to the operator: GitHub refuses both a retarget and a reopen of such a PR (#2578). The existing lane prune already withholds deleting a branch that an open PR targets, so this happens only when the branch was deleted some other way.
- **Couples.** An impl PR inherits `stackParents` from its WE carrier's manifest. Each half is claimed and retargeted in its own repo, to that repo's default branch. The edge is removed in the carrier's manifest, and only when every half is auto-rebased and retargeted. If any half goes to the operator, or any half's retarget fails, every half does, and the carrier keeps the edge. A base couple where only one half closed (the other half still open) sends the child to the operator: a half must never be moved off an open base.
- **Re-entrant sweep.** A crash between the marker and the edge removal leaves an open child that still names the closed base, and the close trigger will not fire again (the fix claim then expires on its TTL). So every pass, the slice-4 handler also sweeps. It starts from the open PRs, never from a listing of closed ones (closed PRs pile up forever, so any fixed limit on that read would eventually always be hit and the sweep would stop for good). Its candidates are the open children whose `stackParents` names an item no open PR carries, whose `baseRefName` is a lane branch no open PR in the same repo heads, **or whose trusted auto-rebase marker names a closed base whose edge is still physically present in the authoritative body/carrier manifest**. Discover those unfinished markers on every open child independently of parent visibility and current base branch: a replacement PR carrying the closed base's item must not hide a retargeted child. Replacement landing satisfies the edge logically but does not remove its manifest entry. A historical marker whose recorded edge has been removed does not by itself select the child again, even after a later author push changes its head. An operator-route marker keeps the existing operator hold. For each candidate it reads the base by that child's own data: the marker's recorded base PR number, or the PR whose head is that lane branch in the child's repo. Never substitute the replacement PR for the closed PR recorded in the marker. An open-PR listing that is truncated or fails names no child, so the sweep writes nothing that pass and retries next pass; the drain-side closed-base ancestry hold still refuses every child whose head carries a closed base's commits. A per-child manifest, marker or base read that fails or is truncated, for a child already selected as a candidate (by its lane-branch `baseRefName`, by a `stackParents` item no open PR carries, or by a trusted marker), parks that child `review:human` (the existing hold only a person clears), keeps its edge, and posts it on the needs-you channel. A failed read never leaves the child with only holds that can expire. Adding that `review:human` hold is the one write the sweep makes without first holding the fix claim, because it only adds a hold: it never removes an edge, retargets or pushes. A label write that itself fails is retried next pass, and the ancestry hold keeps the child from landing meanwhile. An open PR that is not a candidate, including one whose manifest read failed so its `stackParents` could not be checked, is not parked; if it carries a closed base's commits, the ancestry hold refuses it. The sweep re-takes and heartbeats the fix claim before any write and finishes only a recovery the handler itself started. Before the retarget, the handler records an auto-rebase marker naming the rebased sha and the closed base PR, as a PR comment (no new shared file). Only a marker in the exact shape the handler writes, authored by the trusted conveyor identity, counts; any other comment is ignored. The sweep finishes only when that marker names the child's current remote head, the child's `baseRefName` is already the default branch, the child carries no operator-route marker (below), and the full eligibility check passes again: low-risk class, setting on, fingerprint unchanged against the pre-close delta, rebased sha different from the pre-recovery head, trusted same actor, and no `blockedBy` on the base. Then it removes the edge. The sweep never retargets. A child whose marker names its head but whose base is not the default branch was moved back by the operator route, so it goes to the operator. A crash after the marker or after the retarget, but before the push, leaves a marker naming a sha other than the current head, so that child takes the operator route. Every other child selected for recovery, including one the handler sent to the operator whose head later moved onto main, goes to the operator and keeps its edge. The pass wiring lives in `we:scripts/merge-ai-prs.mjs`; `planLabelDrain` and `classifyPr` retain their proof-of-land and base gates.
- **Operator route.** A child sent to the operator keeps its edge and is never left targeting the default branch on the edge alone: the edge clears as soon as the closed item lands through any new PR, which would land the old head with the closed base's commits. A child the handler never retargeted stays on the closed base's branch. A child the handler (or a crash) already retargeted is retargeted back to the closed base's branch when that branch still exists (once no open PR targets it, nothing guarantees it survives the prune); if the branch is gone, or the retarget-back fails or its fresh read does not confirm it, the handler parks the child `review:human`, the existing hold only a person clears. The operator route also records an operator-route marker (a PR comment in the handler's exact shape, naming the head), so the sweep never finishes a recovery the handler handed to a person. The handler releases its fix claim only after one of those holds and the marker are confirmed, then posts the child on the needs-you channel.

## Edge cases this change must handle

One line per class: either the handling, or `n/a: <why>`.

1. **Untrusted text** — class and fingerprint come from the diff and paths, not PR text.
2. **Truncated reads** — an incomplete diff or state read, or a default branch that cannot be resolved, goes to the operator. The sweep starts from the open-PR listing (never an ever-growing closed listing). A truncated or failed open listing writes nothing that pass; a truncated or failed per-child read on a selected candidate parks it `review:human`. Either way the drain's closed-base ancestry hold, which reads only the child's own base history and fails closed on any truncated read, refuses a child whose head carries a closed base's commits.
3. **Shared state files** — adds no new shared file; the operator route uses the existing needs-you channel. The handler holds the child's existing fix claim for the whole recovery; with the edge kept in the body, the drain never lands the child mid-recovery. The durable writes, in order, are the legacy manifest copied into the body (edge intact), the auto-rebase marker (a PR comment), the child PR's base retarget to its repo's default branch, the rebased head push (leased on the old head, so another writer's push is a lost race that goes to the operator), and removing the closed base from the child's lane manifest (the PR body, or the carrier's body for a couple). The edge removal comes last, only after a fresh read confirms both the new base and the rebased head on the remote. A crash anywhere between the marker and the edge removal is caught by the per-pass sweep, which re-takes the claim. None of those holds is the last line: the drain refuses any default-branch child whose head still carries a closed (unmerged) base's commits, with no claim or marker read involved.
4. **Fail closed** — any unknown goes to the operator, never to an automatic rebase. A failed or unconfirmed retarget, a lost push lease, a sha the rebase left unchanged, or a failed or partial stack-edge removal, also goes to the operator. A child routed there keeps its edge and is never left targeting the default branch on the edge alone: it is retargeted back to the closed base's branch, or parked `review:human` when that fails. A recovery read the sweep cannot complete parks the candidate `review:human`, and an ancestry read the drain cannot complete refuses to land.
5. **Identity scoping** — only trusted same-actor lane PRs are handled automatically; the sweep matches a base branch only within the child's own repo.
6. **State over time** — evaluated when the base closes; a later reopen re-evaluates. The base state and the setting are re-read before each recovery write, so a reopen or a setting change mid-recovery takes the operator route, which undoes the retarget.
7. **Who wrote it** — an automation's comment never marks a child low-risk.
