# Owner-review triage screen for feedback suggestions

The owner reviews opt-in, generalized feedback in a tenant-scoped queue with a persistent peek and a one-at-a-time triage stepper. Acceptance records an owner disposition; downstream intake remains #2777. Preserve the parent’s privacy requirements and the ratified Accept / Duplicate / Decline / Snooze grammar.

## Design

All new filenames and endpoints below are proposed, not claims of existing code.

1. **Contract seam.** Specify a versioned review envelope and request/response examples in we:contracts/feedback-review.schema.json and we:contracts/feedback-review.examples.json. Keep the original capture record unchanged. The service envelope carries opaque suggestion ID, revision, receive/activity timestamps, authenticated tenant association and review state. Payload validation and receive-time scrubbing must honor we:scripts/lib/feedback-schema.mjs:40–92; do not add tenant/user identity, source paths, logs or evidence to the user-authored payload. Render payload and notes as text. Errors report field/reason without echoing rejected values.
2. **Owner port.** Proposed Plateau receiver/read/write port at plateau:src/backlog-view/feedback-review-port.ts: explicit capture ingestion, owner-scoped list/detail, and a version-checked disposition write. Identity and owner authorization are injected transport context, never trusted query/body fields. Every read, write, cluster lookup and duplicate target checks that context. Unknown schema versions, unauthenticated/unauthorized callers, unknown IDs, foreign-tenant targets and stale revisions fail closed. Successful writes return canonical state; UI advances only after acknowledgement. No production identity system is invented by this screen.
3. **Closed state machine.** Pending items accept exactly Accept, Duplicate, Decline or Snooze; label Decline as rejection in explanatory copy. Duplicate names a visible same-tenant target and never discards the member’s text. Snooze records an explicit wake time and the activity revision; either elapsed time or newer activity returns it to the queue. Retrying the same request cannot create a second disposition. Keep prior dispositions available for inspection. Acceptance emits a stable accepted envelope for #2777; it neither executes a suggestion nor launches a lane/PR.
4. **Dedup before review.** Cluster only authorized, validated records, by tenant and category, before expensive review. Adapt the complete-link algorithm cited in Progress into Plateau’s pure review core, retaining member IDs, distinct suggestions and provenance as service metadata. Similarity is a cue, never an automatic rejection/acceptance. Inspect all members before an explicit Duplicate verdict; a distinct recommendation must remain reviewable. No browser import of WE operational Node scripts. Show impact ordering only where the service supplies grounded impact; when absent, show “impact unavailable” and a stable ID tie-break, not fabricated scores or age-as-impact.
5. **Surface.** Proposed `/console-feedback` uses a list/detail split with stable selection and next/previous controls, plus buttons and single-key shortcuts for the closed verdicts. Shortcuts do not fire in editable controls. Keep the selected suggestion addressable through refresh, preserve queue position during peek, and retain selection on write failure. Show loading, empty, denied, malformed, conflict and unavailable states distinctly. Compose existing platform navigation/disclosure behavior after checking the trait registry; do not copy imperative wiring merely because an older surface uses it. Provide labelled controls, one main heading, visible focus, status announcements and text alongside colour.
6. **Honest MVP boundary.** Exercise the real port and state machine through a local Vite adapter with an injected owner/tenant principal and two-tenant fixtures. Clearly label this mock transport and its restart persistence limits. Do not expose an unauthenticated arbitrary-tenant selector as production authorization. Production authentication, storage and deployment are explicit follow-ups; the fixture-backed screen is not evidence that those services exist.
