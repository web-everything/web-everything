# Collector seal numbers every member before the PR is marked ready

Per decision 6940 fork 5 (statute backlog-ids-numbered-before-publish): add a number-members seal step after record-sealed and before verify, calling the declared numbering operation once over the whole branch so sibling references resolve together. It fails closed: if numbering fails the batch stays held and never reaches ready.

The `number-members` step must record each member's old->new path map in the batch journal. After numbering, each member carries BOTH `admissionPath` (for the original blob read from `${member.commitSha}:${member.admissionPath}` in `we:scripts/operations/card-batch-extract.mjs:214-218`) and `numberedPath` (for attribution of findings on the renamed card). Member attribution in `we:scripts/operations/card-batch-extract.mjs` (the `cardPath` derivation at lines 199-207) must resolve a member by either path, applying the journal map or following the rename with `git diff-tree -M`. Findings citing the numbered path must still be attributed to the original member. Extraction rebuilds BOTH the standalone card and every surviving batch member at their `numberedPath`, with the numbering operation’s rewritten text taken from the recorded numbering commit, preserving rewritten sibling cross-references. Persist that commit with the path map so extraction can reconstruct the numbered content after restart; never read a numbered path from an original admission commit or emit an admission-path card with stale text.

Extraction takes the closure of references. Its reference edges are the id-references verify refuses when they do not resolve: frontmatter `parent`, every `blockedBy` entry, `closedInto` and every `deferredBlockedBy` array entry. This edge list is exactly the set whose unresolved targets `validateBacklogItem` / `deferredBlockedByFindings` refuse in production verify. Derive the closure from one shared edge-list definition: a single constant imported by the extraction code and its test, with a parity test against the fields checked by production verify so a newly validated edge field cannot be missed. Edge ids are compared the way verify compares them: the parsed frontmatter value as a string, so bare `6500` and quoted `"6500"` are one id. A form verify does not resolve in `parent`, `blockedBy`, `closedInto` or `deferredBlockedBy`, such as `#6500` or a provisional `x…` id left in an edge after numbering, is unresolvable and refuses the extraction. A `deferredBlockedBy` self-edge or an entry also in `blockedBy` remains verify's own error and is left as is; extraction does not rewrite or discard it. Body cross-references are warnings only, so they do not move a member. When a finding cites a member, every surviving member with such an edge that resolves ONLY to a member moving to the standalone PR moves to the standalone PR too. An edge that also resolves on the PR's base branch, read at extraction time, does not move anything. The rule runs in both directions and repeats until nothing changes: a moving member whose edge resolves only to a surviving member takes that survivor along. So extracting epic 6500 takes its child 6501 (`parent: "6500"`), and extracting 6501 takes 6500 and 6500's other children. The same closure applies when 6501 has only `deferredBlockedBy: ["6500"]`, with no `parent` or `blockedBy`. Compute the closure from the numbered content in the recorded numbering commit, never from admission paths or provisional ids. Write it to the extract journal (the standalone set, the remainder set and the base-branch sha it was read against) before either commit is built, then rebuild both commits from it. A resumed extraction reuses the journaled closure and never recomputes it, even if the base branch has moved. Before building, it re-checks every journaled edge against the current base branch; if an edge the journaled sets relied on no longer resolves, the extraction refuses and the batch stays held. If an edge cannot be kept resolvable in either PR, the extraction refuses and the batch stays held for a person. The refusal is posted once on the batch PR and names each unresolvable edge. This covers an edge whose target is on neither the base branch nor in the batch, and numbered content that cannot be read. It never produces a remainder or standalone commit that fails verify. A closure that takes every member leaves no remainder, the journal-only split in 6941.

Seal resume is decided from the journal, not only from the persisted step. `planSeal` in `we:scripts/operations/card-batch-seal.mjs` today slices the step list after the persisted `seal.step`, so inserting `number-members` would let a batch already mid-seal skip it. If any member lacks a recorded `numberedPath` (a batch sealed before this change, at persisted step `verify`, `remove-hold` or `ready`, or any other step after `number-members`), `planSeal` restarts at `number-members`, then continues `verify`, `remove-hold`, `ready`, `label-on-green`. A batch whose members all carry `numberedPath` resumes at the persisted step as today. A member that already carries `numberedPath` is never numbered again on that restart (6943's exactly-once rule). A legacy batch persisted at `remove-hold` or `ready` has already lost its hold, so before `number-members` runs the seal job returns its PR to draft and puts the hold label back; `remove-hold` and `ready` then run again only after numbering and verify succeed, and a numbering failure leaves it draft and held. `sealFailure` still plans `held`, and a `label-on-green` archive is not relaunched (6941), so neither goes through this check.

## Non-goals

## Edge cases this change must handle

One line per class: either the handling, or `n/a: <why>`.

1. **Untrusted text** — card bodies are rewritten only by the declared numbering operation; the seal step does no text substitution of its own (case `seal step changes card text only through the numbering operation`).
2. **Truncated reads** — numbering output that does not cover every member counts as a failure; the batch stays held (case `partial numbering output retains the hold`).
3. **Shared state files** — the step runs under the seal lease on the collector branch; the rewritten head is recorded before verify runs on it (case `crash after the numbering push and before the head is recorded resumes without head-mismatch`).
4. **Fail closed** — any numbering failure keeps the batch held and never reaches ready (case `numbering failure retains the hold and never reaches ready`). Extraction moves the reference closure together, so neither rebuilt commit has a dangling `parent`, `blockedBy`, `closedInto` or `deferredBlockedBy` (case `extracting a parent keeps its child with it so the remainder verifies`). An edge it cannot keep resolvable refuses the extraction and keeps the hold (case `extraction refuses when a reference resolves in neither PR`). The shared extraction edge list stays aligned with production verify (case `closure edge list matches verify`).
5. **Identity scoping** — numbers are allocated per repo through the declared operation (case `members are numbered through the batch repo's own operation`).
6. **State over time** — the resume point comes from the journal, not only the persisted step: a batch persisted mid-seal before this change (at `verify`, `remove-hold` or `ready`, members without `numberedPath`) restarts at `number-members` instead of skipping it (case `legacy mid-seal batch at verify, remove-hold or ready is renumbered before it proceeds`), and a re-run after a timeout must not renumber (6943's case `timeout during number-members then resume leaves each member numbered exactly once`). 6941's resume of an open `sealed/` archive at step `ready` goes through the same journal check. A resumed extraction builds from the journaled closure, not one recomputed against a moved base (case `extraction resume reuses the journaled closure after the base moves`).
7. **Who wrote it** — the numbering commit is not an admit commit; if the batch is later closed, 6941 surfaces it through the PR link.
