# Consume the real dispatch CLI outcome without releasing successful build claims

Resolve the real CLI summary's run ID through the launch's captured run store and validate its persisted dispatch effect before changing ownership. The summary contains effect keys, while the consumer still expects inline records. Production uses detached settlement, so this repair must cover retained evidence and claim handoff as well as stdout parsing (we:scripts/operations/cli-adapter.mjs:1375-1393; we:skills-src/conveyor/build-dispatch-daemon.mjs:195-220; we:skills-src/conveyor/build-dispatch-daemon.mjs:2562-2563).

## Evidence

- The serializer emits `runId`, `op`, `verdict` and `inFlight` keys, with no `effects`; the reader selects `parsed.run ?? parsed` and searches `run.effects` (we:scripts/operations/cli-adapter.mjs:1375-1393; we:skills-src/conveyor/build-dispatch-daemon.mjs:195-220).
- Detached settlement uses that reader and an optional item/kind live-row fallback. That fallback does not correlate the acknowledged run and can mask the mismatch; the mismatch alone does not prove every successful launch loses its claim (we:skills-src/conveyor/build-dispatch-daemon.mjs:1814-1831).
- The helper passes only stdout to resolution and removes the pending record, output and work directory for every settled result. Dead/empty and timed-out launchers become failures. The tick releases every non-dispatching settled lead before planning (we:scripts/conveyor/pending-launches.mjs:55-76; we:skills-src/conveyor/build-dispatch-daemon.mjs:487-506).
- Direct build and prepare callers release lead and member claims on false results. Synchronous exception handling discards accepted parsed stdout, and its finally block always deletes the work directory (we:skills-src/conveyor/build-dispatch-daemon.mjs:886-910; we:skills-src/conveyor/build-dispatch-daemon.mjs:1317-1340; we:skills-src/conveyor/build-dispatch-daemon.mjs:1775-1791).
- Tests still use synthetic inline effects, expect immediate retry after a dead launcher, and require output deletion after timeout (we:skills-src/conveyor/__tests__/build-dispatch-daemon.test.mjs:1416-1421; we:skills-src/conveyor/__tests__/build-dispatch-non-blocking-launch.test.mjs:52-75; we:scripts/conveyor/__tests__/pending-launches.test.mjs:49-55).

## Design

1. **Capture the store and attempt before launch.** Resolve the canonical absolute run-store directory once, pass it to the child as `OPERATION_RUNS_DIR`, and persist it beside item, kind, attempt and any acquired group members in the pending record. The child uses the canonical file store (we:scripts/operations/run.mjs:723). Inject the read boundary for tests; use existing validated reads, without changing the producer summary or run-store schema. Later ticks/restarts use the captured directory despite environment or cwd changes. Legacy records without trustworthy store context remain indeterminate unless exact correlation can be established; do not search unrelated stores.
2. **Resolve exact persisted evidence.** Parse the actual summary, read its `runId`, and correlate summary ID/op, stored ID/op/input item, stored verdict item/kind, and the unique dispatch effect's type/payload. Kind comes from verdict/payload, not a fabricated input requirement. For in-flight acceptance require the matching effect key among the summary's `inFlight` keys, a nonblank handle and no effect error. Keep supported PID/session handles without inventing a grammar. Re-read terminal facts even if an earlier summary still lists the key as in-flight. A bare effect key, planner acceptance, unrelated live session or other attempt for the same item cannot authorize acceptance. Existing identity fields are at we:scripts/operations/dispatch-lane.mjs:1322-1327 and we:scripts/operations/dispatch-lane.mjs:1391-1396.
3. **Use four explicit evidence outcomes.** Accepted means correlated in-flight acknowledgement, not proof of present liveness or completed delivery. Refused means a correlated persisted non-dispatch verdict with zero dispatch effects, matching the existing zero-effect exit (we:scripts/operations/dispatch-lane.mjs:1374-1376). Applied/failed effects are terminal evidence for existing settlement. Everything insufficient or inconsistent is indeterminate: malformed/missing output, unreadable/corrupt/missing records, wrong identities, ambiguous effects, declared/pending effects, blank handles, transport errors and in-flight errors. Preserve diagnostic reasons and run/effect identity. A pre-verdict step refusal remains diagnostic rather than uncorrelated permission to release. In-flight errors can represent work already started (we:scripts/operations/effect-executor.mjs:401-413).
4. **Retain evidence until ownership handoff.** Make settlement two-phase within the scoped modules: resolve with the whole pending record, then acknowledge individual attempts for cleanup only after the daemon consumes their evidence. Indeterminate attempts retain pending record, stdout/stderr, work directory and claims; surface their reason without success, failure hold or automatic redispatch. A dead/timed-out launcher does not prove its child never started. Preserve the timeout duration and launcher signalling, persist that signalling was attempted before sending it, and never repeatedly signal a retained attempt's possibly reused PID. Continue re-reading retained evidence. Resolver/acknowledgement errors leave attempts protected. Remove the item-only fallback as an authority for success (we:skills-src/conveyor/build-dispatch-daemon.mjs:1817-1831).
5. **Hand evidence into the current tick before ownership decisions.** Establish pending protection before prepare completion/retirement as well as build adoption. Merge exact accepted/terminal records from the captured store into this tick's build and prepare views; cached list calls cannot refresh themselves. The current prepare observations precede settlement (we:skills-src/conveyor/build-dispatch-daemon.mjs:385-431), and live snapshots precede the entire tick (we:skills-src/conveyor/build-dispatch-daemon.mjs:2860-2867). Reuse existing row projection/terminal handling, retaining identity through handoff. Keep accepted attempts excluded from orphan adoption until the exact run reaches the normal ownership path; terminal evidence must reach its normal handler before acknowledgement cleanup. If an applied build has no consumable outcome, retain it pending rather than inventing an outcome. On a settlement read/handoff failure, preserve known pending protection or stop the tick before destructive ownership decisions; never continue with empty pending sets as though settlement succeeded.
6. **Protect direct and grouped launches too.** Use the same resolver for ordinary and exception stdout. Persist uncertain synchronous attempts with captured context and stdout/stderr before returning; preserve their work directory for restart. Cover post-spawn failures in detached record persistence as well: a successful spawn followed by a write failure must not become permission to release. Persist an attempt before spawning and update its PID afterward so that failure leaves an inspectable attempt. Distinguish a proven pre-spawn refusal from an unknown post-spawn result. Keep pending guards and same-tick scope/capacity reservations explicitly, without adding uncertainty to confirmed success lists. Preserve both lead and acquired member claims for uncertain/accepted handoffs; use persisted membership and existing `groupLead` metadata across restart. Do not count members as independent launch slots, and do not manufacture member terminal outcomes: use existing group settlement fields and retirement rules (we:skills-src/conveyor/build-dispatch-daemon.mjs:632-663; we:skills-src/conveyor/build-dispatch-daemon.mjs:1172-1187; we:skills-src/conveyor/build-dispatch-daemon.mjs:1648). Confirmed refusal retains existing prepare observation-only classification. Preserve configurable admission limits, kill-switch/freeze behavior and dry-run immutability.

## MVP

Include grouped attempts because both current callers already launch them. Preserve terminal retirement, preparation refusal classification, timeout duration and admission policy. Unknown dispatch is non-idempotent and must stay protected instead of retrying automatically (we:scripts/operations/dispatch-lane.mjs:1381-1390).
