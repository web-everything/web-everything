# Consume the real dispatch CLI outcome without releasing successful build claims

Resolve the dispatch CLI summary's run ID through the launch's configured run store and validate the persisted dispatch effect before changing ownership. The summary contains effect keys rather than effect records, but the consumer still expects records. Production now reaches this consumer through detached-launch settlement, so fixing only synchronous stdout parsing would leave ownership and evidence retention incomplete (we:scripts/operations/cli-adapter.mjs:1246-1272; we:skills-src/conveyor/build-dispatch-daemon.mjs:186-211, we:skills-src/conveyor/build-dispatch-daemon.mjs:2056-2057).

## Evidence

- The serializer emits `runId`, `op`, `verdict` and `inFlight` keys, with no `effects`. The reader selects `parsed.run ?? parsed` and searches `run.effects` (we:scripts/operations/cli-adapter.mjs:1257-1271; we:skills-src/conveyor/build-dispatch-daemon.mjs:189-209).
- Production dispatch is detached. The settlement adapter supplies the same reader, then optionally falls back to an item/kind live-row check, which does not correlate the exact acknowledged run (we:skills-src/conveyor/build-dispatch-daemon.mjs:1412-1429). That fallback can mask the schema mismatch; the mismatch alone does not prove every successful launch loses its claim.
- The detached helper passes only stdout to the reader, then deletes the pending record, output and work directory for every settled result (we:scripts/conveyor/pending-launches.mjs:55-76). The tick releases claims for every non-dispatching settled result before planning (we:skills-src/conveyor/build-dispatch-daemon.mjs:437-452).
- Both direct dispatch callers also release on false results, and synchronous exception stdout discards an accepted parsed result (we:skills-src/conveyor/build-dispatch-daemon.mjs:685-693, we:skills-src/conveyor/build-dispatch-daemon.mjs:951-961, we:skills-src/conveyor/build-dispatch-daemon.mjs:1373-1388).
- Existing parser tests supply full synthetic runs; detached tests stub outcomes or use synthetic full-run output, including an expectation that a dead launcher can immediately retry (we:skills-src/conveyor/__tests__/build-dispatch-daemon.test.mjs:1243-1248; we:skills-src/conveyor/__tests__/build-dispatch-non-blocking-launch.test.mjs:54-85). Helper tests currently require deletion after timeout (we:scripts/conveyor/__tests__/pending-launches.test.mjs:53-60).

## Design

1. Resolve real summary `runId` via the canonical file-store reader using the same resolved store directory as the launched CLI. Inject the read boundary for tests. Resolve the directory before spawning, pass the absolute path to the child through `OPERATION_RUNS_DIR`, and persist it with each new detached attempt so the child and later ticks/restarts use the same store despite environment or working-directory changes; the current pending record has no store context (we:scripts/conveyor/pending-launches.mjs:24-37). A legacy attempt without trustworthy context remains indeterminate if it cannot be correlated. Keep the generic summary and run-store contracts unchanged (we:scripts/operations/run.mjs:659; we:scripts/operations/run-store.mjs:113-121).
2. Pass expected item and launch kind from direct arguments or the persisted pending record into resolution. Correlate summary ID/op, persisted record ID/op/input item, persisted verdict item/kind and the unique matching dispatch effect's type/payload. Kind comes from the verdict and payload, not a required input field. For in-flight acceptance require the matching effect key in the summary's `inFlight` keys; re-read terminal facts even when the earlier summary still lists that key as in flight. Validate status, error and a nonblank handle without inventing a new handle grammar; PID and agent-session handles remain supported. A bare effect key, planner acceptance, unrelated live session or different attempt for the same item cannot establish acceptance. Dispatch payload identity is already present (we:scripts/operations/dispatch-lane.mjs:1351-1369).
3. Return explicit accepted, refused, terminal or indeterminate evidence, retaining run/effect identity and a diagnostic reason. Accepted requires a correlated in-flight effect with usable handle and no error; it proves acknowledgement, not current liveness or completed delivery. Confirmed refusal requires a correlated persisted non-dispatch verdict with no dispatch effects: this is the existing zero-effect exit (we:scripts/operations/dispatch-lane.mjs:1344-1348). Applied/failed effects belong to terminal settlement, not a fabricated running launch or refusal. Missing/corrupt/unreadable records, malformed output, mismatched identities, pending/declared effects, handleless effects and transport errors remain indeterminate. In-flight errors explicitly can mean work started (we:scripts/operations/effect-executor.mjs:400-409).
4. Extend detached settlement so resolution receives the pending record context and runs before destructive cleanup. Indeterminate attempts keep their pending record, stdout/stderr, work directory and claim; surface their reason and any run ID without reporting a successful launch or recording a launch-failure hold. A dead/timed-out CLI is not proof its detached child never started. Preserve the launcher timeout action, but do not turn timeout or empty output into permission to redispatch. Persist the timeout signal attempt so retained records do not repeatedly signal an old/reused PID. Re-read retained attempts on subsequent ticks; clean up only after confirmed refusal or acknowledged handoff of correlated accepted/terminal evidence (we:scripts/conveyor/pending-launches.mjs:62-76).
5. Carry uncertain attempts through the existing pending build/prepare sets before adoption and retirement, protecting claims, guards and occupancy across ticks/restarts. Those sets already exclude pending builds from adoption/retirement and keep prepares busy (we:skills-src/conveyor/build-dispatch-daemon.mjs:473, we:skills-src/conveyor/build-dispatch-daemon.mjs:561, we:skills-src/conveyor/build-dispatch-daemon.mjs:714, we:skills-src/conveyor/build-dispatch-daemon.mjs:772). Preserve existing one-at-a-time launch admission while an attempt is unresolved (we:skills-src/conveyor/build-dispatch-daemon.mjs:646-647). Do not grant acceptance through the current item-only live fallback. Make settlement two-phase within these two modules: first return retained records and their resolved evidence, then explicitly acknowledge individual records for cleanup after the daemon has consumed them. Pass correlated accepted rows into this tick's build or prepare in-flight view, and terminal rows into that kind's existing settled-run handling before adoption/retirement/launch selection. Preparation reads its views earlier than settlement (we:skills-src/conveyor/build-dispatch-daemon.mjs:356-357, we:skills-src/conveyor/build-dispatch-daemon.mjs:403); reorder those reads or explicitly merge evidence into the consumed collections before their ownership decisions. Preserve existing preparation liveness checks and attempt ordering. Protect accepted handoffs from adoption during this tick; remove that temporary protection only once the exact run is available to the normal ownership path. A handoff failure or thrown resolver must leave the attempt pending and protected, not merely set a settlement error and continue with empty pending sets. The live build and prepare in-flight adapters share a snapshot taken before launch settlement (we:skills-src/conveyor/build-dispatch-daemon.mjs:2329-2336), so merge the exact captured-store row into the tick rather than assuming a later list call refreshes it. A one-tick merge is insufficient if the daemon now reads another store: retain the attempt as the durable store locator until the normal ownership path can rediscover the exact run after restart. Cleanup must not discard the only remaining locator. Retain pending protection when the terminal record lacks an outcome the existing handler can consume; do not invent one for applied builds (we:skills-src/conveyor/build-dispatch-daemon.mjs:1242-1247). Acknowledgement parsing must not independently release/retry terminal work.
6. Apply the same evidence contract to normal and exception stdout and both direct build/prepare callers. An uncertain direct result must persist a rereadable evidence record with the same captured store/item/kind and stdout/stderr before returning, so the next tick/restart protects it through the same pending sets. Keep its work directory instead of unconditional synchronous cleanup. Preserve ownership and bookkeeping without adding it to confirmed launch lists. A throw alone is not proof that no child started; preserve diagnostic step-refusal details without letting uncorrelated summary text authorize release. Confirmed refusal keeps the existing preparation observation-only classification. Keep guards for protected attempts explicitly rather than relying on false success to retain them (we:skills-src/conveyor/build-dispatch-daemon.mjs:168-181, we:skills-src/conveyor/build-dispatch-daemon.mjs:685-693, we:skills-src/conveyor/build-dispatch-daemon.mjs:951-961).

## MVP

One consumer repair across the two source files and three test files declared in scope. Implement store-backed evidence resolution, detached context persistence and conditional cleanup, and explicit ownership protection in the daemon's settlement and direct callers. Feed both build and prepare views from the correlated evidence while preserving the shared snapshot read for unrelated runs. Preserve existing terminal retirement, timeout duration, preparation refusal classification and admission limits. Acceptance acknowledges a dispatch; pending or indeterminate protection reserves ownership without reporting confirmed success. Unknown non-idempotent dispatch must remain protected rather than automatically retrying; that requirement is already stated at we:scripts/operations/dispatch-lane.mjs:1358-1362. No new provider, producer summary format, run-store schema, claimless recovery sweep or operator retry policy belongs here.
