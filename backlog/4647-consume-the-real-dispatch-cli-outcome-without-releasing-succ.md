# Consume the real dispatch CLI outcome without releasing successful build claims

Resolve the dispatch CLI summary's run ID through the launch's configured run store and validate the persisted dispatch effect before changing ownership. The summary contains effect keys rather than effect records, but the consumer still expects records. Production now reaches this consumer through detached-launch settlement, so fixing only synchronous stdout parsing would leave ownership and evidence retention incomplete (we:scripts/operations/cli-adapter.mjs:1246-1272; we:skills-src/conveyor/build-dispatch-daemon.mjs:175-192, we:skills-src/conveyor/build-dispatch-daemon.mjs:1772-1773).

## Evidence

- The serializer emits `runId`, `op`, `verdict` and `inFlight` keys, with no `effects`. The reader selects `parsed.run ?? parsed` and searches `run.effects` (we:scripts/operations/cli-adapter.mjs:1257-1268; we:skills-src/conveyor/build-dispatch-daemon.mjs:178-191).
- Production dispatch is detached. The settlement adapter supplies the same reader, then optionally falls back to an item/kind live-row check, which does not correlate the exact acknowledged run (we:skills-src/conveyor/build-dispatch-daemon.mjs:1125-1155). That fallback can mask the schema mismatch; the mismatch alone does not prove every successful launch loses its claim.
- The detached helper passes only stdout to the reader, then deletes the pending record, output and work directory for every settled result (we:scripts/conveyor/pending-launches.mjs:55-76). The tick releases claims for every non-dispatching settled result before planning (we:skills-src/conveyor/build-dispatch-daemon.mjs:391-405).
- Both direct dispatch callers also release on false results, and synchronous exception stdout discards an accepted parsed result (we:skills-src/conveyor/build-dispatch-daemon.mjs:598-605, we:skills-src/conveyor/build-dispatch-daemon.mjs:817-827, we:skills-src/conveyor/build-dispatch-daemon.mjs:1099-1112).
- Existing parser tests supply full synthetic runs; detached tests stub outcomes or use synthetic full-run output, including an expectation that a dead launcher can immediately retry (we:skills-src/conveyor/__tests__/build-dispatch-daemon.test.mjs:1234-1238; we:skills-src/conveyor/__tests__/build-dispatch-non-blocking-launch.test.mjs:54-85). Helper tests currently require deletion after timeout (we:scripts/conveyor/__tests__/pending-launches.test.mjs:53-60).

## Design

1. Resolve real summary `runId` via the canonical file-store reader using the same resolved store directory as the launched CLI. Inject the read boundary for tests. Capture that directory with each new detached attempt so a later tick or restarted daemon cannot read a different store after an environment change; the current pending record has no store context (we:scripts/conveyor/pending-launches.mjs:24-37). A legacy attempt without trustworthy context remains indeterminate if it cannot be correlated. Keep the generic summary and run-store contracts unchanged (we:scripts/operations/run.mjs:624; we:scripts/operations/run-store.mjs:55-58).
2. Pass expected item and launch kind from direct arguments or the persisted pending record into resolution. Correlate summary ID/op, persisted record ID/op/input and the unique matching dispatch effect's type/payload. Validate status, error and a nonblank handle using existing handle conventions. A bare effect key, planner acceptance, unrelated live session or different attempt for the same item cannot establish acceptance. Dispatch payload identity is already present (we:scripts/operations/dispatch-lane.mjs:1315-1332).
3. Return explicit accepted, refused, terminal or indeterminate evidence, retaining run/effect identity and a diagnostic reason. Accepted requires a correlated in-flight effect with usable handle and no error; it proves acknowledgement, not current liveness or completed delivery. Confirmed refusal requires a correlated persisted non-dispatch verdict with no dispatch effects: this is the existing zero-effect exit (we:scripts/operations/dispatch-lane.mjs:1310-1312). Applied/failed effects belong to terminal settlement, not a fabricated running launch or refusal. Missing/corrupt/unreadable records, malformed output, mismatched identities, pending/declared effects, handleless effects and transport errors remain indeterminate. In-flight errors explicitly can mean work started (we:scripts/operations/effect-executor.mjs:400-409).
4. Extend detached settlement so resolution receives the pending record context and runs before destructive cleanup. Indeterminate attempts keep their pending record, stdout/stderr, work directory and claim; surface their reason and any run ID without reporting a successful launch or recording a launch-failure hold. A dead/timed-out CLI is not proof its detached child never started. Preserve the launcher timeout action, but do not turn timeout or empty output into permission to redispatch. Re-read retained attempts on subsequent ticks; clean up only after confirmed acceptance/refusal or a correlated handoff to terminal settlement (we:scripts/conveyor/pending-launches.mjs:62-76).
5. Carry uncertain attempts through the existing pending build/prepare sets before adoption and retirement, protecting claims, guards and occupancy across ticks/restarts. Those sets already exclude pending builds from adoption/retirement and keep prepares busy (we:skills-src/conveyor/build-dispatch-daemon.mjs:425-426, we:skills-src/conveyor/build-dispatch-daemon.mjs:514, we:skills-src/conveyor/build-dispatch-daemon.mjs:621, we:skills-src/conveyor/build-dispatch-daemon.mjs:664). Preserve existing one-at-a-time launch admission while an attempt is unresolved (we:skills-src/conveyor/build-dispatch-daemon.mjs:581). Do not grant acceptance through the current item-only live fallback. Pass terminal evidence to the existing settled-run handling; acknowledgement parsing must not independently release/retry it.
6. Apply the same evidence contract to normal and exception stdout and both direct build/prepare callers. An uncertain direct result preserves ownership and bookkeeping without appearing in confirmed launch lists. Confirmed refusal keeps the existing preparation observation-only classification. Keep guards for protected attempts explicitly rather than relying on false success to retain them (we:skills-src/conveyor/build-dispatch-daemon.mjs:157-165, we:skills-src/conveyor/build-dispatch-daemon.mjs:598-605, we:skills-src/conveyor/build-dispatch-daemon.mjs:817-827).
