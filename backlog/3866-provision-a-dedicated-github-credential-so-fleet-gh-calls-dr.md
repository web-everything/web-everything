# Provision a dedicated GitHub credential so fleet gh calls draw from a budget separate from the operator's personal account

Fleet gh calls and the operator's own personal-account GitHub usage share the SAME primary rate-limit bucket (5,000 points/hour). On 2026-09-22 the operator's own session hit 'API rate limit already exceeded for user ID 760299' after fleet load. #3670 (built, PR #2444) throttles per-call bursts and adds a per-minute points budget, but that only bounds one account's own spend, not the shared ceiling. #3699's ratified ruling addresses request volume via a shared state feed, not credential-level separation. Whether to provision a separate credential — a GitHub App installation token, or a dedicated bot/machine account PAT — so the fleet draws from its own budget.

## Grounding

Checked live 2026-09-21 against GitHub's current REST and GraphQL rate-limit docs (`docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api`, `docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api`), not assumed:

- **Primary limit, authenticated user (PAT/OAuth, any scope, classic or fine-grained):** 5,000 requests/hour (REST) or 5,000 points/hour (GraphQL) per user, keyed on the authenticated identity — this is the operator's own personal-account bucket, and it is what got exhausted on 2026-09-22 ("API rate limit already exceeded for user ID 760299").
- **Primary limit, GitHub App installation (app-to-server, installation access token):** its own 5,000 requests/hour floor, scaling "+50 requests per hour for each repository" past a 20-repo threshold and "+50 requests per hour for each user" past a 20-user org threshold, capped at 12,500/hour — a bucket entirely separate from any human account's personal limit.
- **A real trap, confirmed by reading the docs' own worked example, not inferred:** a GitHub App or OAuth App making requests "on your behalf" (the *user-to-server* flow — what `gh auth login` against an app produces) is NOT separate — "all of these requests count towards your personal rate limit," and "requests made by a higher-limit app reduce the remaining budget available for lower-limit authentication methods." Separation only holds for the app-to-server *installation* token (minted via the app's own private-key + JWT exchange), never the "authorize this app as me" flow.
- **Secondary limits** (from #3670/#3699, re-confirmed): 900 REST points/minute, 2,000 GraphQL points/minute, 100 concurrent requests — account-wide, and already the ceiling #3670's throttle wrapper gates on.
- **GITHUB_TOKEN in Actions:** 1,000 requests/hour per repository (already the basis #3699 Fork 1(c) rejected an Actions-based feed on).
- **This account's own shape** (per #3573, 2026-09-07, re-usable here): 36 public repos, no organization — an installation on it would land near ~5,800 requests/hour (16 repos over the 20-repo floor × 50/hour), short of the 12,500 cap since there is no org to add the +50/user side.
- **#3670** (built, PR #2444, parked `review:pending`) ships a 300 points/minute per-account budget plus a call/exhausted-retry sidecar log — a real, complementary fix for BURST and steady-state VOLUME, gated on before the concurrency slot on every attempt. It does not change WHICH account's bucket the fleet spends from.
- **#3699** (ratified 2026-09-21, read in full) rules Fork 1 of its own decision — a shared read-only PR/CI state feed, to cut fleet CALL VOLUME from ~24-56 points/minute (steady) or ~40-75 points/minute (worst case, ~2,400-4,500/hour) down to a flat ~4-12 points/minute regardless of watcher count. Its whole body is about request volume and where state is read from; it names no App installation, no bot/machine account, and no credential-level isolation anywhere — confirmed by reading it end to end, not assumed from this brief.

## Fork 1 — Which credential should the fleet's `gh`/API calls authenticate as?

**Why this is a fork:** the fleet's automated `gh`/API calls authenticate as some one identity, and that identity is what determines which rate-limit bucket every one of those calls draws down. Keeping the fleet on the operator's own personal token and giving it a separate identity are not compatible answers to "whose budget does fleet traffic spend" — exactly one is true going forward, not both a little. #3670's per-minute throttle and #3699's state feed both ship under every option below; they are prerequisites, not rivals to this fork.

- **(a)** Provision a GitHub App for this repo/org, install it, and route the fleet's `gh`/API calls through its INSTALLATION access token (app-to-server auth — the app authenticates as itself, never as a user, never via `gh auth login`). This is the only shape confirmed above to get a genuinely separate bucket, and it is a *larger* one on this account's own repo count (~5,800/hour today per #3573's math, scaling toward 12,500/hour as repos are added) than a flat personal-token ceiling. Real cost: a one-time setup step — register the app, install it, and swap the fleet's auth layer to mint/refresh short-lived (1-hour) installation tokens instead of a long-lived OAuth token — security-sensitive because it touches the auth layer, but the resulting token is short-lived, scoped to exactly the app's installed permissions, and revocable at the app level without touching the operator's own account credentials. Since #3670 already centralizes every migrated call through one wrapper module, the auth swap is localized there, not per call site.
- **(b)** Create a dedicated bot/machine GitHub account and mint its own PAT for the fleet to use. GitHub's Terms of Service explicitly permit this ("a machine account... set up by an individual human who accepts the Terms on behalf of the Account... used exclusively for performing automated tasks"; one such account is allowed per person in addition to their own). Simpler to stand up than (a) — no app registration, no JWT/installation-token minting, just a second `gh auth login`. But its PAT is still a personal-access-token bucket: flat 5,000 requests/hour with no repo/user scaling, the SAME ceiling class as the operator's own account, not the higher App-installation class — less throughput than (a) for this account's shape. It also adds a second full human identity to manage long-term (its own 2FA and recovery email) and its one secret is a long-lived PAT whose leak exposes that account's full granted scope, versus (a)'s short-lived, narrowly-scoped, centrally-revocable token.
- **(c)** Do nothing beyond #3670's per-call/per-minute throttle. *Rejected:* #3670 bounds bursts (the 900-points/minute secondary ceiling) and now the fleet's own steady-state volume (its 300-points/minute budget), but every one of those points is still drawn from the SAME shared 5,000-points/hour PRIMARY bucket the operator's own interactive `gh`/browser use draws from — the throttle caps how fast the fleet spends, never separates whose budget it spends from. That is exactly the failure this decision exists to fix: on 2026-09-22 the operator's OWN session, not a fleet worker, was the one refused, after the fleet's sanctioned, throttled usage had already drawn the shared bucket down. #3699's ruling is a genuine, complementary lever (cutting call volume via one shared reader instead of N pollers) but its own worst-case estimate (~2,400-4,500/hour) still lands inside the same 5,000/hour bucket the operator's manual use shares — it was never meant to, and does not, separate the credential.
- **(d)** A fine-grained PAT, scoped narrowly, still issued under the operator's own personal account. *Rejected:* GitHub's rate-limit accounting keys on the authenticated USER, not the token's scope shape — a fine-grained PAT's requests "count towards your personal rate limit of 5,000 requests per hour" exactly like a classic PAT, confirmed in the same docs pass above. Narrower scopes shrink the BLAST RADIUS of a leaked token (worth doing regardless of this fork's outcome) but do nothing to separate the BUDGET — the fleet would still be spending the operator's own bucket, so this is not a genuinely different answer to this fork's question.

**Default: (a).** A GitHub App installation, authenticated app-to-server via its installation access token, is the only option confirmed above to give the fleet a rate-limit bucket genuinely independent of the operator's personal account, and it is larger, not merely separate, on this account's own repo count. The one-time app registration and auth-layer swap is real cost, but it is paid once at the auth layer — #3670's existing wrapper centralizes the call sites already. (b) is simpler to stand up but is dominated on both throughput ceiling and secret blast-radius; (c) leaves the exact failure that triggered this decision unaddressed; (d) doesn't touch the actual axis (whose bucket, not which scopes).

**Skeptic:** Attacked (a)'s premise that "a GitHub App" alone means a separate bucket — the docs' own worked example shows a GitHub App authorized *on a user's behalf* shares that user's bucket instead, which would have silently defeated this decision if unnoticed. Fixed by naming the app-to-server / installation-token requirement explicitly in (a)'s own body, not left implicit. Also attacked whether (c) is really inadequate now that #3670 ships a 300-points/minute budget: confirmed #3699's own worst-case load (~4,500/hour) still fits under 5,000/hour alone, but that headroom is shared with the operator's own manual use, which is exactly what was refused on 2026-09-22 — the throttle governs how fast the fleet spends, never from whose account. Holds.
**Screen:** Infra-credential governance (which GitHub identity the fleet's automation authenticates as) — decidable in-repo, no WE platform-standard boundary at stake. The differences named (separate vs. shared bucket, scaling ceiling, secret blast-radius, one-time setup cost) are real functional merit differences, not a timing or prioritization call in fork costume. Clear.

## Ruling

Ratified 2026-09-22 by the operator. The operator's own words, quoted: "I ratify 3866".

- **Fork 1 — RATIFIED, (a):** a GitHub App installation, authenticated app-to-server via its installation access token; never the user-to-server "authorize as me" flow.
