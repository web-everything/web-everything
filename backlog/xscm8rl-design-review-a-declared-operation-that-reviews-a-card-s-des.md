# design-review: a declared operation that reviews a card's design through the jury panel, records it on the card, and gates clearing

A card's design is reviewed by hand today: the orchestrator pastes the card into a jury workflow launch, picks a care level by feel, and copies the findings back. This epic declares that as one operation, `design-review`. It reads a card, sets the care level from the card's own fields, runs the jury panel directly (no launcher subagent relaying a result), writes the verdict and findings onto the card together with the hash of the design it judged, and feeds a gate, so a design-first card cannot be cleared for the conveyor until a review has accepted its current design. Design-first, filed uncleared: this card is itself design-reviewed before any slice is built.

Epic under #3383. Sized as an epic, not a story: it spans a pure core, an operation, a card writer, three clearing paths, a skill and a notice, so no single story of size 8 or less holds it. The proposed slices are at the end.

## Why (each fact read from the code or the cards on 2026-09-20)

1. **Reviews are run by hand.** `we:skills-src/jury/SKILL.md` documents `/workflow subject-jury` with subject `decision-prose`; the caller chooses `careLevel` and pastes the material. Nothing ties a run to a card.
2. **The launcher relay can make a run that happened look like it did not.** Card #3741: a 7-seat panel finished (ok, $0.41) but the launcher subagent could not relay the roughly 55 KB result through its structured output, and the harness reported spend 0 and needs-human with every lens unknown.
3. **The care level is chosen by feel and was mis-scaled.** The `track` epic (#3740) was reviewed at low care and drew 40 findings and an escalation; #3737 at low care returned `changes` with five checked defects. `deriveCareLevel` in `we:scripts/lib/review-escalation.mjs` derives care only from PR signals (dismissed findings, blast radius, size, cross-repo); nothing derives it from a card.
4. **Findings are pasted by hand.** The `## Design review (jury, 2026-09-20, careLevel low)` sections on #3737 and #3738 were typed in by the orchestrator (commit 9df5bf74f). The heading carries date, care and verdict but no spend, no round count and no hash of the design that was judged, so a later edit to the design is invisible.
5. **Never run and found nothing look alike.** A card with no review section and a card whose review found nothing are indistinguishable to any script, and the #3741 failure printed a state that read as "no review".
6. **No gate exists and no marker exists.** Searching `we:scripts/` for `design-first` or `designFirst` finds nothing; `we:docs/agent/design-first.md` is about authoring standards, not cards. Clearing goes through three paths: the `queueAdd` effect of `we:scripts/operations/file-item.mjs` (decided by `planQueueing`); `we:scripts/conveyor/queue.mjs add`, which only warns (kind, readiness) and never refuses, into the gitignored session sidecar `we:.conveyor/queue.json` (`we:scripts/conveyor/queue-store.mjs`, #2613); and the older `we:scripts/backlog.mjs build-queue add` (#2530), which writes `buildQueued: true` into frontmatter. The `track` slices (#3746, #3758, #3759) say "Filed uncleared: a design review comes before any build" in prose only.
7. **A run can die with no record.** Reported by the operator session: a workflow run's task vanished after a reconnect (not confirmable from the repo). Operations already keep a run record (`we:scripts/operations/run-store.mjs`), and an effect can be `in-flight` with an `expectedBy` deadline (#3073, `we:scripts/operations/run-record.mjs`), so an overdue run is detectable if the review is an operation.
8. **The verdict words are not a card state.** `VERDICTS` in `we:scripts/lib/jury-core.mjs` is `accept`, `changes`, `needs-human`, `prevention-outstanding`; no rule says what each means for a card.

## Design

**Settled (read from the code).**

1. **A separate operation over the shared engine.** `we:scripts/operations/review-prep.mjs` already decided that a card is a different subject shape from a PR (separate operation, not a flag). The same reasoning keeps `design-review` apart from `review-prep`: different juror (a tool-free panel against one tool-bearing juror), different output (a verdict state that feeds a gate against a note). It IMPORTS the reader and the content-hash race guard from `we:scripts/operations/review-prep-io.mjs` (`readPrep`, `contentHashOf`, `resolveCardPath`), the adapter `DECISION_PROSE_ADAPTER`, the roster (`resolveAdapterRoster`, `materializeRoster`), the reducer (`derivePanelVerdict`, `buildPanelFindings`) and the red-team pair (`redTeamRequired`, `foldRedTeamVerdict`). It copies no jury logic.
2. **Step shape.** `read` (compute, injected reader) then `plan` (compute: care level, round number, spend ceiling, all recorded) then `panel` (effect) then `reduce` (compute) then, on an accept only, `redTeam` (effect: one tool-free juror) then `record` (effect through the guarded writer). The engine has four step kinds (`compute`, `judge`, `confirm`, `effect`; a fifth is barred by the operations statute, #3031), and a `judge` step is one juror, so a 7-seat panel as judge steps would run its seats one after another. The panel is therefore called from an injected function (`runPanel`) inside an `effect` step, the same injected-io pattern `we:scripts/operations/file-item.mjs` uses. An effect also gives it a run-record lifecycle (`in-flight` with `expectedBy`).
3. **The panel is called directly and its result is a file.** `runPanel` resolves the roster, calls `judgePanel` (`we:scripts/lib/judge-panel.mjs`), writes the whole result to a panel-result file in the run directory (one per round) and returns the path, the seat counts and the spend. The `reduce` step reads the file by path. No subagent relays a payload, so the #3741 failure cannot occur. A crash after the panel returns is resumed with `--resume=<run-id>`: the file exists, so nothing is billed twice.
4. **Care is derived, never chosen.** A pure `deriveDesignCareLevel` beside `deriveCareLevel` reuses `CARE_LEVELS` and `CARE_BANDS` and sums weights over card signals: size and kind, and touched surfaces read from `scope:` paths and a fixed keyword list in the design text (launchd, data migration or backfill, credentials or identity data, cost decisions, hooks or permissions, conveyor machinery). The floor is `low`, never `none`, because `panelRigorForCareLevel('none')` seats zero jurors and a review with zero jurors must not read as reviewed. The dial and each signal that fired are written to the run and to the card. A caller may raise the level and never lower it.
5. **Verdict to card state.** `accept` with a clean red-team is `accepted`. `changes` is `changes` (findings recorded; the design must absorb them). `prevention-outstanding` is treated as `changes` (accepted in substance but an uncaptured prevention guard is owed). `needs-human` stays `needs-human`. Two states are added that no jury verdict can produce: `relay-failed` (the panel or the record did not complete, or the result file is missing or unreadable; written by the operation itself, or reported by `--status` for an overdue run) and `not-run` (no record). Only `accepted` with a design hash equal to the card's current design hash satisfies the gate; `accepted` with a different hash reads `stale`. `relay-failed` and `not-run` can never read as accepted or as reviewed, and both are loud in the run outcome and in `--status`.
6. **The gate is a pure function read at clear time and again at launch.** `designReviewGate(card)` in the new core returns `{ cleared, state, reason }` from the card text alone. It is called by `planQueueing` (`we:scripts/operations/file-item.mjs`), by `we:scripts/conveyor/queue.mjs add` (which today warns only, so this is a change from warning to refusing for a marked card), and by `we:scripts/backlog.mjs build-queue add`. Because the sidecar `we:.conveyor/queue.json` is tolerantly parsed and can be edited by anything, it is also checked on the launch side: a cleared row whose card is marked and not `accepted`-current is not launchable in `planTick` (`we:scripts/conveyor/tick-core.mjs`). Refusing early gives feedback; checking at launch is the backstop.
7. **Independence and safety.** Jurors are the tool-free headless `claude -p` processes `judgePanel` already spawns (`--tools ''`, distinct `--session-id` per seat, refused before any spawn if not pairwise distinct). Card text is passed as fenced data (`fenceUntrusted`, `FENCED_DATA_RULE` from `we:scripts/lib/review-core.mjs`); a card can carry text from other sources (the `track` intake). The operation applies no label, posts no comment and clears nothing; it writes exactly one review section and never touches `status`, `buildQueued` or the queue sidecar. The honest limit, as in #2895: a distinct session id is not an unforgeable actor signal, and a hand-typed review header would satisfy the gate. The gate defends against habit, not against a person who forges a record.
8. **Cost control.** The plan step sets a spend ceiling per round from the care level and passes it as `maxTotalBudgetUsd` (`judgePanel` already refuses a missing ceiling and checks the declared per-seat budgets before the first spawn; the operation adds a refusal, before the first spawn, when cumulative spend on this card plus the planned round would exceed the ceiling). The verdict reports `totalCostUsd` from the panel result. A second round is allowed only when all four hold: the last recorded verdict is `changes` or `prevention-outstanding`; the design hash differs from the one last reviewed (a round on an unchanged design judges nothing new, the same rule `we:scripts/operations/review-loop-cli.mjs` states for diffs); rounds used are below the cap from `panelRigorForCareLevel` (low 1, elevated 2, high 3); and cumulative spend stays under the ceiling. An exhausted cap ends in `needs-human`.
9. **Recording.** One `## Design review` section per round, appended by the guarded writer (`we:scripts/backlog/guarded-write.mjs`, which refuses the primary checkout, scrubs secrets and enforces the locus prefix). It opens with one machine-readable header line (verdict state, date, care level and the signals that set it, round, spend, design hash, run id) and then the findings text. Later sections do not replace earlier ones; the gate reads the last header.
10. **Front door.** The CLI is derived from the declaration by `we:scripts/operations/cli-adapter.mjs` (registered in `we:scripts/operations/run.mjs`, with a `we:scripts/operations/declared-homes.mjs` entry naming the hand sequence it replaces); there is no hand-written CLI. `/design-review <card>` is a thin skill in `we:skills-src/design-review/SKILL.md`, in the manner of `we:skills-src/jury/SKILL.md`, and states when NOT to use it (a PR diff is `review-pr`, an interactive verdict on a parked PR is `/review`, a claims-against-live-code check is `review-prep`). `--status` lists marked cards with their state and any run past its `expectedBy`.

**Open (settle in the design review; each has a leaning).**

1. **Care table values.** The signals in settled 4 are certain; the weights and bands are not. Leaning: launchd, data migration and credentials or identity each weigh 3 (elevated alone); cost decisions, hooks or permissions and conveyor machinery weigh 2; size 5 weighs 1 and size 8 or epic weighs 2; an all-docs scope weighs 0 (floored to low). So a launchd card reaches elevated or high and a docs-only card stays at low. To be checked against the two hand-scaled cases (#3737, #3740) before it is fixed.
2. **The design hash.** What is hashed decides what counts as "the same design". Leaning: SHA-256 over the LF-normalised body with every `## Design review` and `## Independent review` section removed, plus the frontmatter fields `kind`, `size`, `parent`, `scope` and `blockedBy` (sorted). Status, dates, `buildQueued`, `tags` and the prepare stamps are excluded, so a claim or a review append never stales a review but any edit to the digest, the design or the acceptance does. Open sub-question: should a typo fix stale the review (leaning yes, deterministic) and is a `--restamp` shortcut wanted (leaning no: it is a bypass).
3. **Section or sidecar.** Leaning section: it is durable, reviewed in the same pull request, and survives JIT renumbering, which strands a sidecar keyed by id (`we:scripts/conveyor/queue.mjs` documents that failure for the queue sidecar). Costs: findings can be large (40 findings on #3740), so the section caps the findings list and says how many more the run record holds; and the locus-prefix rule refuses a whole write that quotes a bare code path (a live run of `review-prep` hit exactly this), so the record step normalises prefixes and, if it still cannot write, records `relay-failed` rather than dropping findings.
4. **Editor fold in v1.** Leaning out of v1. The editor fold would propose a revised design as a patch, never applied silently; in v1 the caller edits the card, which changes the hash and makes the next round legal. Filed later if hand-absorbing findings proves to be the bottleneck.
5. **What the gate covers.** No code today knows a design-first marker (fact 6), so the epic must define one. Leaning: an explicit frontmatter key `designReview: required`, written by `file-item` (default on for `epic` and for a `story` of size 5 or more, off otherwise), with an explicit recorded waiver (`designReview: waived` plus a reason) instead of silence. `decision` cards keep their own path (`we:skills-src/prepare-decision-item/SKILL.md`, ratify) and are not gated, though the decision-prose adapter can review their approach on request. For an `epic`, clearing is moot (the conveyor never builds an epic), so the gate applies to slicing: children are not filed until the epic's design is accepted. Cards without the key are not gated (grandfathered) until the marking sweep.
6. **Tool-free jurors cannot check code claims.** The #3158 ruling keeps panel seats tool-free by design, so the panel judges design soundness but cannot verify "this function exists at this line". Options: the `read` step gathers evidence for each `we:` path in the card (exists, the cited lines) and passes it as fenced data; or the gate also requires a `review-prep` run. Leaning: evidence pre-fetch in v1, `review-prep` stays optional.
7. **Coexistence.** Leaning as in settled 1 and 10: four separate front doors over one engine, each skill naming when not to use it. `/jury` stays the generic hand-run method for any subject.
8. **Commit or working tree only.** `review-prep` commits and pushes; `file-item` writes the working tree and leaves landing to the caller. Leaning working tree only, so the review lands with the design edit it judged through the normal `verify` then `open-pr` path; the run record keeps the panel file path if a session dies before landing.
9. **The completion notice.** `we:scripts/operations/operator-notify.mjs` is shaped for PR rows, not for a card run. Precedent for a non-PR notice: `we:scripts/operations/review-loop-cli.mjs` appends an entry to the learnings pool. Leaning: the same, on `needs-human`, `changes` and `relay-failed`; an `accepted` is reported in the run outcome only.
10. **Ceiling numbers and wall time.** One measured data point exists (a 7-seat low panel cost $0.41, #3741); high care seats twice as many jurors per lens and runs up to three rounds. The ceilings are to be set from that and from the usage aggregation in #3738, not guessed here. Panel wall time is unmeasured; the operation runs in the foreground and the tool call cap is 10 minutes, so a high-care run with a red-team may not fit in one call. Resumability (settled 3) is what makes that safe; measure it in slice 3.
11. **A card-specific adapter.** v1 reuses `DECISION_PROSE_ADAPTER` unchanged (it found real defects on #3737 and #3740). Whether a card needs its own lenses (executable acceptance, slice size, scope fit) is decided from what the first real runs miss.
12. **Existing cards.** The marking sweep decides which open, uncleared cards get the marker (at least #3737, #3738 and the `track` slices) and re-records their hand reviews in the new format.

## Proposed slices (to be filed after the design review, each design-reviewed in turn)

1. **Core, pure:** design hash, header render and parse, state derivation, `deriveDesignCareLevel` and its table, `designReviewGate`. Size 5.
2. **Operation declaration and io** with an injected panel runner: read, plan, panel, reduce, red-team, record; run record with `expectedBy`; the spend refusal. Size 8 (split further if the design review says so). Blocked by 1.
3. **The real panel runner:** roster, `judgePanel`, result file by path, spend; one live run on a real card; wall-time measurement. Size 5. Blocked by 2.
4. **Gate wiring:** `planQueueing` (composed with #3746), `we:scripts/conveyor/queue.mjs add`, `we:scripts/backlog.mjs build-queue add`, the launch-side check in `planTick`, and the marker written by `file-item`. Size 5. Blocked by 1 and #3746.
5. **Front door:** `/design-review` skill, `we:scripts/operations/run.mjs` registration, `we:scripts/operations/declared-homes.mjs` entry, `--status`, the completion notice. Size 3. Blocked by 2.
6. **Marking sweep** of the open cards and re-recording of the two hand reviews. Size 2. Blocked by 4.
7. **Later, not filed:** the editor fold as a proposed patch; a card-specific adapter.

## Done when

The epic is done when its slices are resolved and the five checks below pass. Slice cards carry the narrower form of each.

1. **Executable (decisions)** — `node --test we:scripts/lib/__tests__/design-review-core.test.mjs` passes. On fixture cards, the care level of a card whose scope touches launchd is higher than the care level of a docs-only card; the docs-only card is `low`, never `none`; each surface row of the table is pinned by its own case. The design hash is unchanged by a review-section append, a status change and a claim stamp, and changes when one word of the digest, the design or the acceptance changes. The state derivation returns `accepted`, `stale`, `changes`, `needs-human`, `relay-failed` or `not-run` for the matching fixture, and only `accepted` with an equal hash clears `designReviewGate`.
2. **Executable (operation, fake panel)** — `node --test we:scripts/operations/__tests__/design-review.test.mjs` passes. The panel runs against a fake spawn at the `judgeSpawn` seam, so the real argv is built and asserted: every seat has `--tools ''` and a pairwise distinct `--session-id`. A fake panel of all-accept plus a clean red-team records `accepted`; a fake panel with a failing mandatory lens records `changes` with each finding on the card; a fake panel that throws, or writes an unreadable or missing result file, records `relay-failed`, which the run outcome prints as failed and which never equals `accepted`. With a spend ceiling below the planned round, zero spawns happen and the run refuses. A second round on an unchanged design hash is refused. The run record shows the panel effect `in-flight` with an `expectedBy` before the fake returns, and a run killed there is reported overdue by `design-review --status`.
3. **Executable (real mechanism)** — `node --test we:scripts/lib/__tests__/design-review-gate.test.mjs` passes, and it uses a real temporary git repo and real child processes, not doubles. The record step writes a real `## Design review` section through the real guarded writer (a finding that quotes a bare code path is prefixed or refused loudly, never dropped silently). Then, for a `designReview: required` story with no review, each of `we:scripts/conveyor/queue.mjs add` (run as a real process with `CONVEYOR_BACKLOG_DIR` and `CONVEYOR_QUEUE_FILE` pointed at the fixture), `we:scripts/backlog.mjs build-queue add` and the `file-item` queue effect refuses to clear it, and the queue sidecar is byte-identical afterwards. After an `accepted` section whose hash matches, all three clear it. After a one-word edit to the design, all three refuse again. A card without the marker behaves exactly as before.
4. **Executable (launch-side backstop)** — the same suite feeds `planTick` (`we:scripts/conveyor/tick-core.mjs`) a state whose sidecar already lists an unreviewed `designReview: required` story as cleared, and asserts it has no build spawn for that card. `node we:scripts/operations/run.mjs design-review --help` lists flags derived from the declaration, and `npm run check:standards` passes with the new files.
5. **Observable (one live run, recorded)** — one real `design-review` run on a real filed card leaves a `## Design review` section on that card with the date, care level and the signals that set it, round, spend, design hash and run id, and the run record holds the panel result file by path. The card names the run id. This is the only criterion that spends real money, and it is where the wall time of a high-care round is first measured.
