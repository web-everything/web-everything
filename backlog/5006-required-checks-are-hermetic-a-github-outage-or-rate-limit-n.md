# Required checks are hermetic: a GitHub outage or rate limit never fails a PR or turns main red

Operator ruling 2026-10-03. Live: PR #3828's required soak-replay-gate failed at 18:49Z with 'gh: API rate limit exceeded for installation', because we:.github/workflows/soak-replay-gate.yml calls the API to read the live PR body. A required check that depends on GitHub's API budget makes good code look broken, and on main it reads as main-red and blocks every PR. Fixed rules: (1) soak-replay-gate reads the PR body from the workflow's event payload (github.event.pull_request.body), not the API; this is the cheap first step. (2) Tests never call real gh or the network; they use recorded responses. Any live-GitHub test moves to a non-required scheduled group that alerts but never gates. (3) A guard fails any required test that spawns gh or opens a network socket. Configurable (config-extends-platform-default, we:config/platformDefaults.ts and we:config/defineConfig.ts): ciChecks.onGithubUnavailable = retry-then-neutral (default) | fail | skip, plus a retry budget; a neutral 'could not run' result never counts as main-red and never dispatches a fixer. Done when: soak-replay-gate passes with the API blocked; the guard catches a seeded gh call in a test; a rate-limited check reports neutral, not failure.

## Design

**One shared pure classifier, one policy, one thin wrapper.** The decision lives in a new pure module we:scripts/lib/github-unavailable.mjs, the shape of we:scripts/conveyor/infra-cancelled.mjs (pure, a mirror of a platform default pinned by a test, env override):

1. `classifyGithubUnavailable({ exitCode, stderr, httpStatus })` returns `'unavailable'` or `'real'`. `unavailable` only on positive evidence: HTTP 403/429 whose text matches `API rate limit exceeded`, `secondary rate limit` or `abuse detection`; HTTP 502/503/504; or a transport failure (`ECONNRESET`, `ETIMEDOUT`, `EAI_AGAIN`, `could not resolve host`, `connection refused`). Everything else (a 404, a 401/403 without a rate-limit marker, a parse error, an empty body) is `real` and keeps failing. The text is folded with `foldUntrusted` (we:scripts/lib/jury-core.mjs) and NFKC-normalised; matching is against a fixed marker list, never a regex built from the text.
2. `resolveOnGithubUnavailable(env)` returns `{ policy, retries, backoffSeconds, refusedReason? }`. Policy from `ciChecks.onGithubUnavailable` (`retry-then-neutral` default, `fail`, `skip`), env `WE_CI_ON_GITHUB_UNAVAILABLE`; budget default 3 attempts, 5 s backoff doubling, hard cap 60 s per sleep, env `WE_CI_GITHUB_RETRIES` and `WE_CI_GITHUB_BACKOFF_SECONDS`. An unrecognised policy or a non-numeric/negative/over-cap budget resolves to the SAFE side (`fail`, default budget) with a `refusedReason` the wrapper prints.
3. `runWithGithubPolicy({ run, policy, sleep })` returns `{ kind: 'ok' | 'real-failure' | 'neutral' | 'skipped' | 'failed-unavailable', attempts, evidence }`. `retry-then-neutral` retries only `unavailable` outcomes up to the budget, then `neutral`. `fail`: no retry, an `unavailable` outcome is `failed-unavailable` (nonzero). `skip`: no retry, `skipped`. A `real` failure is ALWAYS `real-failure` (nonzero) under every policy.
4. Thin CLI we:scripts/ci/gh-with-policy.mjs runs a command through (3), prints its stdout on `ok`, and on `neutral`/`skipped` prints `::warning::<check>: neutral - GitHub unavailable after N attempts (<evidence>)` plus a `$GITHUB_STEP_SUMMARY` line, then exits 0. GitHub Actions cannot conclude a job `neutral`; here "neutral" means the job PASSES with a warning annotation, which satisfies the required check and which the conveyor reads as non-red. `failed-unavailable` and `real-failure` exit nonzero.

## Edge cases this change must handle

1. **Untrusted text** - the PR body/title and `gh` stderr reach a shell, argv and a classifier. The body travels only via env (`PR_BODY`), never interpolated into `run:`; stderr is folded (`foldUntrusted`), NFKC-normalised and matched against a FIXED marker list (no regex from input); the CLI keeps `--body=<value>` as one token so a `--`-prefixed value never becomes a flag. Test cases 4 and 1.
2. **Truncated reads** - the merge-group PR JSON read goes through the wrapper with a large `maxBuffer`; truncated, empty or unparseable JSON is a `real` failure, never "no PRs"; the existing empty-group fail-closed (`[ -n "$PRS" ]`) stays. Test case 5.
3. **Shared state files** - n/a: the classifier and wrapper keep no state across runs (the attempt counter is in-process); the only shared file written is `$GITHUB_STEP_SUMMARY`, appended once per run.
4. **Fail closed** - an unrecognised policy, an unparseable budget, an unknown error shape or a wrapper crash resolves to `fail`/`real-failure` (nonzero) naming the reason. `neutral` is reachable ONLY through a positive `unavailable` classification AND an exhausted budget under `retry-then-neutral`. Test cases 2 and 3.
5. **Identity scoping** - the neutral warning and summary name the check, repo, PR number and head sha; merge-group results are per PR number; the retry budget is per invocation, never shared across PRs or heads. Test case 5.
6. **State over time** - a stale payload body: `edited` stays in `on.pull_request.types`, so every body edit re-triggers with a fresh payload; a manual re-run of an old run sees the old body (documented in the workflow header, in Follow-ups). Backoff is bounded (budget x doubling, 60 s cap per sleep, total well under the job timeout); a runner restart mid-retry simply re-runs the step.
7. **Who wrote it** - `github.event.pull_request.body` is author-controlled text, but it only feeds the soak gate's `soak-waiver:` line, which is the existing trust model; a `neutral` outcome grants no soak waiver, and a merge-group `neutral` is justified in Design (the PR-event run already evaluated the same head) and always leaves a visible record. The socket guard trusts only loopback/unix targets, never a hostname a test supplies.
