# Required checks are hermetic: a GitHub outage or rate limit never fails a PR or turns main red

Operator ruling 2026-10-03. Live: PR #3828's required soak-replay-gate failed at 18:49Z with 'gh: API rate limit exceeded for installation', because we:.github/workflows/soak-replay-gate.yml calls the API to read the live PR body. A required check that depends on GitHub's API budget makes good code look broken, and on main it reads as main-red and blocks every PR. Fixed rules: (1) soak-replay-gate reads the PR body from the workflow's event payload (github.event.pull_request.body), not the API; this is the cheap first step. (2) Tests never call real gh or the network; they use recorded responses. Any live-GitHub test moves to a non-required scheduled group that alerts but never gates. (3) A guard fails any required test that spawns gh or opens a network socket. Configurable (config-extends-platform-default, we:config/platformDefaults.ts and we:config/defineConfig.ts): ciChecks.onGithubUnavailable = retry-then-neutral (default) | fail | skip, plus a retry budget; a neutral 'could not run' result never counts as main-red and never dispatches a fixer. Done when: soak-replay-gate passes with the API blocked; the guard catches a seeded gh call in a test; a rate-limited check reports neutral, not failure.

## Design

**1. Pure classifier and policy** — new we:scripts/lib/ci-github-unavailable.mjs (pure, no process spawn, no import of we:scripts/lib/gh-throttle.mjs, which spawns; the required workflows run it from a `ref: main` checkout). Exports:
- `isGithubUnavailable(text)`: true for a rate limit, HTTP 5xx, and connection-level errors or timeouts (`ECONNRESET`, `ETIMEDOUT`, "timed out", `EAI_AGAIN`, "could not resolve host"). False for 401, 404, and any 403 that is not rate-limit-shaped (a real denial must fail closed). The patterns are COPIED as light local regexes, not imported: `classifyPrOpenFailure` (we:scripts/conveyor/infra-blocked.mjs:117) lives in a module that imports queue-store and operations code, so it is not pure. A pin test (A6) asserts the new classifier agrees with `isRateLimitShaped` (we:scripts/lib/gh-throttle.mjs:948) on the rate-limit incident strings so the two cannot drift.
- `resolveOnGithubUnavailable(env)` / `resolveRetryBudget(env)`: env `WE_CI_CHECKS_ON_GITHUB_UNAVAILABLE` (`retry-then-neutral` | `fail` | `skip`) and `WE_CI_CHECKS_GITHUB_RETRY_BUDGET` (non-negative integer, default 3). **How a project override reaches the workflow:** the workflow step sets the two env vars from repository variables (`vars.CI_CHECKS_ON_GITHUB_UNAVAILABLE`, `vars.CI_CHECKS_GITHUB_RETRY_BUDGET`); an unset variable means the platform default, and the `.ts` setting is the declared contract those variables implement (A6 asserts the workflow wires both variables, so a configured `fail` cannot be silently replaced by the default). An unknown value does NOT fall back silently: it returns `{ok:false, reason:'unknown-mode'}` and the CLI exits 1 naming the bad value (a typo must not quietly turn a gate neutral).

**2. Workflow-side reader** — new we:scripts/ci/github-read.mjs (CLI): it takes any command argv after `--` (a `gh api <path> --jq …` call, or the we:scripts/merge-gate-check.mjs list-group call), plus `--require-value` when empty stdout is an error (a legitimately empty PR body, `.body // ""`, is read without it). It runs that argv with an explicit `maxBuffer` and a read timeout, retries with doubling backoff (base 2 s, cap 30 s, at most `retryBudget` retries) only while `isGithubUnavailable(stderr)`, and decides:
- success → stdout passes through, exit 0.
- unavailable after the budget, mode `retry-then-neutral` → print `::warning title=could-not-run::github-unavailable (<cause>)` to STDERR (never stdout: callers capture stdout with `PR_BODY=$(...)`, which would swallow a stdout command; the runner parses workflow commands from stderr too, and a test asserts stdout carries only the value; the title is the machine-readable marker the merge gate reads, see A10), append the same line to `$GITHUB_STEP_SUMMARY`, write `could_not_run=true` to `$GITHUB_OUTPUT`, exit 0. Later steps carry `if: steps.<id>.outputs.could_not_run != 'true'`, so the job ends **success with a could-not-run annotation**. GitHub Actions cannot set a job conclusion to `neutral` from a step, and branch protection treats neutral, skipped and success alike, so this is the closest honest "neutral": never failure, never red.
- unavailable, mode `skip` → no retries, same outputs, exit 0.
- unavailable, mode `fail` → exit 1 (explicit strictness, the operator's opt-in).
- any other failure (404, 401, non-rate-limit 403, unparseable output, spawn error, buffer overflow, empty stdout under `--require-value`) → exit 1 in EVERY mode, naming the refusal reason. A missing `gh` binary is a failure, not "unavailable".
The argv after `--` is passed as an array (never through a shell); a value starting with `--` in the path position is refused.

**3. Config (config-extends-platform-default)** — we:config/defineConfig.ts gains `export type CiChecksOnGithubUnavailable = 'retry-then-neutral' | 'fail' | 'skip'` and a `ciChecks?: { onGithubUnavailable?: …; retryBudget?: number }` setting; we:config/platformDefaults.ts gains `PLATFORM_CI_CHECKS_DEFAULTS = { onGithubUnavailable: 'retry-then-neutral', retryBudget: 3 }` (same declare-and-mirror pattern as `PLATFORM_CI_HEAL_DEFAULTS` at we:config/platformDefaults.ts:73, mirrored by constants in we:scripts/lib/ci-github-unavailable.mjs because `.mjs` cannot import `.ts`; we:config/__tests__/config-contract.test.ts pins the two together).

**4. Workflows**
- we:.github/workflows/soak-replay-gate.yml, `pull_request` step: add `EVENT_PR_BODY: ${{ github.event.pull_request.body }}` and `RUN_ATTEMPT: ${{ github.run_attempt }}`. If `RUN_ATTEMPT` is 1, `PR_BODY="$EVENT_PR_BODY"` and no `gh api` runs. If greater than 1, read the live body through the we:scripts/ci/github-read.mjs wrapper (keeps #4479). When it reports `could_not_run`, skip the rest of the step (and say so in the summary). The `git fetch` calls are plain git over the token and keep their fail-closed `exit 1` (a failed fetch is a real failure, not a body read).
- Same file, `merge_group` step (the LAST gate before `main`): both reads go through the wrapper for its RETRIES only (the we:scripts/merge-gate-check.mjs `--list-group` GraphQL read and each per-PR `gh api repos/$PR_REPO/pulls/$N`; no payload exists for a group's member PRs), but this step is **always fail-closed after the retry budget**, whatever the mode is set to: an unevaluated PR in a merge group can lack both soak coverage and a waiver, and a failed merge-queue entry is simply retried by the queue. The wrapper therefore takes `--fail-closed` (exit 1 on unavailable) and the step passes it. Only the `pull_request` run can report could-not-run.
- we:.github/workflows/ci.yml "Enforce bot-owned test timings": we:scripts/ci/check-timings-bot-only.mjs makes three `gh api` reads (head sha at :37, base ref at :46, compare at :52) inside a catch-all that swallows stderr. It never reports could-not-run. The operator's "done when" needs only `soak-replay-gate` to pass blocked and "a rate-limited check reports neutral"; the soak gate satisfies both, and the timings check gains transient-limit resilience without loosening.

Its fake `node` must pass through for we:scripts/ci/github-read.mjs (otherwise it swallows the wrapper and runs the gate evaluator), and the fixture must copy the wrapper and the lib files it imports.

## MVP

Musts only:
- The pure classifier/policy, the wrapper CLI, the config setting with its mirror and contract test.
- we:.github/workflows/soak-replay-gate.yml reads the payload body on attempt 1 and routes the rerun reads through the wrapper (could-not-run allowed) and the merge-group reads through it fail-closed after retries; the we:.github/workflows/ci.yml bot-only-timings read gets retries only, then fails closed.
- Fail-closed on every non-unavailable error and on an unknown mode.
- The merge backstop (A10): a head whose required check reported could-not-run is held at `mergePr` until a rerun evaluates it, so could-not-run can never land unevaluated code under `drain-direct`.
- The two extra hermetic cases in A8 (raw socket, debt-list identity).
- A pinning test that a neutral/success-with-annotation check is never red and dispatches no ci-heal; a regression case that the existing hermetic guard still catches a seeded `gh` call.

Deliberately OUT (see Follow-ups): the other required workflows' API reads, the merge-gate-check script's own reads, retrying third-party action steps (`actions/checkout`), a real Checks-API `neutral` conclusion, and the `fail`-mode job being classified as infra by the conveyor.

## Edge cases this change must handle

1. **Untrusted text** — the PR body and title reach `--body=` and `--title=`: keep them in env vars and quoted `--key="$VAR"` form (never `--`-leading argv on their own); the wrapper takes the `gh` argv as an array after `--` with no shell; fold newlines and backticks in anything it echoes into `::warning::` or the step summary (`foldUntrusted`, we:scripts/lib/jury-core.mjs) so a `gh` error body cannot inject workflow commands. NFKC and invisible characters: n/a beyond that fold, no key is derived from them.
2. **Truncated reads** — the wrapper sets an explicit `maxBuffer` (we:scripts/lib/proc-read.mjs) and treats a buffer overflow and a successful exit with empty stdout under `--require-value` as FAILURES, not "unavailable". A read TIMEOUT is classed unavailable (the classifier maps "timed out" to a network cause) and is covered by an A3/A4 case. `--limit` hit: n/a (single-object `pulls/<n>` read).
3. **Shared state files** — n/a: the wrapper keeps no state file; the retry count lives in the process. (The `$GITHUB_OUTPUT` and `$GITHUB_STEP_SUMMARY` appends are append-only, one writer per step.)
4. **Fail closed** — a failed parse of the mode env, a missing `gh`, a 401/404/non-rate-limit 403, a spawn error, or an unreadable body each exit 1 with a named reason; only a positively classified unavailable result can become neutral. `fail` mode exits 1 on unavailable. An unset env var means the platform default, an invalid one means exit 1.
5. **Identity scoping** — the body read is keyed by `github.repository` + `github.event.pull_request.number`; a rerun re-reads that PR's live body, and the head/base shas stay the event's (unchanged). Merge group: each PR read is by its own number from `--list-group`.
6. **State over time** — a rerun after a waiver edit sees the new body (attempt > 1 live read); attempt 1 after an `edited` event sees the new payload, and a body edit that removes a waiver queues a new run whose `concurrency` group (`cancel-in-progress: true`, keyed by PR number) cancels any earlier run still holding the stale payload, so waiver removal still takes effect without a new commit (A1 includes the removal case: payload without waiver at attempt 1 fails the gate); a rate limit that clears mid-retry succeeds on a later try and is NOT reported neutral; backoff is bounded (cap 30 s, budget 3) so a persistent outage ends the step in about 1 minute; a restart mid-retry just reruns the step.
7. **Who wrote it** — the live body is read only from `repos/$GITHUB_REPOSITORY/pulls/<n>` with the workflow token; the neutral marker is trusted only when produced by the wrapper's own `$GITHUB_OUTPUT` write, never by text in a PR body (a body containing `could_not_run=true` must not skip the gate: A5 covers it).
