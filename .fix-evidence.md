PR #5009 — round 3 fix evidence (security finding: unpaginated `rules/branches` read in `readQueueRequiredChecks`)

Finding: `readQueueRequiredChecks` did its own unpaginated `gh api repos/<repo>/rules/branches/<branch>` read (30 rules per page) instead of the shared paginated reader, so a ruleset check on page 2 was dropped — notably on the `declared` path, where the classic set is the declared policy and the raw read was the only ruleset source.

Fix: merged live `origin/main` once (it carries PR #4924's shared reader: `defaultReadRequiredStatusChecks` reads `rules/branches?per_page=100` with `--paginate --slurp`, unions classic protection, and `getRequiredStatusChecks` caches it). `readQueueRequiredChecks` now calls only `getRequiredStatusChecks` with `ttlMs: 0` and accepts only `live` (the full paginated union, read once per pass by the existing memo). `cache`, `declared`, `fallback`, `stale-cache`, `unavailable`, any malformed result and any throw grant no relief. The raw `gh` read and its `exec` injection are gone.

Self-review (adversarial subagent) found two more same-class variants, both fixed in a second commit:
- A fresh `cache` entry is not proof of the full union: entries carry no version, so a partial entry an older reader wrote (first rules page only, or classic only) or a future-dated entry passed as `cache`. Fixed: forced live read, `cache` refused; tests use the real shared reader with a planted partial entry (re-read live → `smoke` kept) and a future-dated one (no relief).
- `classifyPr`'s relief gate went through `reviewCiGate`, which drops `integration` when it has no row and `test` is green (`withoutImpliedRequiredChecks`). GitHub enforces each required check by its own row, so that PR would be enqueued and refused. Fixed in scripts/merge-ai-prs.mjs: any required check with no rollup row refuses relief as `missing`; test added.
